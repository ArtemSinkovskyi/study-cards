Lecture 10: tool design and MCP (domain 2)

Based on the exam course, domain 2: Tool Design & MCP Integration. Cards: groups "Інструменти: дизайн і помилки" and "MCP і вбудовані інструменти", test "Домен 2".

The main idea

The model sees your tool only through its name, its description and the errors it returns. A badly designed tool does not crash: the agent just quietly behaves worse.

Step 1. The description is the selection mechanism

Claude cannot see the function's code. It picks a tool from its name and description, like a shopper reading the label on a box.

A good description has four parts:

Part Example
What it does "Finds a customer's orders by email"
When to use it and when not "Not for lookup by order number: use get_order_by_id"
Each parameter in plain words "email: the customer's address as in their profile"
A short sample call search_orders_by_customer(email="a@b.com")

"When not to use it" is the part people skip, and it is exactly what stops the model reaching for the wrong tool.

Names. getData and fetchData sound the same, and the model mixes them up. Prefer get_order_by_id and search_orders_by_customer. Overlapping names and descriptions are a top cause of wrong-tool calls.

Split or consolidate. Split distinct actions: instead of handle_travel(action, ...) offer search_flights, book_flight, cancel_booking. Consolidate steps that always go together. Avoid both extremes: dozens of tiny tools, or one do-everything tool.

Step 2. Errors the model can act on

"Booking failed" says nothing. "Payment failed: insufficient balance, try another method" gives the model a next move.

  • Return the error, do not throw. isError: true with details is something the model sees and can react to. A thrown exception becomes a low-level protocol error.
  • The error category (errorCategory) points to the next move:
Category What the model should do
validation Fix the input and retry
auth / permission Escalate
not_found Nothing there, report it
rate_limit / transient Wait, then retry
  • isRetryable says whether retrying makes sense: true for transient and rate_limit, false for validation, auth and business rules. A refund over the limit is never retryable: the answer will be "no" every time.
  • An empty result is not an error. isError: false, resultCount: 0 means "nothing found". An error is "could not reach the database". The classic trap: an agent retrying a successful empty query.
  • The error text: what was attempted, what failed, what to do next. No stack trace: it confuses the model and leaks your internals. Replace "no such table: users_v2" with "The requested resource could not be accessed."

Step 3. How many tools, and tool_choice

Give an agent 60 tools and selection accuracy drops. Each role gets only its own tools: a reporting agent does not need the refund tool.

The tool set is the menu. tool_choice decides whether the model may order and what:

таблицю можна гортати вбік →
Mode What it does When to use it
auto The model decides (the default) An ordinary assistant
any Must call some tool "Act, but you choose how", structured output
tool Must call the named tool A non-negotiable step: always save_report
none No tools A text-only reply

In the course, any and tool cannot be combined with extended thinking. Also remember from lecture 3: on Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1 these two modes return 400.

Step 4. MCP

MCP is USB-C for tools: one standard plug instead of a custom connector for every system.

  • Tools are actions (create_issue, run_query). Resources are read-only data (a file, a schema). In Claude Code you pull a resource in with @.
  • Transport: stdio is a local program Claude launches (command, args). http is a remote server at a url.
  • Secrets: never paste a key into the file. Write ${GITHUB_TOKEN} or ${VAR:-default}. It works in command, args, env, url, headers.

Three scopes in Claude Code:

таблицю можна гортати вбік →
Scope Where it lives Who sees it
local ~/.claude.json Only you, in this project (the default)
project .mcp.json in git The whole team
user ~/.claude.json You, in all projects

Same-named server: local > project > user. A personal token in project scope leaks to the whole team. Check server status with /mcp. Name servers clearly: github, stripe-prod, not server1.

Step 5. Claude Code built-in tools

Tool Job
Read Open a file
Write Create or overwrite a whole file
Edit Replace an exact part of a file
Bash Run a command
Grep Search inside files
Glob Find files by name
  • Grep or Glob: contents or names. The exam tests this directly.
  • Read before Edit. The text to replace must match exactly and be unique. Not unique: widen the surrounding text or use replace_all. Read plus Write is only the last resort.
  • Built-in tools beat cat, grep, find in Bash: finer permissions and fewer prompts. Keep Bash for running tests and builds.
  • Locate first with Grep or Glob, then read only those files.

What to remember for the exam

  • The model picks a tool from its name and description.
  • Return errors with isError, a category and isRetryable, never a stack trace.
  • An empty result is a success, not a failure.
  • tool for a mandatory step, any for structured output.
  • MCP: local > project > user, keys through ${VAR}.
  • Grep for contents, Glob for names, Read before Edit.

Check yourself

  1. Which part of a description do people skip most?
  2. What does a tool that found nothing return?
  3. What is isRetryable for a business-rule error?
  4. Where does an MCP server for the whole team live?
  5. What finds every *.test.js?
Answers
  1. When to use it and when not.
  2. isError: false and 0 results.
  3. false.
  4. .mcp.json in git (project scope).
  5. Glob.
