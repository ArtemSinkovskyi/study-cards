Лекція 12: промпти, структурований вивід і рев'ю (домен 4)

За курсом до іспиту, домен 4: Prompt Engineering & Structured Output. Картки групи «Структурований вивід і рев'ю», тест «Домен 4». Базові техніки промптів у лекції 4.

Головна ідея

Форму відповіді гарантує схема, а правильність перевіряє ваш код. Довкола цього: чіткі критерії, приклади, валідація з повтором, пакетна обробка й рев'ю в кілька проходів.

Крок 1. Явні критерії

На «Чи добрий цей код?» Claude вигадує власне мірило, і воно плаває від запуску до запуску.

Розмито (побажання) Конкретно (перевірно)
«Перевір безпеку» «Познач SQL-запит, зібраний конкатенацією рядків»

Критерій, який не можна перевірити вручну, застосовуватиметься непослідовно.

Рівні серйозності:

Рівень Приклад
critical Пароль у коді: блокує реліз
major Немає обробки помилок: виправити скоро
minor Непослідовна назва: бажано

Хибні спрацювання. False positive: позначено те, що насправді нормально. 18 зайвих позначок ховають 2 справжні, і люди перестають читати взагалі. Шумний рецензент гірший за відсутнього.

Що робити: звузити правило шумної категорії або вимкнути її. Фраза «будь уважнішим» не допомагає. Налаштований рецензент знаходить менше, і саме тому команда діє за його зауваженнями.

Крок 2. Few-shot

Shot означає приклад. Zero-shot: без прикладів. One-shot: один. Few-shot: кілька.

  • Один приклад замінює абзац правил: показує тон, формат і крайні випадки одразу.
  • Приклади фіксують значення розмитих міток («терміново») і формат відповіді.
  • Модель вчиться шаблону, а не конкретним прикладам: показали 3 адреси «брудна → чиста», вона почистить четверту.
  • Додайте приклад, де даних нема і правильна відповідь null. Якщо всі приклади «повні», модель вирішить, що значення має бути завжди, і вигадуватиме.

Які приклади: правильні, різні, з крайніми випадками. Скільки: зазвичай 2-5, зупиняйтесь, коли точність перестає рости. Формат у всіх однаковий. Стоять перед реальним входом.

Крок 3. Структурований вивід через tool_use

Вільний текст ненадійний для автоматизації: модель може додати «Ось дані:» чи markdown-огорожу, і парсер зламається.

За курсом стандартний прийом такий: інструмент зі схемою. Ви описуєте інструмент з input_schema, і відповідь моделі стає входом цього інструмента.

{
  "name": "extract_claim",
  "input_schema": {
    "type": "object",
    "properties": {
      "claim_id": {"type": "string"},
      "amount": {"type": "number"},
      "phone": {"type": ["string", "null"]},
      "type": {"enum": ["auto", "home", "health", "other"]},
      "detail": {"type": "string"}
    },
    "required": ["claim_id", "amount"]
  }
}
  • Обов'язкові й nullable поля. Поле, якого може не бути в документі, робіть необов'язковим або nullable. Обов'язкове поле без даних модель заповнить вигадкою. Це виправлення в корені, а не прохання «не вгадуй».
  • Enum з other. Без запасного варіанта незвичний вхід потрапить у найближчий неправильний. other плюс detail тримає відповідь чесною.
  • tool_choice. На auto модель може відповісти текстом. Беріть any або tool з назвою, щоб виклик був гарантований.
  • Схему з помилкою API відхилить одразу (400), ще до запуску моделі.

У самому API є ще режим structured outputs і strict: true (лекція 3). Принцип той самий.

Чого це не виправляє. Форму гарантовано, правду ні: суми можуть не сходитись, значення може бути вигаданим чи в чужому полі.

Крок 4. Валідація й повтор з відгуком

Помилка Приклад Хто ловить
Синтаксична Зламаний JSON Схема й tool_use
Семантична Правильна форма, неправильний зміст Ваша валідація

Що перевіряти: чи сходяться суми, чи дати реальні й у межах, чи кожне значення справді є в документі.

Якщо перевірка не пройшла, надішліть моделі документ, хибний результат і конкретну помилку: «позиції дають 4 800, а total 5 000». «Неправильно» майже не допомагає.

Ліміт: 2-3 спроби. Далі людині або позначка низької впевненості. Без ліміту цикл може крутитись вічно.

Крок 5. Message Batches API

Що Значення
Ціна На 50% дешевше вхід і вихід
Час До 24 годин (часто швидше)
Стрімінг Нема
Розмір До 100 000 запитів або 256 МБ
Зберігання результатів Близько 29 днів: зберігайте одразу

Правило вибору: чи можна користувачу отримати це протягом 24 годин? Так: batch (масове витягання, оцінки, модерація). Ні: звичайний API (чат, живий інтерфейс).

Результати приходять не по порядку, тож кожному запиту дайте custom_id зі свого запису (номер заяви), а не випадковий.

Процес: подати, перевіряти статус, забрати JSONL, зберегти. Кожен результат далі проходить ту саму валідацію з кроку 4.

Крок 6. Рев'ю в кілька проходів

Один прохід пропускає речі: увага розпорошується, а автор, що перевіряє себе, схильний схвалювати.

  • Незалежний рецензент: окремий екземпляр з чистим контекстом.
  • Прохід по кожному файлу ловить локальні помилки, прохід по зв'язках ловить невідповідність інтерфейсів. Потрібні обидва.
  • Впевненість на кожній знахідці: висока застосовується, низька йде людині.
  • Злиття: прибрати дублікати, лишити найвищу серйозність, згрупувати за впевненістю.

Що запам'ятати на іспит

  • Критерії конкретні й перевірні, з рівнями серйозності. Шумну категорію звужують або вимикають.
  • Few-shot: 2-5 різних прикладів однакового формату перед входом, серед них приклад із null.
  • Структурований вивід: tool_use зі схемою і tool_choice any або tool.
  • Nullable поля проти вигадок, enum з other.
  • Схема гарантує форму, валідація перевіряє зміст. Повтор з конкретною помилкою, ліміт 2-3.
  • Batch: 50% дешевше, до 24 годин, custom_id.

Перевірте себе

  1. Що робити з категорією, яка дає багато хибних спрацювань?
  2. Навіщо приклад із null серед few-shot?
  3. Як не дати моделі вигадати телефон?
  4. Хто ловить суму, що не сходиться?
  5. Коли Batch API не підходить?
Відповіді
  1. Звузити правило або вимкнути категорію.
  2. Щоб модель не вигадувала значення, коли даних нема.
  3. Зробити поле nullable або необов'язковим.
  4. Ваша валідація, а не схема.
  5. Коли користувач чекає відповіді зараз.
