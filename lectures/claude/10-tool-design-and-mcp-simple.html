Лекція 10: дизайн інструментів і MCP (домен 2)

За курсом до іспиту, домен 2: Tool Design & MCP Integration. Картки груп «Інструменти: дизайн і помилки» та «MCP і вбудовані інструменти», тест «Домен 2».

Що з цього питають на іспиті

Як описати й назвати інструмент, щоб модель не помилилась. Як повертати помилки. Який tool_choice узяти. Де лежить MCP-сервер і як сховати ключ. Grep чи Glob.

Головна ідея

Модель знає про твій інструмент лише назву, опис і помилки, які він повертає. Погано спроєктований інструмент не падає: агент просто тихо працює гірше.

Крок 1. За описом модель обирає інструмент

Claude не бачить коду функції. Він обирає інструмент за назвою й описом, як покупець за етикеткою на коробці.

Добрий опис має чотири частини:

Частина Приклад
Що робить «Шукає замовлення клієнта за email»
Коли брати і коли ні «Не для пошуку за номером замовлення: для цього get_order_by_id»
Кожен параметр простими словами «email: адреса клієнта, як у профілі»
Короткий приклад виклику search_orders_by_customer(email="a@b.com")

Частину «коли ні» найчастіше пропускають, а саме вона не дає моделі схопити не той інструмент.

Назви. getData і fetchData звучать однаково, і модель їх плутає. Краще get_order_by_id і search_orders_by_customer. Схожі назви й описи одна з головних причин виклику не того інструмента.

Розбити чи об'єднати. Різні дії розбивай: замість handle_travel(action, ...) дай search_flights, book_flight, cancel_booking. Кроки, що завжди йдуть разом, об'єднуй. Уникай обох крайнощів: десятків дрібних інструментів і одного «на все».

Крок 2. Помилки, з якими модель може щось зробити

«Booking failed» нічого не каже. «Оплата не пройшла: недостатньо коштів, спробуйте інший спосіб» підказує моделі наступний крок.

  • Повертай помилку, а не кидай виняток. isError: true з поясненням модель бачить і може відреагувати. Виняток стає низькорівневою помилкою протоколу.
  • Категорія помилки (errorCategory) підказує, що робити далі:
Категорія Що робити моделі
validation Виправити вхід і повторити
auth / permission Передати далі (ескалювати)
not_found Нічого немає, так і сказати
rate_limit / transient Почекати й повторити
  • isRetryable каже, чи є сенс пробувати ще раз: true для transient і rate_limit, false для validation, auth і бізнес-правил. Повернення понад ліміт ніколи не повторюють: відповідь щоразу буде «ні».
  • Порожній результат не помилка. isError: false, resultCount: 0 означає «нічого не знайдено». Помилка це коли до бази не вдалося дістатися. Класична пастка: агент повторює успішний порожній запит.
  • Текст помилки: що пробував, що зламалось, що робити далі. Без stack trace: він плутає модель і розкриває внутрішню будову. «no such table: users_v2» заміни на «Запитаний ресурс недоступний».

Крок 3. Скільки інструментів і tool_choice

Дай агенту 60 інструментів, і точність вибору впаде. Кожна роль отримує лише свої інструменти: агенту звітів не потрібне повернення коштів.

Набір інструментів це меню. tool_choice вирішує, чи можна замовляти і що саме:

таблицю можна гортати вбік →
Режим Що робить Коли брати
auto Модель вирішує сама (за замовчуванням) Звичайний асистент
any Мусить викликати якийсь інструмент «Дій, але сам обери як», структурована відповідь
tool Мусить викликати названий Обов'язковий крок: завжди save_report
none Без інструментів Відповідь лише текстом

За курсом any і tool не поєднуються з extended thinking. Окремо з документації (лекція 3): на Opus 5.5, Sonnet 5.5, Fable 5.1 і Mythos 5.1 ці два режими дають 400.

Крок 4. MCP

MCP це USB-C для інструментів: один стандартний роз'єм замість окремого кабелю для кожної системи.

  • Tools це дії (create_issue, run_query). Resources це дані лише для читання (файл, схема). У Claude Code resource підтягують через @.
  • Транспорт: stdio це локальна програма, яку запускає Claude (command, args). http це віддалений сервер за url.
  • Секрети: не вписуй ключ у файл. Пиши ${GITHUB_TOKEN} або ${VAR:-default}. Це працює в command, args, env, url, headers.

Три scope у Claude Code:

таблицю можна гортати вбік →
Scope Де лежить Кому видно
local ~/.claude.json Лише тобі в цьому проєкті (за замовчуванням)
project .mcp.json у git Усій команді
user ~/.claude.json Тобі в усіх проєктах

Однойменний сервер: local > project > user. Особистий токен у project scope побачить уся команда. Стан серверів видно в /mcp. Називай сервери зрозуміло: github, stripe-prod, а не server1.

Крок 5. Вбудовані інструменти Claude Code

Інструмент Що робить
Read Відкриває файл
Write Створює або переписує весь файл
Edit Точно замінює частину файла
Bash Запускає команду
Grep Шукає всередині файлів
Glob Шукає файли за іменем
  • Grep чи Glob: вміст чи імена. Іспит перевіряє це напряму.
  • Read перед Edit. Текст для заміни має збігатися точно й бути унікальним. Не унікальний: розшир навколишній текст або replace_all. Read і Write лише як останній варіант.
  • Вбудовані інструменти кращі за cat, grep, find у Bash: точніші дозволи й менше запитів. Bash лишай для тестів і збірки.
  • Спершу знайди потрібне через Grep чи Glob, потім читай лише ці файли.

Що запам'ятати на іспит

  • Модель обирає інструмент за назвою й описом.
  • Помилку повертають з isError, категорією та isRetryable, без stack trace.
  • Порожній результат це успіх, а не збій.
  • tool для обов'язкового кроку, any для структурованої відповіді.
  • MCP: local > project > user, ключі через ${VAR}.
  • Grep для вмісту, Glob для імен, Read перед Edit.

Перевір себе

  1. Яку частину опису найчастіше пропускають?
  2. Що повертає інструмент, який нічого не знайшов?
  3. Яке isRetryable у помилки бізнес-правила?
  4. Де лежить MCP-сервер для всієї команди?
  5. Чим знайти всі *.test.js?
Відповіді
  1. Коли брати і коли ні.
  2. isError: false і 0 результатів.
  3. false.
  4. .mcp.json у git (project scope).
  5. Glob.
