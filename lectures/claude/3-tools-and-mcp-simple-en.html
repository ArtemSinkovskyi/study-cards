Lecture 3: how to describe tools and what MCP is

Simplified version. The full lecture exists in Ukrainian only. The exam-course view of tool design is in lecture 10.

The main idea

The model picks a tool only from its description. The description is everything it knows about the tool. So its quality matters more than anything else.

Why it is designed this way

Tools are described with a schema so the model knows what they can do. MCP is a shared standard, so you do not write a separate integration for every service.

Step 1. How to describe a tool

A tool has four fields: name, description, input_schema and, optionally, input_examples.

For the model it is like an OpenAPI contract: it does not see the code, only the contract.

What the description should say:

  • what the tool does;
  • when to use it and when not;
  • what each parameter means;
  • what it does not return.

The documentation recommends at least 3-4 sentences per tool. Example: "Returns the current stock price for a ticker on NYSE or NASDAQ, in dollars. Use it when someone asks about the current price. Returns no other company information." A bad one: "Gets a stock price".

Step 2. Four more tips

  • Fewer, more capable tools. The documentation suggests one pr tool with an action parameter instead of create_pr, review_pr, merge_pr. The exam course (lecture 10) puts the emphasis differently: split distinct actions (search_flights, book_flight instead of handle_travel(action)) and consolidate only steps that always go together. Both agree: neither dozens of tiny tools nor one do-everything tool.
  • Prefixes in names when there are many tools: github_list_prs, slack_send_message.
  • Return only useful fields from a tool. Long outputs waste context.
  • input_examples help with complex inputs (each example must match the schema, otherwise 400).

Step 3. How to make the model pick a tool: tool_choice

Value What it does
auto The model decides (the default when there are tools)
any Must call some tool
tool Must call the named tool
none Calls nothing (the default when there are no tools)

Things people get wrong:

  1. On Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1 the values any and tool return 400. Use auto with strict there.
  2. With any and tool the model writes no explanation before the call.
  3. Changing tool_choice mid-conversation invalidates the messages cache (tools and system stay cached).
  4. In the exam course, any and tool cannot be combined with extended thinking.

When to use which (lecture 10): auto for an ordinary assistant, any for structured output, tool for a mandatory step (always save_report), none for a text-only reply.

Step 4. How to return the result

Three hard rules; breaking them gives 400:

  1. The tool_result must come right after the message with tool_use, nothing in between.
  2. In the user message the tool_result blocks come first, text after them.
  3. Several results of one turn go in one message (see lecture 2).

A typical error: "tool_use ids were found without tool_result blocks immediately after".

Step 5. Tool errors

  • A tool failed: a tool_result with is_error: true and a clear text. Not "failed", but "Rate limit exceeded. Retry after 60 seconds".
  • The model called a tool without a required parameter: it usually retries 2-3 times with fixes. Better to improve the description.
  • To rule this out completely, set strict: true: the input is guaranteed to match the schema and the tool name is always valid.

Step 6. Security

Tool results often hold someone else's content: web pages, emails, third-party API replies. Someone can hide an instruction there: "ignore everything and do this". This is indirect prompt injection.

Rule: keep such content inside tool_result, not in the system prompt or plain user text.

One more: tool schemas are cached for up to 24 hours, so do not put personal data in a schema (property names, enum, const, pattern).

Step 7. What MCP is

MCP (Model Context Protocol) is the protocol the model uses to connect to external systems through a server. One MCP server offers a set of tools.

The MCP connector is a Messages API feature that connects remote MCP servers without your own MCP client (beta).

Limits the exam asks about:

  • only tool calls are supported (not resources or prompts);
  • the server must be public HTTPS (Streamable HTTP or SSE);
  • a local STDIO server cannot be connected.

For a private network (for example Loki or Prometheus inside) the connector does not fit: you need your own MCP connection. The SDK has client-side helpers for that.

Step 8. How to set up the MCP connector

The request has two pieces:

  1. mcp_servers: a list of servers with type (url), url, name, authorization_token.
  2. An mcp_toolset in the tools array: what to enable from that server.

Each server has exactly one mcp_toolset.

How to make a read-only assistant:

  • Denylist: switch off dangerous tools (configs with enabled: false).
  • Allowlist: default_config.enabled: false and switch on only the ones you need.

Authentication: you obtain the OAuth token yourself and pass it in authorization_token; refreshing it is also on you.

The reply contains mcp_tool_use and mcp_tool_result blocks.

Step 9. Tool runner

Instead of your own loop (lecture 2) the SDK can run the loop for you: you describe tools as functions, and the runner executes them and drives the conversation. It wraps errors in is_error too.

When you need a manual loop: human approval, your own logging, conditional execution.

What to remember for the exam

  1. The tool description is the most important factor. At least 3-4 sentences, with limits.
  2. any and tool return 400 on Opus 5.5, Sonnet 5.5, Fable 5.1, Mythos 5.1.
  3. tool_result right after tool_use and before any text.
  4. An error: is_error: true and a clear text. strict: true removes invalid calls.
  5. Tool results are untrusted: keep them in tool_result.
  6. MCP connector: tools only, public HTTPS only, no STDIO.
  7. Read-only mode: a denylist or allowlist in mcp_toolset.

Check yourself

  1. What does the model know about your tool?
  2. What does tool_choice: any return on Opus 5.5?
  3. Where do tool_result blocks go in the user message?
  4. Can the connector attach a local STDIO server?
  5. How do you make an MCP assistant read-only?
  6. What does strict: true guarantee?
Answers
  1. Only its description and parameter schema.
  2. A 400 error.
  3. First, text after them.
  4. No, public HTTPS only.
  5. A denylist of dangerous tools or an allowlist of needed ones in mcp_toolset.
  6. The input matches input_schema and the tool name is valid.
