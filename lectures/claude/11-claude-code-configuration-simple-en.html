Lecture 11: Claude Code configuration and workflows (domain 3)

Based on the exam course, domain 3: Claude Code Configuration & Workflows. Cards: groups "Claude Code: пам'ять і налаштування" and "Claude Code: команди й CI", test "Домен 3". Permissions and hooks in detail are in lecture 5.

The main idea

Explain your project once, not every session. Standing rules go into CLAUDE.md and .claude/rules, repeatable actions into commands and skills, risky work into plan mode, automated work into CI.

Step 1. The CLAUDE.md hierarchy

CLAUDE.md is a note Claude reads at the start of every session: build commands, conventions, gotchas.

таблицю можна гортати вбік →
Level Where it lives What it is for
user ~/.claude/CLAUDE.md Your preferences across all projects
project ./CLAUDE.md Team rules, in git
directory a nested CLAUDE.md Rules for one folder

Organisation policy (managed) sits on top of everything.

  • The levels combine into one context; one does not replace another.
  • On a conflict the more specific one wins. You say 2 spaces, the project says 4: it is 4.
  • A nested frontend/CLAUDE.md loads only when Claude works on files in that folder. That saves large monorepos.
  • @docs/style.md imports another file. Imports keep things tidy but do not shrink the context: imported files load at launch.
  • /memory opens memory files for editing.

What to write: what Claude cannot guess (pitfalls, departures from defaults, the reason behind a rule). What to skip: folder layout, dependency lists. Keep it under about 200 lines: a bloated CLAUDE.md is followed less well.

Step 2. Rules for part of the code: .claude/rules

  • Every .md in .claude/rules/ loads as project memory, at the same priority as .claude/CLAUDE.md.
  • With a paths: frontmatter (a list of glob patterns) the rule loads only for matching files. For example paths: ["src/api/**"].
  • Without paths: the rule always applies.
You need Pick
A pattern across the repo (every *.test.js) A rule with paths:
Everything in one folder A CLAUDE.md in that folder

Path rules are appended last, so they win on a conflict: broad first, most specific last.

Step 3. Commands and skills

A slash command is a Markdown file:

  • .claude/commands/ for the whole team (in git) or ~/.claude/commands/ for you alone;
  • the file name becomes the command, the body becomes the prompt;
  • $ARGUMENTS drops in your input: fix-issue.md runs as /fix-issue 123.

Command frontmatter: description (shown in /help, lets Claude suggest the command), argument-hint, allowed-tools, model.

A skill is the richer form: .claude/skills/<name>/SKILL.md also gives /name, but it has a folder for supporting files and Claude can invoke it on its own. Commands are now merged into skills. On a name clash the skill wins.

Three fields the exam likes:

Field What it does
context: fork Runs the skill in an isolated context
allowed-tools Pre-approves the listed tools. It does not block the others
disable-model-invocation: true Only you can trigger it: for /commit, /deploy

CLAUDE.md or a command? Standing conventions go into CLAUDE.md (always on). Repeatable tasks become a command or skill (on demand).

Step 4. Plan mode

Plan mode is read-only: Claude explores and writes a plan, and Write and Edit are blocked at the tool level until you approve the plan. It is a block, not a polite request.

How to turn it on: Shift+Tab twice, /plan, or --permission-mode plan (also works with -p).

Plan No need
Several files, refactors, migrations A single-file tweak
Auth, payments, production Small quick edits
An unfamiliar repo, an ambiguous task

The loop: explore, plan, approve (or edit the plan first), execute, verify with tests.

The Explore subagent is a scout with only Read, Grep and Glob. It reads in a separate context and returns only the findings, so heavy reading does not clutter your session.

Step 5. Iteration

  • Treat the first result as a draft.
  • Show an input/output example: it removes guesswork better than a long description.
  • Interview pattern: ask Claude to question you first (framework, error handling, edge cases). A fuzzy ask becomes a spec.
  • Test first: write the test that must pass and let Claude iterate to green.
  • Batch independent fixes, sequence dependent ones.

Step 6. Claude Code in CI/CD

  • claude -p "prompt" is headless mode: it runs, prints the result and exits with a status code.
  • --output-format json returns the result plus metadata (cost, session_id), parsed with jq. Formats: text, json, stream-json.
  • --json-schema guarantees the shape of the result in structured_output: use it when a later step branches on the result.
  • Limits, because nobody is watching: --max-turns, --allowedTools, --max-budget-usd. Check the output content, not just the exit code.
  • CLAUDE.md loads in CI too: your rules become the reviewer's context.
  • A separate instance does the review: it never saw the author's reasoning and does not defend its own choices.

What to remember for the exam

  • CLAUDE.md: user, project and directory combine; the more specific wins.
  • A pattern across the repo: a rule with paths:. One folder: a CLAUDE.md in it.
  • allowed-tools pre-approves but does not restrict.
  • disable-model-invocation: true for commands with side effects.
  • Plan mode blocks Write and Edit until approval.
  • CI: -p, --output-format json, --json-schema, turn and budget caps.

Check yourself

  1. You say 2 spaces, the project says 4. Which applies?
  2. What happens to other tools if a skill has allowed-tools: Read?
  3. How do you turn on plan mode?
  4. How do you guarantee the shape of a claude -p result?
  5. Why use a separate instance for review?
Answers
  1. 4: the more specific level wins.
  2. Nothing: they stay available as usual.
  3. Shift+Tab twice, /plan or --permission-mode plan.
  4. --output-format json with --json-schema.
  5. It is not biased by the author's choices.
