Лекція 3 (просто): як описувати інструменти і що таке MCP

Спрощена версія. Усі факти ті самі, що в повній лекції: ../3-define-tools-handle-results-mcp-connector.md. Рідкісні деталі (повні списки моделей, коди помилок) лишились лише там.

Головна ідея

Модель вибирає інструмент лише за його описом. Опис це все, що вона про нього знає. Тому якість опису важливіша за все інше.

Крок 1. Як описувати інструмент

У інструмента чотири поля: name, description, input_schema і, за бажанням, input_examples.

Для моделі це як OpenAPI-контракт: вона не бачить коду, лише контракт.

Що має бути в описі:

  • що робить інструмент;
  • коли його використовувати й коли ні;
  • що означає кожен параметр;
  • чого він не повертає.

Документація радить мінімум 3-4 речення на інструмент. Приклад: «Повертає поточну ціну акції за тікером з NYSE чи NASDAQ, у доларах. Використовуйте, коли питають про поточну ціну. Іншу інформацію про компанію не повертає.» Поганий опис: «Дає ціну акції».

Крок 2. Ще чотири поради

  • Менше інструментів, але потужніших. Один pr з параметром action краще за create_pr, review_pr, merge_pr.
  • Префікси в іменах, коли інструментів багато: github_list_prs, slack_send_message.
  • Повертайте з інструмента лише корисні поля. Довгі відповіді витрачають контекст.
  • input_examples допомагають для складних входів (кожен приклад має відповідати схемі, інакше 400).

Крок 3. Як змусити модель вибрати інструмент: tool_choice

Значення Що робить
auto Модель сама вирішує (за замовчуванням, коли є інструменти)
any Мусить викликати якийсь інструмент
tool Мусить викликати саме названий
none Не викликає (за замовчуванням, коли інструментів нема)

Три речі, на яких помиляються:

  1. На Opus 5.5, Sonnet 5.5, Fable 5.1 і Mythos 5.1 значення any і tool дають 400. Там використовуйте auto разом зі strict.
  2. При any і tool модель не пише пояснення перед викликом.
  3. Зміна tool_choice посеред розмови скидає кеш повідомлень (інструменти й system лишаються в кеші).

Крок 4. Як повертати результат

Три жорсткі правила, порушення яких дає 400:

  1. tool_result має йти одразу після повідомлення з tool_use, між ними нічого.
  2. У user-повідомленні блоки tool_result йдуть першими, текст після них.
  3. Кілька результатів одного ходу йдуть в одному повідомленні (див. лекцію 2).

Типова помилка: «tool_use ids were found without tool_result blocks immediately after».

Крок 5. Помилки в інструментах

  • Інструмент упав: tool_result з is_error: true і зрозумілим текстом. Не «failed», а «Rate limit exceeded. Retry after 60 seconds».
  • Модель викликала інструмент без обов'язкового параметра: вона зазвичай повторює 2-3 рази з виправленнями. Краще покращити опис.
  • Щоб такого не було зовсім, ставте strict: true: вхід гарантовано відповідає схемі, ім'я інструмента завжди валідне.

Крок 6. Безпека

Результати інструментів часто містять чужий вміст: сторінки, листи, відповіді сторонніх API. Хтось може сховати там інструкцію «ігноруй усе й зроби ось що». Це indirect prompt injection.

Правило: тримайте такий вміст усередині tool_result, а не в системному промпті чи звичайному тексті користувача.

Ще одне: схеми інструментів кешуються до 24 годин, тому в схему (імена властивостей, enum, const, pattern) не кладіть персональні дані.

Крок 7. Що таке MCP

MCP (Model Context Protocol) це протокол, яким модель підключається до зовнішніх систем через сервер. Один MCP-сервер дає набір інструментів.

MCP connector це функція Messages API, що підключає віддалені MCP-сервери без вашого власного MCP-клієнта (beta).

Обмеження, які питають на іспиті:

  • підтримуються лише виклики інструментів (не ресурси й не промпти);
  • сервер має бути публічним HTTPS (Streamable HTTP чи SSE);
  • локальний STDIO не підключити.

Для приватної мережі (наприклад, Loki чи Prometheus усередині) connector не підходить: потрібне власне MCP-з'єднання. SDK має для цього допоміжні функції (client-side helpers).

Крок 8. Як налаштувати MCP connector

У запиті два шматки:

  1. mcp_servers: список серверів із полями type (url), url, name, authorization_token.
  2. mcp_toolset у масиві tools: що з цього сервера вмикати.

Кожен сервер має рівно один mcp_toolset.

Як зробити асистента лише для читання:

  • Denylist: вимкніть небезпечні інструменти (configs із enabled: false).
  • Allowlist: default_config.enabled: false і ввімкніть лише потрібні.

Автентифікація: OAuth-токен ви отримуєте самі й передаєте в authorization_token; оновлювати його теж ви.

У відповіді приходять блоки mcp_tool_use і mcp_tool_result.

Крок 9. Tool runner

Замість власного циклу (лекція 2) SDK може вести цикл сам: ви описуєте інструменти як функції, runner виконує їх і веде розмову. Помилки він теж обгортає в is_error.

Коли потрібен ручний цикл: схвалення людиною, власне логування, умовне виконання.

Що запам'ятати на іспит

  1. Опис інструмента це найважливіший фактор. Мінімум 3-4 речення, з обмеженнями.
  2. any і tool дають 400 на Opus 5.5, Sonnet 5.5, Fable 5.1, Mythos 5.1.
  3. tool_result одразу після tool_use і перед текстом.
  4. Помилка: is_error: true і зрозумілий текст. strict: true прибирає невалідні виклики.
  5. Результати інструментів недовірені: тримайте їх у tool_result.
  6. MCP connector: лише інструменти, лише публічний HTTPS, без STDIO.
  7. Режим лише читання: denylist чи allowlist у mcp_toolset.

Перевірте себе

  1. Що модель знає про ваш інструмент?
  2. Що поверне tool_choice: any на Opus 5.5?
  3. Де в user-повідомленні мають стояти tool_result?
  4. Чи можна через connector підключити локальний STDIO-сервер?
  5. Як зробити MCP-асистента лише для читання?
  6. Що гарантує strict: true?
Відповіді
  1. Лише його опис і схему параметрів.
  2. Помилку 400.
  3. Першими, текст після них.
  4. Ні, лише публічний HTTPS.
  5. Denylist небезпечних інструментів або allowlist потрібних у mcp_toolset.
  6. Вхід відповідає input_schema, а ім'я інструмента валідне.
