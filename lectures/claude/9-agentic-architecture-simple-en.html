Lecture 9: agents and orchestration (domain 1)

Based on the exam course, domain 1: Agentic Architecture & Orchestration. Cards: group "Агенти й оркестрація", test "Домен 1".

The main idea

Everything in domain 1 is built around the agentic loop. Coordinators, subagents, hooks, task decomposition and sessions are things we do around that loop.

The exam tests decisions: which pattern to pick and why.

Step 1. The agentic loop

A chatbot answers once. An agent keeps going until the job is done.

Step What happens
Perceive The model reads the request
Reason It decides what to do
Act It calls a tool
Observe It reads the result and goes round again

One field drives the loop, stop_reason:

  • tool_use: run the tool, send back a tool_result, call the model again;
  • end_turn: the model is done, leave the loop.

Example. "Where's my refund for order 9931?" The model calls look_up_order(9931), sees no refund on file, calls check_refund_policy(), sees "eligible" and answers (end_turn). The model chose each tool from the previous result. That is the loop reasoning, not a fixed script.

Three anti-patterns (common wrong answers on the exam):

  1. ignoring stop_reason;
  2. no end condition (an infinite loop);
  3. not feeding tool results back: the model flies blind.

The exam favours a model-driven loop: the model picks the next tool from context. An if/else tree breaks on cases you did not foresee.

Step 2. Coordinator and subagents

A big job with several parts (research, analysis, writing) clutters one agent's context. The answer is hub-and-spoke.

  • The coordinator hands work to subagents.
  • Subagents report only to the coordinator and never talk to each other.
  • Each subagent has a clean context with only its own part.

The coordinator's jobs: route, select the subagents, handle their errors, synthesize the results. It does not do the task itself. After synthesizing it can judge the result and send work back for another pass.

Independent parts run in parallel, dependent ones in sequence.

The narrow-decomposition trap. A question about "the creative industries" went only to a visual-arts subagent, so music, film and design were lost. The pieces must add up to the whole question.

A simple single-threaded job does not need a coordinator.

Step 3. Spawning a subagent and what to give it

A subagent is spawned with the Task tool (newer Claude Code versions call it Agent). Several such calls in one turn run the subagents in parallel.

Four fields describe a subagent:

Field What it sets
description When the coordinator should use it
prompt How it behaves
tools Only the tools it needs
model Optional: a cheaper model for simple work

A subagent inherits nothing. It sees neither the coordinator's conversation nor other subagents' findings. So its prompt must hold:

  • the goal and the quality bar ("find the top 3, with sources");
  • the facts it needs;
  • complete, structured prior findings, not a one-line summary.

Give a goal, not step-by-step directions: the subagent has its own loop.

Step 4. When a rule must always hold

Way What you get
Prompt Probable compliance: usually holds
Code or hook Guaranteed compliance: always holds

Ask yourself: what happens if Claude ignores this rule once? If the harm is serious (payment without an identity check, a refund over the limit), it is a rule for code.

  • Prerequisite gate: code blocks an action until a required step is done. No refund until identity is verified.
  • PreToolUse hook: fires before a tool call and can allow it, modify the input or block it. Canonical example: block any refund over $500 and route it to a human.
  • PostToolUse hook: fires after the call. In the course it is used to transform the result before Claude sees it (normalize timestamps) and for logging.

A handoff to a human carries a structured summary: the customer, the issue, what has been done and the recommended action. The human should not have to re-read everything.

Step 5. How to decompose a task

Situation What to pick
Steps cannot be listed upfront (research, debugging) Adaptive decomposition and orchestrator-workers
Steps are known and depend on each other A sequential chain, prompt chaining
Steps are known and independent Parallel

A code-review example: per-file passes in parallel, then one cross-file pass for how the files fit together.

Step 6. Sessions

  • --resume reopens a specific saved session, --continue the most recent one. The agent keeps its whole prior context.
  • The stale-transcript trap: a resumed session still holds old tool results. If files changed, Claude will act on stale data with confidence.
  • fork_session copies a session for an experiment. Pattern: one stable base session, a fork per investigation, throw the fork away afterwards.
  • If the session is stale, do not resume it: start a fresh one with a short summary of the key facts.

What to remember for the exam

  • tool_use means keep looping, end_turn means stop.
  • "Must never break" means a hook or code, not a prompt.
  • Fixed known steps: prompt chaining. A coordinator directing workers: orchestrator-workers.
  • A subagent inherits nothing: put everything it needs into its prompt.
  • Stale session: summarize and start fresh.

Check yourself

  1. What does your code do when stop_reason is tool_use?
  2. Does a subagent see the coordinator's conversation?
  3. How do you guarantee that no refund goes through without an identity check?
  4. When do you pick orchestrator-workers over prompt chaining?
  5. Why is --resume risky after files have changed?
Answers
  1. Runs the tool, sends back a tool_result and calls the model again.
  2. No. The coordinator writes everything it needs into its prompt.
  3. A prerequisite gate in code or a PreToolUse hook.
  4. When the steps cannot be listed upfront.
  5. Old tool results: the model acts on stale data with confidence.
