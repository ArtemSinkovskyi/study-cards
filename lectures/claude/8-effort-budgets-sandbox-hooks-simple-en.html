Lecture 8: effort, task budget and preserved thinking

Simplified version. The full lecture exists in Ukrainian only. The sandbox and rare hook events were removed from this lecture: they are not on the exam.

What the exam asks about this

How to control spend (effort, budget) and what you must not change in a conversation so you do not break thinking and the cache.

The main idea

Not every task needs maximum effort. Effort and budgets let you pay only for the depth you need. And conversation history can only be appended to, never rewritten.

Part 1. Effort

Effort is the output_config.effort parameter: how much work the model puts in. It affects all tokens: text, tool calls and thinking.

Level When
low Simple tasks, speed, subagents
medium A balance of speed and quality
high Complex tasks
xhigh Long agentic and coding tasks
max The deepest thinking with no limits

What to know:

  • The default is high, and on Opus 5.5 and Haiku 5.5 it is medium.
  • Effort is a signal, not a hard budget. The hard ceiling is max_tokens.
  • adaptive is not an effort level: it is a thinking mode.
  • Lower effort means fewer and shorter tool calls.
  • To make the model think less, lower effort first rather than asking in the prompt.

Changing effort in a conversation

Way What happens to the cache
A new top-level effort value in the next request Invalidates the cache
Per-message effort (a role: "system" message with output_config.effort, beta) Keeps the cache

So in a cached conversation keep the top-level effort constant or use per-message effort.

Part 2. Task budget

A task budget is an advisory token budget for the whole agent loop (many requests). The model sees a countdown and plans its work to finish cleanly.

Rules:

  • the setting is output_config.task_budget with type: "tokens" and total; a beta header is required;
  • minimum 20,000 tokens, less returns 400;
  • it is advisory: the model may slightly exceed it. The hard ceiling is still max_tokens;
  • it counts what the model sees (thinking, calls, results, text), not what you resend in history;
  • not supported in Claude Code;
  • too small a budget can produce refusal-like behaviour: the model stops early.

The remaining field is needed only when your own code compacts the history. Do not decrease it on every request: that invalidates the cache.

Part 3. Preserved thinking (Claude 5.1+)

When you send back a thinking block, the API checks its signature: can the model read it, and has everything before it stayed unchanged.

Rule: work append-only, that is, only add messages at the end.

Allowed Breaks the blocks
Add a message at the end Change system
Change effort, max_tokens, tool_choice Add, remove or change a tool
Add or remove cache_control Change or delete earlier messages
Server compaction or context editing Shorten an earlier tool_result

What to do instead of editing: change system through a role: "system" message at the end, change tools through tool_addition and tool_removal blocks, change effort through per-message effort.

The mismatch mode (thinking.block_binding.prefix_mismatch_behavior):

  • "error": 400. For tests.
  • "drop_block": drops the failing block and all later ones. Only a patch, because it can change quality.

The reply has an input_transformations array listing the dropped blocks. Log it on every turn.

Part 4. Compaction: two additions

  • Keep-tail: the last turns stay verbatim after the summary. The cut must be where no tool call is left open, otherwise the API rejects the request.
  • Background compaction: the summary request runs while the conversation goes on. When the block arrives, drop exactly the messages you sent, and keep later turns after the block.

The condition for both: system and tools do not change, otherwise thinking in the kept turns becomes invalid.

Glossary

Term What it is
Effort how hard the model tries: affects thinking, tool calls and answer length
Task budget an advisory token limit for the whole agent loop, visible to the model
Append-only history is only added to at the end, nothing is rewritten
Per-message effort changing effort through a message, without invalidating the cache

What to remember for the exam

  1. Effort defaults to high, on Opus 5.5 and Haiku 5.5 to medium. It is a signal; the hard ceiling is max_tokens.
  2. Changing the top-level effort invalidates the cache, per-message effort does not.
  3. Task budget: advisory, minimum 20,000, not in Claude Code.
  4. Preserved thinking: append-only. Changing system or tools breaks the blocks.
  5. Log input_transformations every turn.

Check yourself

  1. What is the default effort on Opus 5.5?
  2. What is the minimum task_budget.total?
  3. What breaks preserved thinking blocks?
  4. Why is per-message effort better than changing the top-level value?
  5. Where may you cut the history in keep-tail?
Answers
  1. medium.
  2. 20,000 tokens.
  3. Changing system, the tools or earlier messages.
  4. It keeps the cache.
  5. Where no tool call is left open.
