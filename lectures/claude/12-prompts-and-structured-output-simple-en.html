Lecture 12: prompts, structured output and review (domain 4)

Based on the exam course, domain 4: Prompt Engineering & Structured Output. Cards: group "Структурований вивід і рев'ю", test "Домен 4". Basic prompting techniques are in lecture 4.

The main idea

A schema guarantees the shape of the answer; your code checks that it is right. Around that: clear criteria, examples, validation with retries, batch processing and multi-pass review.

Step 1. Explicit criteria

Ask "Is this code good?" and Claude invents its own yardstick, which drifts from run to run.

Vague (a wish) Specific (testable)
"Check for security problems" "Flag any SQL query built with string concatenation"

A criterion you could not check by hand will be applied inconsistently.

Severity levels:

Level Example
critical A hard-coded password: blocks the release
major Missing error handling: fix soon
minor An inconsistent name: nice to fix

False positives. A false positive flags something that is actually fine. 18 noise flags bury the 2 real ones, and people stop reading altogether. A noisy reviewer is worse than none.

What to do: tighten the noisy category's rule or switch it off. "Be more careful" does not help. A tuned reviewer finds fewer things, and that is exactly why the team acts on them.

Step 2. Few-shot

Shot means example. Zero-shot: no examples. One-shot: one. Few-shot: several.

  • One example replaces a paragraph of rules: it shows tone, format and edge handling at once.
  • Examples pin down fuzzy labels ("urgent") and the output format.
  • The model learns the pattern, not the literal examples: show 3 "messy → clean" addresses and it cleans a fourth.
  • Add an example where the data is missing and the right answer is null. If every example is "full", the model assumes it must always produce a value and fabricates.

Which examples: correct, diverse, with edge cases. How many: usually 2-5, stop when accuracy plateaus. The same format in all of them. Place them before the real input.

Step 3. Structured output with tool_use

Free text is unreliable for automation: the model may add "Here's the data:" or a markdown fence, and the parser breaks.

In the course the standard move is a tool with a schema. You describe a tool with an input_schema, and the model's answer becomes that tool's input.

{
  "name": "extract_claim",
  "input_schema": {
    "type": "object",
    "properties": {
      "claim_id": {"type": "string"},
      "amount": {"type": "number"},
      "phone": {"type": ["string", "null"]},
      "type": {"enum": ["auto", "home", "health", "other"]},
      "detail": {"type": "string"}
    },
    "required": ["claim_id", "amount"]
  }
}
  • Required and nullable fields. A field the document might not have should be optional or nullable. A required field with no data gets filled with an invention. That is the root-cause fix, not a "don't guess" plea.
  • Enum with other. Without an escape hatch an unusual input lands in the closest wrong option. other plus detail keeps the answer honest.
  • tool_choice. On auto the model may reply in text. Use any or a named tool so the call is guaranteed.
  • A malformed schema is rejected up front (400), before the model even runs.

The API itself also has a structured outputs mode and strict: true (lecture 3). The principle is the same.

What it does not fix. The shape is guaranteed, the truth is not: sums may not add up, a value may be invented or sit in the wrong field.

Step 4. Validation and retry with feedback

таблицю можна гортати вбік →
Error Example Who catches it
Syntax Broken JSON The schema and tool_use
Semantic Valid shape, wrong content Your validation

What to check: do the totals add up, are the dates real and in range, does every value actually appear in the document.

If a check fails, send the model the document, the bad extraction and the specific error: "line items sum to 4,800, but total says 5,000". "It's wrong" barely helps.

Cap it at 2-3 retries. After that, a human or a low-confidence flag. Without a cap the loop can run forever.

Step 5. The Message Batches API

What Value
Price 50% off input and output
Time Up to 24 hours (often faster)
Streaming None
Size Up to 100,000 requests or 256 MB
Result retention About 29 days: save them right away

Decision rule: is it fine for the user to get this within 24 hours? Yes: batch (bulk extraction, evals, moderation). No: the normal API (chat, a live UI).

Results come back out of order, so give each request a custom_id from your own record (the claim number), not a throwaway.

The flow: submit, poll the status, retrieve the JSONL, save it. Each result still goes through the same validation from step 4.

Step 6. Multi-pass review

One pass misses things: attention spreads thin, and an author reviewing its own work is biased to approve.

  • An independent reviewer: a separate instance with a clean context.
  • A per-file pass catches local bugs, a cross-file pass catches mismatched interfaces. You need both.
  • Confidence on every finding: high gets applied, low goes to a human.
  • Aggregate: de-duplicate, keep the highest severity, group by confidence.

What to remember for the exam

  • Criteria are specific and testable, with severity levels. A noisy category is tightened or switched off.
  • Few-shot: 2-5 diverse examples in one format before the input, including a null case.
  • Structured output: tool_use with a schema and tool_choice any or tool.
  • Nullable fields against invention, enum with other.
  • The schema guarantees shape, validation checks meaning. Retry with the specific error, cap at 2-3.
  • Batch: 50% cheaper, up to 24 hours, custom_id.

Check yourself

  1. What do you do with a category that gives many false positives?
  2. Why include a null example in few-shot?
  3. How do you stop the model inventing a phone number?
  4. Who catches a total that does not add up?
  5. When is the Batch API the wrong choice?
Answers
  1. Tighten its rule or switch the category off.
  2. So the model does not invent values when the data is missing.
  3. Make the field nullable or optional.
  4. Your validation, not the schema.
  5. When a user is waiting for the answer now.
