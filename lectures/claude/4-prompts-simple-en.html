Lecture 4: how to write prompts and check them

Simplified version. The full lecture exists in Ukrainian only. The exam-course view of prompts and structured output is in lecture 12.

The main idea

First decide how you will check that a prompt is good. Then write it. Otherwise you will never know whether you improved it.

Why it is designed this way

The model responds well to clear instructions and examples, so prompting techniques are about removing ambiguity. Evaluation lets you judge changes by numbers, not by feel.

Step 1. Before the prompt

The documentation asks for three things:

  1. Clearly defined success criteria.
  2. A way to test them on examples.
  3. A first draft of the prompt.

Good criteria are specific, measurable, achievable, relevant. Example: "F1 of at least 0.85 on 10,000 tweets". A bad one: "should work well".

Not every problem is fixed by a prompt. Sometimes changing the model is simpler.

Step 2. Core principles

  • Be clear. The model is like "a brilliant new employee with no context". Show the prompt to a colleague: if they do not get it, neither will the model.
  • Give the reason. Not "never write an ellipsis", but "a text-to-speech engine will read this and cannot pronounce ellipses". The model generalises from the reason.
  • Give examples. The documentation suggests 3-5, relevant and diverse, in <example> tags. The exam course says "usually 2-5, while accuracy keeps rising" and suggests an example where the data is missing and the answer is null, so the model does not invent (lecture 12).
  • Separate parts with tags: <instructions>, <context>, <input>.

Step 3. Long documents

If the prompt holds more than about 20 thousand tokens of documents:

  • long data goes at the top;
  • the question goes at the end (up to 30% better results).

Several documents: <documents>, each one a <document index="n"> with <source> and <document_content>.

Step 4. Output format

Say what to do, not what not to do.

Instead of Write
"Don't use markdown" "Your answer is made of flowing prose paragraphs"

The style of the prompt itself also shapes the answer: remove markdown from the prompt and there will be less of it in the answer.

Step 5. Prefill no longer works

Prefill means writing the start of the assistant's answer yourself so the model continues it. From Claude 4.6 onwards it returns 400.

What prefill was for Replace it with
Forcing a format (JSON) structured outputs, or a tool with a schema and tool_choice any or tool (lecture 12); for classification a tool with an enum
Removing a "Here is..." intro A direct instruction "Answer without an introduction"
Continuing a cut-off answer Move it into the user turn: "Your answer stopped at …, continue"

Step 6. Prompts for tools

  • New models follow instructions literally. "Can you suggest changes" gives only suggestions. For action write: "Change this function".
  • Aggressive "MUST use this tool" can over-trigger on Opus 4.5 and 4.6. Write more calmly: "Use this tool when...".
  • For parallel calls there is a ready block <use_parallel_tool_calls>. Add: if calls depend on each other, do not parallelise, and never guess parameters.

Step 7. Thinking (very briefly)

  • New models have adaptive thinking: the model decides whether and how much to think.
  • The old budget_tokens returns 400 on Claude 4.7 and newer. Use effort or max_tokens instead.

Step 8. Complex tasks

  • Subagents: the model delegates on its own. Sometimes too much; then add a rule for when to use them.
  • Prompt chaining (several calls) is needed when you must check intermediate results. A typical scheme: draft, check against criteria, refine.

Step 9. How to evaluate

Evaluation principles:

  1. Task-specific: a realistic distribution, with edge cases.
  2. Automate where you can.
  3. Volume beats quality: many automatically graded questions beat a few hand-graded ones.

Two kinds of grading:

таблицю можна гортати вбік →
Kind For what Examples
By code Categories, deterministic answers Exact match, ROUGE-L
By a model Nuance (tone, empathy) A 1-5 scale, yes/no

Rule: grade with a different model from the one that generated the answer.

Glossary

Term What it is
Success criteria what counts as a good answer; set before the prompt
Few-shot / examples several input and output samples in the prompt
XML tags markup that separates instructions from data
Prefill a pre-written start of the answer; does not work on new models
Prompt chaining a complex task split into several calls
Adaptive thinking the model chooses how deeply to think

What to remember for the exam

  1. Success criteria and a way to test them come first.
  2. 3-5 diverse examples in tags.
  3. Long documents at the top, the question at the end.
  4. Say what to do, not what not to do.
  5. Prefill on 4.6+ returns 400. budget_tokens on 4.7+ returns 400.
  6. An aggressive "MUST" can over-trigger a tool.
  7. Grade with a different model.

Check yourself

  1. What do you need before writing a prompt?
  2. How many examples, and what should they be like?
  3. Where do long documents and the question go?
  4. What happens to prefill on Claude 4.6+?
  5. What replaces prefill for JSON?
  6. Which model should grade?
Answers
  1. Success criteria, a way to test them, a first draft.
  2. 3-5, relevant, diverse, in <example>.
  3. Documents at the top, the question at the end.
  4. A 400 error.
  5. Structured outputs, or a tool with an enum for labels.
  6. A different one from the generator.
