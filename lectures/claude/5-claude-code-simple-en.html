Lecture 5: Claude Code

Simplified version. The full lecture exists in Ukrainian only. The exam-course view of Claude Code configuration is in lecture 11.

The main idea

Some things only advise the model; others enforce. The exam keeps asking about exactly this difference.

Only advises Enforces
CLAUDE.md, rules, skills, auto memory Permission rules (deny), hooks with exit 2, managed settings, sandbox

For a Spring developer: CLAUDE.md is like a README or Javadoc (people read it, nobody is forced to follow it), while deny and hooks are like Spring Security or a filter (they cannot be broken).

So the answer to "how do I guarantee X" is never "write it in CLAUDE.md".

Why it is designed this way

Claude Code runs on your machine and can break things, so there are permissions, hooks and a sandbox: you decide yourself what it may do.

Step 1. CLAUDE.md

This is the instruction file Claude reads at the start of every session. It is context, not an enforced rule.

Rules for a good file:

  • up to 200 lines;
  • concrete instructions ("Use 2-space indentation", not "format nicely");
  • only facts needed in every session. Step-by-step procedures belong in a skill, and rules for part of the code in a rule with paths.

Where it lives: ~/.claude/CLAUDE.md (for you), ./CLAUDE.md (for the project), ./CLAUDE.local.md (personal, in .gitignore).

All found files are added together; they do not override each other. On a conflict the more specific level wins: you say 2 spaces, the project says 4, it is 4. Files in subdirectories load when Claude touches files there. More in lecture 11.

Step 2. AGENTS.md

A shared instruction format for different agents. The reading rule:

In the repository Claude reads
only AGENTS.md AGENTS.md
AGENTS.md and CLAUDE.md only CLAUDE.md
a CLAUDE.md that imports @AGENTS.md both

That is why in ai-ops CLAUDE.md simply contains @AGENTS.md.

Step 3. Rules and auto memory

  • Rules (.claude/rules/): separate files per topic. With paths they load only when Claude works on files matching the pattern.
  • Auto memory: notes Claude writes itself. The MEMORY.md index loads at startup (the first 200 lines or 25 KB), topic files only on demand. The memory is local to the machine.

Step 4. Permissions

Three kinds of rules: deny, ask, allow. They are checked in exactly that order, and the first match decides.

Hence the key point: allow cannot carve an exception out of deny. If deny has Bash(aws *), then Bash(aws s3 ls) in allow will not help.

The rules are enforced by Claude Code itself, not by the model. A prompt or CLAUDE.md cannot change them.

Modes

Mode What it does
default Asks on first use of a tool
acceptEdits Accepts file edits on its own
plan Only reads and plans; Write and Edit are blocked until you approve. Turn it on with Shift+Tab twice, /plan or --permission-mode plan
auto A separate classifier model checks actions
dontAsk Denies everything that would prompt (for CI)
bypassPermissions No prompts; only for isolated environments

In bypassPermissions deny rules apply and allow rules do not.

Bash rules

  • Put the star after the subcommand: Bash(git log *) allows only git log, while Bash(git *) allows every git command.
  • A compound command (a && b) runs without a prompt only if every part is allowed.
  • A Bash rule is not a security boundary. Bash(curl *) will not stop sh -c 'curl ...' or /usr/bin/curl. For that you need the sandbox or a hook.

File rules

  • Read(./.env) in deny blocks reading, and also Edit and Write on that path.
  • Grep(...), Glob(...) and Write(...) rules with a path do nothing: write Read(...) or Edit(...).
  • A .claudeignore file does nothing: move it into a Read deny.

Step 5. Hooks

A hook is a script (or a prompt) that Claude Code runs on an event. The most important ones:

таблицю можна гортати вбік →
Event When What it can do
PreToolUse Before a tool Block it
PostToolUse After a tool Cannot undo it (already done). In the course: shape the result for Claude, logging
UserPromptSubmit Before the prompt is processed Block it or add context
Stop When Claude finished answering Keep it from stopping
SessionStart At session start (with compact, after compaction) Add context

For a Spring developer PreToolUse is like HandlerInterceptor.preHandle: it can stop the call from going further.

Exit codes

Code What happens
0 Success
2 Blocks the action (stderr goes to the model as the reason)
any other, including 1 Does not block; the action continues

2 blocks, 1 does not.

What else to know

  • A decision can be returned as JSON in hookSpecificOutput (permissionDecision: allow, deny, ask, defer). A top-level field is silently ignored.
  • deny in a hook applies even in bypassPermissions.
  • Several hooks on one event run in parallel; the strictest decision wins (deny > defer > ask > allow).
  • A Stop hook fires after every reply. After 8 blocks in a row Claude Code overrides it. The script must check the stop_hook_active field.
  • If a hook crashed or timed out, the action continues (to block you need onFailure: "block").
  • JSON from a hook does not work if the shell profile prints something first (the output must start with {).

Step 6. Skills

A skill is a folder with SKILL.md: instructions for a specific task.

  • The description is always in context; the full body only when the skill is invoked.
  • Move a very long procedure out of CLAUDE.md into a skill: it costs no context until needed.
  • disable-model-invocation: true: only you can run the skill (for deployment).
  • context: fork: the skill runs in a separate subagent.
  • allowed-tools pre-approves the listed tools but does not block the others.
  • Slash commands (.claude/commands/*.md, $ARGUMENTS) are now merged into skills. On a name clash the skill wins (lecture 11).

Step 7. Subagents

A subagent is a helper with its own context window.

The main benefit: context isolation. It runs a bulky search in its own window and returns only a summary.

You can limit its tools (tools) and permissions. Built-in ones: Explore (fast read-only search), Plan, general-purpose.

Default limits: up to 3 levels of nesting, up to 20 at once.

Step 8. Settings

Priority from highest: managed, command line, local, shared project, user. Lists (for example allow) are merged, not overridden. It is like the order of property sources in Spring.

Managed settings are the organisation's settings that a user cannot bypass.

Step 9. Sandbox (briefly)

An operating-system boundary around shell commands (Bash, PowerShell, Monitor). Off by default. File tools, MCP and hooks are outside it.

Details in lecture 8.

Glossary

Term What it is

What to remember for the exam

  1. CLAUDE.md advises. Deny, hooks and managed settings enforce.
  2. Rule order: deny, ask, allow. Allow does not carve an exception out of deny.
  3. Exit 2 blocks, exit 1 does not.
  4. deny in a hook and in rules applies even in bypassPermissions.
  5. A Bash rule is not a security boundary.
  6. MEMORY.md at startup: 200 lines or 25 KB.
  7. AGENTS.md is read only when there is no CLAUDE.md (or through an import).
  8. A subagent gives context isolation.
  9. Stop hook: 8 continuations in a row, check stop_hook_active.

Check yourself

  1. How do you guarantee that Claude will not change .env?
  2. What does a hook with exit code 1 do?
  3. Which wins: deny Bash(aws *) or allow Bash(aws s3 ls)?
  4. How much of MEMORY.md loads at startup?
  5. What is the main benefit of a subagent?
  6. What part of a skill is always in context?
Answers
  1. deny for Read and Edit on .env, or a PreToolUse hook with exit 2.
  2. It does not block: the action continues.
  3. deny.
  4. The first 200 lines or 25 KB.
  5. Context isolation.
  6. Only the description.
