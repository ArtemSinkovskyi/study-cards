Лекція 8: CI/CD, змінні, секрети, OIDC

Середній рівень: усі правила й числа з повної лекції, але простими словами й без розповіді про наш проєкт, команд та проблем. Повна: ../8-ci-variables-secrets-oidc.md. Числа в повній лекції дані з пам'яті, їх варто звірити з документацією AWS. Домени Security і Deployment.

Головна ідея

Довгих ключів у CI не має бути. GitHub підписує короткоживучий токен «я job такого-то репозиторію й гілки», AWS обмінює його на тимчасові ключі ролі. Захист не в тому, що ключ добре сховано, а в тому, що його нема.

Крок 1. Словник

Термін Суть
GitHub Actions CI/CD в GitHub: workflow (YAML у .github/workflows/) запускається подіями (push, PR, вручну)
Variable іменоване значення репозиторію, не секрет: ${{ vars.NAME }}, видно в інтерфейсі й логах
Secret зберігається зашифрованим: ${{ secrets.NAME }}, не показується, в логах маскується ***
OIDC federation GitHub підписує токен, AWS обмінює на тимчасові ключі ролі
Secrets Manager / Parameter Store секрети й конфігурація самого застосунку (не CI)
workflow_dispatch запуск вручну кнопкою
id-token: write дозвіл job'у запросити OIDC-токен
sub claim токена: хто просить доступ (репозиторій і гілка)
aud claim токена: для кого він (sts.amazonaws.com)
trust policy політика ролі: хто може її взяти
permission policy політика ролі: що вона може робити
dynamic reference {{resolve:...}} у шаблоні CloudFormation
SecureString тип параметра Parameter Store, зашифрований KMS

Крок 2. Що секрет, а що ні

Секрет це те, що дає доступ тому, хто його побачив.

Значення Секрет? Чому
ARN ролі ні сам нічого не дає: роль можна взяти лише з токеном, що проходить trust policy
Назва бакета ні доступ керується IAM
ID акаунта, регіон ні ідентифікатори, не ключі
OIDC-токен GitHub так, але його не зберігають видається job'у на ходу, живе хвилини
Тимчасові ключі ролі так, але не зберігають видаються STS на час job'у
AWS access key у CI його нема головна перевага OIDC
Токен HCP Terraform так дає доступ до HCP

Правило: уявіть значення в публічному репозиторії. Якщо наслідок нульовий (як для ARN ролі), це змінна.

Крок 3. Variable проти Secret

Variable Secret
Читання ${{ vars.NAME }} ${{ secrets.NAME }}
Видно в інтерфейсі так, можна редагувати ні, лише перезаписати
У логах видно маскується ***
Для чого конфігурація токени, паролі, ключі
З fork-PR залежить від налаштувань ні (захист від крадіжки)
  • Рівні від вузького до широкого: environment → repository → organization. Діє найвужчий.
  • Захист environment (обов'язкові рецензенти) на безкоштовному плані приватного репозиторію недоступний, тому гейтом може бути ручний запуск workflow_dispatch.
  • Маскування не гарантоване: працює лише на точний збіг рядка. Закодований у base64 чи розбитий на частини секрет з'явиться в логах відкритим. Секрети не друкують і не передають у echo.

Задати значення можна через інтерфейс (Settings → Secrets and variables → Actions) або через gh variable set і gh secret set (значення секрету вводиться в запиті, в історії команд не лишається).

Крок 4. Як workflow використовує OIDC

permissions:
  contents: read
  id-token: write

- uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: ${{ vars.AWS_DEPLOY_ROLE_ARN }}
    aws-region: ${{ env.AWS_REGION }}
  • id-token: write єдина зміна прав, потрібна для OIDC. Без нього токен не видається.
  • configure-aws-credentials бере токен, викликає AssumeRoleWithWebIdentity і кладе тимчасові ключі в змінні середовища job'у.
  • Значення vars.* підставляється до запуску команди, тож у логах видно повну команду з назвою бакета: для змінних це нормально.

Крок 5. Три захисти OIDC

  1. Умова на sub у trust policy. Без неї будь-який GitHub-репозиторій, що знає ARN, міг би взяти роль. Форми sub:

    • гілка: repo:ORG/REPO:ref:refs/heads/main
    • тег: repo:ORG/REPO:ref:refs/tags/v1
    • pull request: repo:ORG/REPO:pull_request
    • environment: repo:ORG/REPO:environment:prod

    Якщо у workflow з'явиться environment: prod, sub зміниться, і роль перестане працювати, доки не оновити trust policy.

  2. Умова на aud (sts.amazonaws.com). Токен для іншого отримувача не підходить.

  3. Мінімальні права ролі і деплой лише вручну з main.

Імутабельний sub. Якщо в репозиторії ввімкнено use_immutable_subject, sub містить числові ID (repo:ORG@id/REPO@id:ref:refs/heads/main) і переживає перейменування репозиторію. Якщо в trust policy стоїть звичайна форма, StringEquals не збігається і STS відмовляє: Not authorized to perform sts:AssumeRoleWithWebIdentity. Діагностика за порядком: audience у провайдері (ClientIDList), потім реальний sub токена. Умову на sub не послаблюють.

Ім'я ролі. Якщо політика дозволяє змінювати IAM-ролі за шаблоном імен (наприклад homeeho-lambdas-*), CI-роль не називають за цим шаблоном: інакше вона змогла б змінити сама себе й отримати будь-які права.

Крок 6. Перший запуск за кроками

  1. Застосувати платформу (бакет артефактів, прапорець EventBridge на бакеті).
  2. Задати змінні репозиторію.
  3. Запушити репозиторій: workflow CI запуститься сам.
  4. Запустити Deploy з dry_run: створюється change set, але не виконується.
  5. Повторити без dry_run: перший справжній деплой.
  6. Перевірити: стек у CREATE_COMPLETE, alias live, обробка тестового файла.

Порядок важливий: Deploy до застосування платформи не знайде бакета артефактів, а правило EventBridge не спрацює без прапорця на бакеті.

Крок 7. Секрети самого застосунку

Secrets Manager Parameter Store (SSM)
Призначення секрети, що змінюються конфігурація й прості секрети
Ціна 0,40 USD за секрет на місяць плюс запити стандартні параметри безкоштовні, advanced платні
Автоматична ротація так (через Lambda) ні
Шифрування завжди KMS SecureString через KMS, звичайні рядки без шифрування
Розмір до 64 КБ стандартний до 4 КБ, advanced до 8 КБ
Міжрегіональна реплікація так ні

Правило вибору: автоматична ротація (пароль RDS) означає Secrets Manager; просто зберігати конфіг чи дешевий секрет означає Parameter Store. Ієрархічні імена: /app/env/key.

Як функція отримує значення:

  1. Змінна середовища Lambda. Значення видно в консолі й API (шифрування KMS «at rest» не ховає його від користувача з lambda:GetFunctionConfiguration). Ліміт 4 КБ. Для справжніх секретів недобре.
  2. Читання під час роботи через SDK (GetSecretValue, GetParameter з WithDecryption) і кешування в пам'яті. Потрібні права на секрет і kms:Decrypt. Для кешу: Powertools Parameters або Lambda-розширення Parameters and Secrets.
  3. Dynamic references у CloudFormation: {{resolve:ssm:...}} чи {{resolve:secretsmanager:id:SecretString:key}}. Значення підставляється під час деплою, тому потрапляє в конфігурацію функції (як у варіанті 1).

Пастка: секрет у змінній Lambda «зашифровано, тому безпечно». Шифрування захищає значення на диску, а не від тих, хто має читати конфігурацію.

Крок 8. Вартість стеку

Ресурс Ціна

SQS 1 млн запитів на місяць безкоштовно
CloudWatch alarm перші 10 стандартних безкоштовні

Budgets рахують гроші з затримкою до доби, тому від різкого сплеску викликів (цикл, нескінченні повтори) не захищають. Захищають технічні запобіжники: розділення префіксів проти рекурсії, MaximumRetryAttempts, alarm на Errors, reserved concurrency.

Крок 9. Типові помилки деплою

  • dry_run створює лише change set і не перевіряє права на реальне створення ресурсів. AccessDenied (наприклад на lambda:ListVersionsByFunction) може вилізти на першому справжньому деплої: CloudFormation відкотить усе (ROLLBACK_COMPLETE). Причину знаходять через describe-stack-events з фільтром FAILED: у ResourceStatusReason повна дія й ARN. Додають дію в permission policy ролі.
  • Стек у ROLLBACK_COMPLETE оновити не можна, його лише видаляють. Це добре, що CI-роль не має cloudformation:DeleteStack.
  • Тип OIDC-провайдера token.actions.githubusercontent.com в акаунті створюють один раз.

Що запам'ятати на іспит

  1. Тимчасові облікові дані замість ключів: AssumeRoleWithWebIdentity для OIDC (GitHub, Cognito, Google), AssumeRole для ролей, GetSessionToken з MFA.
  2. Trust policy: хто може взяти роль. Permission policy: що роль може робити.
  3. Без умови на sub будь-який репозиторій GitHub міг би взяти роль.
  4. ARN ролі не секрет.
  5. Секрети застосунку: Secrets Manager (ротація), Parameter Store SecureString. Не в змінних середовища й не в коді.
  6. У CodeBuild секрети беруть із env у buildspec.yml: parameter-store і secrets-manager.
  7. Dynamic references є в CloudFormation і SAM.
  8. iam:PassRole лише на потрібні ролі. Найменші привілеї.
  9. Масковання GitHub не гарантоване.

Відповіді
  1. ARN сам нічого не дає: роль можна взяти лише з токеном, що проходить trust policy.
  2. Будь-який репозиторій GitHub, що знає ARN, зможе взяти роль.
  3. Дозволяє job'у запросити OIDC-токен. Без нього токен не видається.
  4. sub набуде форми repo:ORG/REPO:environment:prod, і trust policy треба оновити.
  5. Variable видно, вона для конфігурації. Secret не показується, маскується в логах. У fork-PR не передається, щоб його не вкрали.
  6. Автоматична ротація: Secrets Manager. Конфіг чи дешевий секрет: Parameter Store.
  7. KMS-шифрування захищає на диску, але користувач із lambda:GetFunctionConfiguration бачить значення.
  8. AssumeRoleWithWebIdentity.
  9. Інакше роль могла б змінити сама себе й отримати будь-які права.
  10. STS відмовив. Спершу audience у провайдері (ClientIDList), потім реальний sub токена проти trust policy.
  11. dry_run створює лише change set і не перевіряє права на створення ресурсів.
