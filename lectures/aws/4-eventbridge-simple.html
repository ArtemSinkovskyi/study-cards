Лекція 4: EventBridge

Середній рівень: усі правила з повної лекції, але простими словами й без розповіді про наш проєкт. Повна: ../4-eventbridge.md. Числа й ціни в повній лекції дані з пам'яті, позначка (не звірено) означає те саме тут.

Головна ідея

EventBridge відповідає на питання «хто і як дізнається, що щось сталося». Подія потрапляє на шину, правило перевіряє її за шаблоном і надсилає цілям.

Схема: джерело (сервіс AWS, ваш код, SaaS) → event bus → rule (патерн) → target (Lambda, SQS, SNS, Step Functions та інші).

Навіщо це так задумано

Щоб сервіси не знали один про одного напряму: джерело лише каже «щось сталося», а хто реагує, вирішують правила. Тоді можна додати нового споживача, не змінюючи джерела.

Крок 1. Словник

Термін Суть
Event JSON «щось сталося» (факт, не команда)
Event bus шина: default (в кожному акаунті й регіоні, на неї пишуть сервіси AWS, зокрема S3), custom (ваші застосунки), partner (SaaS)
Rule «якщо подія відповідає патерну (або настав час за розкладом), надішли цілям»
Event pattern JSON-шаблон відбору
Target ціль: Lambda, SQS, SNS, Step Functions, Kinesis, інша шина, API destination. До одного правила можна додати кілька цілей
Scheduler окремий сервіс розкладів (разово, cron, rate)
Pipes з'єднання «джерело → фільтр → збагачення → ціль» для SQS, Kinesis, DynamoDB Streams

Крок 2. Навіщо шина, а не прямий виклик

Підхід Плюси Мінуси
Джерело викликає ціль напряму (S3 notification → Lambda) просто підписки прописані в джерелі; для S3 перетинні префікси на одну подію заборонені; конфігурація бакета одна, друга підписка перезапише першу
Через шину (S3 → EventBridge → Lambda) багато незалежних правил, фільтр за будь-яким полем, кілька цілей, архів і повтор трохи більша затримка, ще один сервіс

Для S3 у бакеті треба лише ввімкнути надсилання подій в EventBridge, правило створюється окремо. Правило нічого не отримає, поки це не ввімкнено.

Крок 3. Структура події

Поля: version, id, detail-type (людська назва типу), source (хто відправив: aws.s3, aws.ec2 або ваше), account, time, region, resources, detail (корисне навантаження, форму задає джерело).

Сумарний розмір запису в PutEvents має бути менше 1 МБ (у старих матеріалах трапляється 256 КБ). В одному запиті до 10 записів.

Крок 4. Event pattern

Правила збігу:

  • усередині одного поля масив означає АБО: ["a", "b"];
  • між різними полями І: усі вказані поля мають збігтися;
  • поле, якого нема в патерні, ігнорується;
  • значення в патерні завжди в масиві.

Приклад: source: [aws.s3], detail-type: [Object Created], detail.bucket.name: [моє-ім'я], detail.object.key: [{prefix: images/}]. Читається: подія з S3 І Object Created І цей бакет І ключ починається з images/.

Оператор Значення
prefix починається з
suffix закінчується на
anything-but усе, крім
numeric числове порівняння, наприклад [">", 1000]
exists поле є
equals-ignore-case без урахування регістру

Захист від рекурсії. Якщо Lambda пише в thumbs/, а правило слухає весь бакет, кожна мініатюра запустить нову Lambda до нескінченності. Тому префікс у патерні важливий.

Перевірити патерн без деплою: aws events test-event-pattern.

Крок 5. Цілі, права, налаштування

Хто дозволяє доставку:

Ціль Хто дозволяє
Lambda, SQS, SNS resource-based policy на цілі (для events.amazonaws.com з SourceArn правила)
Step Functions, Kinesis, ECS, інша шина IAM-роль, яку правило приймає (assume)

Налаштування цілі:

Параметр Що дає
Input transformer виймає поля з події й складає свій JSON
Input path / constant передати частину події або фіксований JSON
Retry policy скільки часу й спроб повторювати доставку
DLQ (SQS) куди скласти подію, яку не вдалося доставити

Крок 6. Надійність: дві різні черги помилок

Класична пастка: DLQ бувають на різних рівнях.

Рівень Що ловить Повтори
Ціль правила EventBridge EventBridge не зміг передати подію (нема прав, ціль не існує, throttling) за замовчуванням до 24 год і до 185 спроб (налаштовується)
Lambda (async) подію прийнято, але код кидає помилку 2 повтори, потім DLQ чи on-failure destination

Події доставляються принаймні один раз (at-least-once): можливі дублікати, порядок не гарантований, тому handler ідемпотентний.

Прогалина: без DLQ на цілі правила подія, яку не вдалося доставити, зникає через 24 год без сліду. «Подія пропала через 24 год, а в DLQ функції порожньо» означає шукати доставку: права, resource-based policy, DLQ цілі.

Крок 7. Інші можливості

Можливість Суть Коли
Cross-account / cross-region ціль = шина в іншому акаунті чи регіоні (потрібна політика на шині-приймачі) збирати події з багатьох акаунтів
Archive & Replay архів подій шини, повторна відправка за період відтворити збій, протестувати нову ціль
Schema registry виявляє форму подій, генерує типи для коду типізація в IDE
API destination відправка на HTTP-ендпойнт поза AWS з авторизацією й rate limit SaaS-вебхуки
Scheduler rate(5 minutes), cron(...), разовий at(...), часові пояси замість cron-сервера
Pipes точка-точка з SQS/Kinesis/DynamoDB Streams, фільтр, збагачення потоки без коду-клею
Custom events PutEvents із вашого коду на власну шину доменні події

Cron в EventBridge має 6 полів: хвилини, години, день місяця, місяць, день тижня, рік. В одному з полів «день» обов'язково ?. Приклад щодня о 03:00 UTC: cron(0 3 * * ? *).

Scheduler проти розкладу на правилі: Scheduler новіший, підтримує часові пояси, разові виклики, повтори й DLQ; для нових розкладів його рекомендують.

Крок 8. EventBridge проти SNS проти SQS

EventBridge SNS SQS
Модель шина з правилами pub/sub черга (споживач бере сам)
Фільтр потужний за будь-яким полем за атрибутами повідомлення нема
Споживачі багато цілей багато підписників зазвичай один
Буфер і повтор ні (є Replay) ні так, зберігання до 14 днів
Типово події сервісів AWS, інтеграції розсилка, fan-out згладжування піків, пачки

Підказки:

  • реагувати на подію сервісу AWS і фільтрувати за полем: EventBridge;
  • одне повідомлення багатьом одразу: SNS (часто SNS → кілька SQS);
  • згладити піки, обробка у власному темпі: SQS;
  • запуск за розкладом без сервера: EventBridge Scheduler;
  • повторити події минулого тижня: Archive & Replay.

Крок 9. Ціна (не звірено)

Що Орієнтир
Події сервісів AWS на default bus (S3) безкоштовно
Власні події (PutEvents) приблизно 1 USD за мільйон
Archive & Replay плата за оброблені ГБ і зберігання
Scheduler приблизно 1 USD за мільйон викликів понад безкоштовні
Pipes приблизно 0,40 USD за мільйон запитів

Що запам'ятати на іспит

  1. Події → шина → правила за патерном → цілі. Для S3 безкоштовно, лише ввімкнути прапорець на бакеті.
  2. Патерн: масив = АБО, різні поля = І.
  3. Lambda, SQS, SNS потребують resource-based policy на цілі. Step Functions та інші потребують IAM-роль.
  4. At-least-once: handler ідемпотентний.
  5. Два рівні DLQ: цілі правила (доставка, 24 год і 185 спроб) і функції (код, 2 повтори).
  6. Правило не слухає префікс, куди сама пише (інакше рекурсія).
  7. Розклад: Scheduler, cron має 6 полів і ?.

Відповіді
  1. Багато незалежних правил, фільтр за будь-яким полем, кілька цілей, архів і replay. Нема обмеження про перетинні префікси.
  2. Масив це АБО всередині поля, кілька полів це І.
  3. {"source":["aws.s3"],"detail-type":["Object Created"],"detail":{"object":{"key":[{"suffix":".png"}]}}}.
  4. Кожна мініатюра запускала б нову Lambda: нескінченна рекурсія.
  5. Lambda: resource-based policy на функції (events.amazonaws.com). Step Functions: IAM-роль, яку приймає правило.
  6. Ціль правила ловить помилки доставки (24 год, 185 спроб). Lambda DLQ ловить помилки коду після прийняття (2 повтори).
  7. Подія може прийти двічі. Повторна обробка не має шкодити.
  8. EventBridge: події AWS з фільтром. SNS: розсилка багатьом. SQS: буфер, піки, власний темп.
  9. EventBridge Scheduler: cron(0 3 * * ? *).
  10. У доставці EventBridge → Lambda: права, resource-based policy, DLQ цілі правила (її могли не налаштувати).
