Лекція 36: CloudWatch Agent, експорт і підписки логів, Synthetics

Середній рівень: усі правила з повної лекції, але простими словами. Повна: ../36-cloudwatch-agent-synthetics.md. Теоретична лекція, в AWS не виконувалась. Що не підтверджено документацією, позначено (не звірено).

Головна ідея

Це три доповнення до CloudWatch: агент збирає з серверів те, чого AWS сам не бачить; підписки вивозять логи на обробку; canary перевіряє сайт зовні, як це зробив би клієнт.

Навіщо це так задумано

AWS бачить сервер ззовні: CPU, диск, мережу. Що робиться всередині (пам'ять, процеси), знає лише агент на самому сервері. А «сайт працює» не те саме, що «клієнт може на ньому купити»: це перевіряє canary.

Крок 1. Звідки беруться логи

Джерело Що шле
SDK, агенти CloudWatch ваші застосунки й сервери
Elastic Beanstalk, ECS, Lambda логи застосунків, контейнерів, функцій
VPC Flow Logs мережевий трафік VPC
API Gateway логи API
Route 53 DNS-запити
CloudTrail за фільтром події API-викликів

Log group це група (зазвичай один застосунок), log stream це потік у ній (сервер, файл, контейнер). Строк зберігання задають на групі: від 1 дня до 10 років або «ніколи». Логи шифруються за замовчуванням, можна свій ключ KMS.

Крок 2. Агент: старий і новий

таблицю можна гортати вбік →
Logs Agent (старий) Unified Agent
Що шле лише логи логи і метрики
RAM, процеси, swap ні так
Налаштування локально централізовано в SSM Parameter Store

Пастка іспиту: без Unified Agent у CloudWatch нема пам'яті й swap із EC2, лише CPU, диск і мережа зовні.

Агент збирає: CPU (active, idle, system, user, steal), диск і Disk IO, RAM (free, used, cached), мережу (TCP і UDP з'єднання), процеси, swap.

Крок 3. Експорт чи підписка

Хочеш вивезти логи з CloudWatch? Є два шляхи.

таблицю можна гортати вбік →
Експорт у S3 Підписка (subscription filter)
Як CreateExportTask фільтр на log group
Швидкість пакетом, не реальний час майже одразу
Куди S3 Kinesis Data Streams, Firehose, Lambda
Коли архів за період обробляти на льоту

Правило: «реальний час» означає підписку, а не експорт.

Про підписки:

  1. Фільтр вирішує, які події летять далі.
  2. Підписку можна надіслати в інший акаунт (cross-account).
  3. На одну log group до п'яти фільтрів.
  4. Доставка «щонайменше раз», дублікати можливі.

Колега писав, що логи стають доступні для експорту «до 12 годин». Сучасна документація цього не підтверджує (не звірено); пам'ятай лише, що експорт не швидкий.

Крок 4. Canary: перевірка зовні

Canary це скрипт, що за розкладом (наприклад, кожні 5 хвилин) робить те, що робить клієнт: відкриває сторінку, натискає посилання, заповнює форму. Йому допомагає headless Chrome (браузер без вікна), працює він у Lambda.

Що зберігає: час відповіді, скриншоти, HAR-файли (список усіх HTTP-запитів сторінки). Якщо перевірка провалилась, спрацьовує CloudWatch Alarm.

Готові шаблони (blueprints), щоб не писати з нуля:

Blueprint Що робить
Heartbeat monitor відкриває URL, робить скриншот і HAR
API canary перевіряє читання й запис REST API
Broken link checker шукає мертві посилання
Visual monitoring порівнює скриншот з еталоном
Canary recorder записує ваші дії в Chrome і пише скрипт
GUI workflow builder перевіряє, що кнопки й форми працюють

Словник

Термін Що це
Unified Agent агент для логів і метрик серверів
subscription filter фільтр для живої передачі логів
CreateExportTask пакетний експорт логів у S3
canary скрипт, що перевіряє сайт зовні
blueprint готовий шаблон canary
HAR file запис усіх запитів сторінки
headless Chrome браузер без вікна

Що запам'ятати на іспит

  • RAM і swap з EC2 дає лише Unified Agent.
  • Unified Agent шле логи й метрики, налаштовується через SSM Parameter Store; Logs Agent старий, лише логи.
  • Експорт CreateExportTask не реального часу; для живих логів підписка.
  • Підписка шле у Kinesis Data Streams, Firehose, Lambda, може бути cross-account.
  • Canary працює на Lambda з headless Chrome, зберігає скриншоти й HAR.
  • Broken link checker шукає мертві посилання, Visual monitoring порівнює скриншоти.
