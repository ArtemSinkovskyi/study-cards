Лекція 17: X-Ray і спостережуваність

Середній рівень: усі правила з повної лекції, але простими словами й без розповіді про наш проєкт. Повна: ../17-xray-observability.md. Факти, які в повній лекції «з пам'яті», тут із позначкою (не звірено). Доповнює лекцію 9 (CloudWatch). Навички 4.1.2, 4.2.1-4.2.5.

Головна ідея

X-Ray показує шлях одного запиту через усі сервіси і скільки часу зайняв кожен. Метрики кажуть «скільки», логи «що», X-Ray «де саме застряг». Образ: багажна бирка, що йде з валізою через усі пункти.

Це AWS-варіант розподіленого трейсингу, ідея така сама, як в OpenTelemetry.

Навіщо це так задумано

У розподіленій системі один запит проходить через багато сервісів, і логи кожного окремо не показують шлях. X-Ray зшиває їх в один трейс, щоб було видно, де затримка.

Крок 1. Словник

Термін Суть
trace усі дані одного запиту, має trace ID
segment робота одного сервісу
subsegment деталь: виклик DynamoDB, функція
service map / graph карта сервісів
annotation індексована мітка для пошуку
metadata неіндексовані дані
sampling яку частку запитів трейсити
inferred segment вузол сервісу, що сам не шле дані
filter expression запит по трейсах
group збережений фільтр

Крок 2. Основи

  • Сервіс надсилає segments; X-Ray збирає їх у traces; з них будує service graph.
  • Subsegments дають деталі: виклик AWS, HTTP, SQL. Сервіси, що не шлють даних (DynamoDB), з'являються як inferred segments.
  • Заголовок X-Amzn-Trace-Id: Root=1-...;Parent=...;Sampled=1 передає trace ID між сервісами. Перший сервіс його додає.
  • Дані зберігаються 30 днів. Документ сегмента до 64 КБ.
  • Sampling за замовчуванням: перший запит кожної секунди плюс 5% решти. Правила можна змінити: усі записи про гроші, мало для health checks.

Крок 3. Annotations проти metadata

Пошук фільтром так ні
Типи прості значення будь-які, об'єкти

«Знайти всі трейси користувача 42» означає annotation, бо лише вона індексується.

Помилки в X-Ray: Error це 4xx, Fault це 5xx, Throttle це 429.

Крок 4. Як увімкнути

  • Lambda: Tracing: Active у SAM. У ролі виконання потрібні xray:PutTraceSegments і xray:PutTelemetryRecords (є в політиці AWSXRayDaemonWriteAccess).
  • Для деталей у коді: Powertools Tracer, що обгортає SDK-клієнти (captureAWSv3Client), плюс putAnnotation.
  • API Gateway: увімкнути X-Ray на stage (лише REST API, не HTTP API).
  • EC2 і контейнери: потрібен X-Ray daemon: приймає дані по UDP 2000 і шле в X-Ray. В ECS це sidecar-контейнер.
  • Сучасний шлях: AWS Distro for OpenTelemetry (ADOT) і CloudWatch Application Signals (для Lambda він підключається шаром ADOT; старий X-Ray SDK із daemon AWS позначає як legacy).

Крок 5. Як це виглядає

Уявний трейс повільного запиту: API Gateway 2980 мс, у ньому Lambda 2940 мс, в ній Init 390 мс (холодний старт), DynamoDB 18 мс, S3 Get 2400 мс. Висновок: повільний S3 для великого файлу, а не база. Без трейсу оптимізували б не те.

Крок 6. Власні метрики (навичка 4.2.2)

таблицю можна гортати вбік →
Спосіб Як Коли
PutMetricData виклик API простий випадок, але це мережа й гроші на виклик
Metric filter лог перетворюється на метрику не хочете змінювати код
EMF структурований JSON у лог Lambda: без додаткового виклику

EMF робить Powertools Metrics автоматично.

  • Роздільна здатність: стандартна 1 хв; high-resolution до 1 с (StorageResolution: 1), зберігається 3 години.
  • Dimensions множать метрики: не кладіть userId у вимір, це тисячі метрик і великий рахунок.

Крок 7. Логи (навичка 4.2.1)

Структурований JSON замість рядків, з requestId і correlationId (Powertools Logger). Запити: Logs Insights.

Крок 8. Здоров'я застосунку (навичка 4.2.5)

  • Liveness: процес живий? Ні: перезапустити.
  • Readiness: готовий приймати трафік? Ні: не слати трафік, але не вбивати.
  • ALB health checks виводять поганий target; ECS замінює task; Route 53 health check перемикає DNS.
  • Lambda сама не має health check; дивіться Errors, Duration, Throttles.

Сповіщення про квоти й завершення деплою (навичка 4.2.3): EventBridge ловить подію CodeDeploy чи CodePipeline і шле в SNS; про alarm-и в Service Quotas на використання квот не звірено (не звірено).

Крок 10. X-Ray: сумісність, безпека, діагностика

Навіщо X-Ray. У монолітові легко зазирнути в лог. У розподіленої системи нема спільного погляду. X-Ray дає карту сервісів: на кожному вузлі середня затримка й кількість трейсів за хвилину.

З чим працює: Lambda, Elastic Beanstalk, ECS, ELB, API Gateway, EC2 і будь-який сервер (навіть on-premise). Трейсити можна кожен запит або вибірку (відсоток чи кількість за хвилину).

Безпека: IAM для прав, KMS для шифрування даних.

Cross-account: daemon або агент можна налаштувати слати трейси в інший акаунт (він приймає роль). Так роблять центральний акаунт для всіх трейсів.

Правила sampling можна змінювати без зміни коду.

Не працює X-Ray? Перевір:

Де Що
EC2 чи роль EC2 має дозволи і чи запущений X-Ray daemon
Lambda роль виконання з політикою для запису в X-Ray (у нотатках AWSX-RayWriteOnlyAccess, точну назву перевір (не звірено)), X-Ray підключено в коді, увімкнено Active Tracing

Крок 11. API X-Ray

API Що робить
PutTraceSegments надсилає segments
PutTelemetryRecords daemon надсилає телеметрію (скільки segments прийнято, відхилено, помилки зв'язку)
GetSamplingRules які правила sampling діють
GetServiceGraph головна карта
BatchGetTraces повні трейси за ID

Daemon потребує IAM-політики на запис.

Крок 12. X-Ray і Beanstalk

Платформи Beanstalk уже містять X-Ray daemon. Вмикають в консолі чи файлом .ebextensions/xray-daemon.config з XRayEnabled: true. Instance profile потребує дозволів, код інструментують SDK. Для Multicontainer Docker daemon не надається (не звірено).

Крок 13. ADOT і майбутнє X-Ray SDK

AWS Distro for OpenTelemetry (ADOT) збирає трейси, метрики і метадані ресурсів, може інструментувати код без змін і шле дані в X-Ray, CloudWatch, Managed Prometheus і партнерські системи. Переходять на нього, коли хочуть відкритий стандарт OpenTelemetry або кілька приймачів.

Виправлення до нотаток: X-Ray SDK і daemon із 25 лютого 2026 у режимі maintenance, а підтримка закінчується 25 лютого 2027. AWS радить мігрувати на OpenTelemetry. Сам X-Ray як сервіс лишається, а наявні застосунки працюють далі.

Словник

Термін Що це
Trace шлях одного запиту через усі сервіси
Segment / Subsegment ділянка роботи одного сервісу і її частини
Annotation індексована пара ключ-значення, за нею шукають
Metadata додаткові дані, за ними не шукають
Service graph карта сервісів і зв'язків між ними
X-Ray daemon локальний процес, що приймає сегменти й шле в X-Ray
EMF формат лога, з якого CloudWatch сам робить метрики
Liveness / Readiness живий чи вже готовий приймати запити

Що запам'ятати на іспит

  1. X-Ray показує шлях запиту; метрики скільки; логи що.
  2. Annotations індексуються (пошук), metadata ні.
  3. Sampling: перший запит кожної секунди плюс 5%. Дані зберігаються 30 днів.
  4. Lambda: Tracing: Active і права xray:PutTraceSegments, xray:PutTelemetryRecords.
  5. Заголовок X-Amzn-Trace-Id передає контекст.
  6. На EC2 і в контейнерах потрібен daemon (UDP 2000) чи ADOT.
  7. X-Ray на API Gateway лише для REST API.
  8. Власні метрики в Lambda: EMF.
  9. Error це 4xx, Fault це 5xx, Throttle це 429.

Відповіді
  1. Annotation (лише вона індексується).
  2. Працює sampling: перший запит секунди плюс 5% решти.
  3. Створити власні sampling rules.
  4. Це inferred segment: X-Ray виводить вузол з викликів клієнта.
  5. xray:PutTraceSegments і xray:PutTelemetryRecords (політика AWSXRayDaemonWriteAccess).
  6. Error це 4xx, Fault це 5xx.
  7. EMF: JSON у лог (Powertools Metrics).
  8. Liveness: жити чи перезапустити. Readiness: слати трафік чи ні.
  9. CloudTrail.
