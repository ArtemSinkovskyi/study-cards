Лекція 15: кешування і вибір сховища

Середній рівень: усі правила з повної лекції, але простими словами й без розповіді про наш проєкт. Повна: ../15-caching-and-data-stores.md. Факти, які в повній лекції «з пам'яті», тут із позначкою (не звірено).

Головна ідея

На іспиті тут питають «що обрати»: важливіше розрізняти варіанти, ніж знати налаштування. Навички: 1.3.2 (обрати сховище), 1.3.3 (обрати кеш), 4.3.4 (ElastiCache, DAX, CloudFront).

Кеш можна поставити на кожному кроці шляху: браузер (Cache-Control) → CloudFront → API Gateway cache → Lambda (змінні поза handler, /tmp) → ElastiCache або DAX → база. Правило: чим ближче до користувача, тим дешевше й швидше, але тим важче скинути.

Навіщо це так задумано

Кеш потрібен, бо база повільна й дорога, а більшість запитів повторюється. Чим ближче кеш до користувача, тим швидше й дешевше, але тим важче його скинути.

Крок 2. Стратегії кешування

таблицю можна гортати вбік →
Стратегія Як Плюс Мінус
Lazy loading (cache-aside) читаємо кеш; промах: база, потім запис у кеш у кеші лише потрібне; збій кешу не фатальний перший запит повільний; дані старіють
Write-through пишемо в базу і кеш одночасно дані свіжі у кеші зайве; запис повільніший
TTL будь-яка стратегія плюс час життя застарілі дані зникають самі
Write-behind запис спершу в кеш, у базу потім

Найчастіша комбінація: lazy loading плюс TTL. Питання «кеш містить застарілі дані» означає write-through або коротший TTL. «Кеш забитий непотрібним» означає lazy loading.

Крок 4. DAX

Кеш в пам'яті, сумісний з API DynamoDB:

  • читання з мілісекунд до мікросекунд (eventually consistent);
  • мінімальні зміни коду: інший клієнт, той самий API;
  • живе у VPC;
  • корисний для гарячих ключів (розвантажує hot partition);
  • найкраще, коли cache hit більше 90%.

Не підходить: потрібні strongly consistent читання (такі запити DAX пропускає прямо в DynamoDB і не кешує; так само TransactGetItems); багато записів; мало повторних читань; не потрібні мікросекунди.

DAX чи ElastiCache: DAX лише для DynamoDB, без коду кешування. ElastiCache для всього іншого, але логіку кешу пишете самі.

DAX докладніше

  1. Читання eventually consistent: DAX шукає в кеші. Знайшов (cache hit): віддає. Не знайшов (cache miss): іде в DynamoDB, кладе відповідь у кеш і віддає.
  2. Читання strongly consistent: DAX проксує прямо в DynamoDB, у кеш не кладе.
  3. Запис (write-through): дані спершу йдуть у таблицю DynamoDB, потім у DAX.
Параметр Значення
TTL кешу 5 хвилин за замовчуванням
Що кешує окремі items (GetItem, BatchGetItem) і результати Query, Scan (окремий кеш запитів)
Розмір кластера до 11 вузлів: primary плюс до 10 реплік (у нотатках «до 10», документація точніша)
Для production мінімум 3 вузли в різних зонах доступності; 1-2 вузли лише для розробки й тестів
Безпека VPC, IAM, шифрування в спокої через KMS, CloudTrail

DAX проти ElastiCache ще раз. DAX кешує окремі items і результати Query/Scan прозоро, без зміни коду. ElastiCache береться, коли треба кешувати результат агрегації (SUM, AVG), бо DynamoDB їх не рахує. Застосунок може мати обидва.

Крок 5. ElastiCache

Рушії: Valkey, Redis OSS, Memcached.

таблицю можна гортати вбік →
Valkey / Redis OSS Memcached
Реплікація, Multi-AZ так, до 5 реплік на primary ні
Персистентність, бекапи так ні
Структури даних, pub/sub, sorted sets так лише ключ-значення
Багатопотоковість так

Запам'ятайте: відмовостійкість чи рейтинг (sorted set) означає Redis/Valkey; простий розподілений кеш означає Memcached.

Режими: Serverless (без вузлів, оплата за ГБ і ECPU, завжди Multi-AZ) і node-based (свої вузли, оплата за годину). Працює у VPC, тож Lambda треба підключити до VPC. Типове застосування: сесії застосунку, щоб сервери були stateless.

Сесії: і DynamoDB, і ElastiCache підходять. DynamoDB простіше й без VPC, ElastiCache швидше.

Доповнення з нотаток

таблицю можна гортати вбік →
Redis / Valkey Memcached
Висока доступність Multi-AZ з автоматичним failover нема
Read replicas є нема
Розподіл даних sharding (cluster mode) дані діляться між вузлами

Поправка до нотаток: «довговічність через AOF» застаріла. У порівняльній таблиці ElastiCache довговічності в Redis/Valkey нема. Довговічна база в пам'яті це MemoryDB; ElastiCache це кеш. Докладніше: лекція про RDS, Aurora і RDS Proxy.

Де ще тримати сесії

Варіант Чому не підходить так добре

EFS треба підключати до EC2 як мережевий диск
EBS і Instance Store лише локальний кеш, не спільний між серверами

Крок 6. CloudFront

Cache key, cache policy, origin request policy, invalidation, OAC, signed URL і signed cookies проти S3 presigned: лекція 27.

Лише тут: TTL за замовчуванням min 0, default 86 400 с, max 31 536 000 с; Cache-Control: max-age від origin має пріоритет у межах min і max. Файли з Cache-Control: public, max-age=31536000, immutable потребують нового імені при зміні.

Крок 7. API Gateway cache

  • лише REST API, налаштовується на stage;
  • TTL за замовчуванням 300 с, максимум 3600 с, 0 вимикає;
  • кешує лише GET за замовчуванням;
  • відповідь до 1 МБ; створення кешу до 4 хв;
  • оплачується щогодини, без Free Tier;
  • клієнт скидає запис заголовком Cache-Control: max-age=0; потрібен дозвіл execute-api:InvalidateCache, інакше будь-хто зможе скидати кеш;
  • для параметрів запиту треба увімкнути cache keys, інакше різні запити отримають одну відповідь;
  • метрики CacheHitCount, CacheMissCount;
  • чутливі дані: увімкнути шифрування кешу.

Пастка: /users?type=admin без cache key поверне кешований результат для type=regular.

Крок 8. Кеш у самій Lambda

  • об'єкти поза handler живуть між викликами (клієнт S3, конфіг);
  • /tmp теж лишається, поки середовище живе;
  • покладатися не можна: середовище зникає, у кожного своя копія;
  • Parameter Store і Secrets Manager кешують через Lambda-розширення Parameters and Secrets: воно піднімає локальний HTTP-сервер на порту 2773 і тримає значення в пам'яті, тож функція не ходить в API на кожен виклик.

Крок 9. Як обрати сховище

Потрібно Вибір
файли, зображення, дешево S3
ключ-значення, мілісекунди, серверлес DynamoDB
SQL, JOIN, транзакції RDS
SQL з більшою швидкістю й реплікацією Aurora
кеш, сесії в пам'яті ElastiCache
повнотекстовий пошук, логи OpenSearch
SQL-запити по файлах S3 Athena
спільна файлова система для багатьох EC2 EFS
блочний диск одного EC2 EBS
архів S3 Glacier

RDS і Lambda: Lambda масштабується швидко, а RDS має обмежені з'єднання. Рішення RDS Proxy (пул з'єднань, навичка 4.3.1) (не звірено). Для читань read replicas. Докладно про RDS, Multi-AZ, Aurora і MemoryDB дивіться в окремій лекції про RDS.

Що запам'ятати на іспит

  1. Кеш ближче до користувача дешевший, але важче скинути.
  2. Lazy loading плюс TTL типова комбінація. Свіжі дані: write-through.
  3. DAX лише DynamoDB, мікросекунди, без strongly consistent.
  4. Redis/Valkey для відмовостійкості й sorted sets, Memcached для простого кешу.
  5. API Gateway cache: REST, stage, 300 с, лише GET, потрібні cache keys.
  6. CloudFront: багато файлів signed cookies, один файл signed URL.
  7. Lambda вичерпує з'єднання з RDS: RDS Proxy.
  8. Athena для SQL по S3.
  9. DAX: TTL 5 хв, до 11 вузлів, для production мінімум 3 вузли в різних зонах, write-through.
  10. Кешувати результат агрегації: ElastiCache; окремі items і запити DynamoDB: DAX.
  11. ElastiCache кеш, MemoryDB база; довговічності через AOF в ElastiCache нема.

Відповіді
  1. Lazy loading заповнює при першому читанні, write-through при записі. Якщо кеш застаріває, write-through або коротший TTL.
  2. Strongly consistent читання, багато записів, мало повторних читань, мікросекунди не потрібні.
  3. DAX лише для DynamoDB і без коду. ElastiCache для решти (сесії, RDS, складні обчислення).
  4. Redis/Valkey.
  5. Не ввімкнено cache keys для параметрів запиту.
  6. Заголовок Cache-Control: max-age=0 з дозволом execute-api:InvalidateCache. Без обмеження будь-хто скине кеш.
  7. CloudFront signed cookies.
  8. RDS Proxy.
  9. Athena.
