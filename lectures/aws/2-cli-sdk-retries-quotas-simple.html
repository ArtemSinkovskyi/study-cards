Лекція 2: CLI і SDK: повтори з exponential backoff і Service Quotas

Середній рівень: усі правила з повної лекції, але простими словами. Повна: ../2-cli-sdk-retries-quotas.md. Теоретична лекція, в AWS окремо не виконувалась. Що не підтверджено документацією, позначено (не звірено).

Головна ідея

Коли AWS відповідає «спробуй пізніше», SDK сам повторює запит, і кожного разу чекає довше. Це exponential backoff. А якщо ліміт справді замалий, його піднімають у Service Quotas.

Навіщо це так задумано

Тимчасові збої та «забагато запитів» минають самі. Якщо тисяча клієнтів одночасно ломиться знову, збій лише збільшується. Тому пауза росте, а до неї додають випадковість (jitter), щоб клієнти повторювали запити не всі разом.

Крок 1. Що таке backoff

Образ: 🚪 двері зайняті. Ти не б'єш у них щосекунди, а чекаєш 1 с, потім 2 с, потім 4 с, і щоразу трохи випадково довше чи коротше.

Усі офіційні SDK (boto3, Java та інші) роблять це самі. Власний цикл повторів зазвичай писати не треба.

Крок 2. Що SDK повторює

таблицю можна гортати вбік →
Тип помилки Приклади Повторює?
тимчасова таймаут, HTTP 500, 502, 503, 504 так, пауза від 50 мс
throttling ThrottlingException, ProvisionedThroughputExceededException, RequestLimitExceeded так, пауза від 1000 мс
нетимчасова AccessDeniedException, ValidationException, ResourceNotFoundException ні, помилка йде в код

Логіка проста: повторювати варто лише те, що може минути. Неправильні дані чи права від повтору не виправляться. Throttling теж буває HTTP 429, але його повторюють: SDK дивиться на код помилки.

Крок 3. Скільки спроб і де налаштувати

таблицю можна гортати вбік →
Що Змінна Ключ у ~/.aws/config Типово
режим AWS_RETRY_MODE retry_mode standard
всього спроб AWS_MAX_ATTEMPTS max_attempts 3

3 спроби це одна перша і два повтори. Значення 1 вимикає повтори. Для DynamoDB типово 4 спроби. Якщо значення задано в коді, воно сильніше за змінну, а змінна сильніша за файл.

Три режими:

  1. standard (типовий): backoff, jitter, ліміт повторів.
  2. adaptive: як standard, але ще притримує і першу спробу, коли бачить throttling. Для одного ресурсу, який часто тротлить.
  3. legacy: стара поведінка, різна в різних мовах, лише для сумісності.

Рецепт: скільки чекатиме SDK (3 кроки)

  1. Візьми базу: 50 мс для тимчасових, 1000 мс для throttling.
  2. Помнож її на 2 в степені номера повтору (перший повтор 2⁰, другий 2¹) і візьми не більше 20 секунд.
  3. Помнож результат на випадкове число від 0 до 1: це і є пауза.

Приклад: throttling, перший повтор: від 0 до 1000 мс. Другий: від 0 до 2000 мс.

Є ще ліміт повторів: при довгому збої SDK перестає повторювати й швидко повертає помилку. Це захищає від безкінечного очікування. Нова поведінка за документацією вмикається змінною AWS_NEW_RETRIES_2026=true; без неї діє попередня, трохи інша за часом пауз.

Крок 4. Service Quotas

Це інструмент, що показує ліміти акаунта, скільки вже використано, і дозволяє попросити підвищення.

  • Регульовані ліміти можна підняти запитом.
  • Жорсткі AWS не змінює.

Приклад з Lambda: aws service-quotas get-service-quota --service-code lambda --quota-code L-B99A9384 показує ліміт паралельності та чи він регульований. Запит на підняття: консоль або aws service-quotas request-service-quota-increase (з --service-code, --quota-code, --desired-value).

Сценарій іспиту: Lambda повертає 429, бо досягла ліміту паралельності акаунта. Рішення: підняти квоту в Service Quotas. Backoff на клієнті лише згладить, але не усуне причину.

Крок 5. Профілі в одному реченні

Облікові дані й налаштування CLI/SDK лежать у ~/.aws/credentials і ~/.aws/config, згруповані в профілі; профіль обирають --profile чи AWS_PROFILE. Порядок пошуку облікових даних розібрано в лекції про IAM.

Що запам'ятати на іспит

  • Backoff: пауза росте, jitter додає випадковість; SDK робить це сам.
  • Повторюються тимчасові помилки й throttling, а помилки валідації й прав ні.
  • Типово 3 спроби, режим standard; змінюється в коді, змінною, у config.
  • Service Quotas: бачити ліміти й підіймати регульовані.
  • Постійний throttling лікують квотою, а не повторами.
