Лекція 14: API Gateway і завантаження файлів у S3

Середній рівень: усі правила й числа з повної лекції, але простими словами. Повна: ../14-api-gateway.md. Факти, які в повній лекції позначено «з пам'яті», тут із позначкою (не звірено).

Головна ідея

API Gateway це керований «вхідний двір» для API: приймає HTTP-запити, перевіряє, обмежує й передає бекенду. Не треба тримати свій сервер для двох методів.

Навіщо це так задумано

API Gateway бере на себе нудне перед кодом (авторизацію, ліміти, кеш, перевірку входу), щоб ваша функція займалась лише логікою.

Крок 1. Який тип API обрати

таблицю можна гортати вбік →

Ціна дорожчий дешевший
Endpoint edge, regional, private лише regional

Запам'ятайте: усе «просунуте» лише в REST API. HTTP API обирають, коли потрібен дешевий проксі до Lambda. WebSocket API для двостороннього зв'язку (чат, сповіщення).

Типи endpoint: Edge-optimized (через CloudFront), Regional, Private (лише з VPC, через interface endpoint).

Крок 2. Інтеграції

Тип Що робить

HTTP / HTTP_PROXY на зовнішній HTTP
AWS service напряму в SQS, DynamoDB, без Lambda
Mock відповідь без бекенду

Головна пастка: Lambda proxy

Функція мусить повернути об'єкт із statusCode, headers, body і isBase64Encoded. body це рядок, а не об'єкт. Якщо формат інший, клієнт отримує 502 Bad Gateway. Запам'ятайте: 502 з API Gateway і Lambda означає, що функція повернула неправильний формат.

CORS у proxy-режимі робить сама функція: Access-Control-Allow-Origin у headers відповіді.

Крок 3. Stages і deployment

Зміни в REST API не діють, доки ви не зробите deployment на stage. Часте питання: «змінив метод, клієнти не бачать» означає, що немає deployment.

Stage це частина URL: .../prod/thumbnails.

Stage variables це як змінні середовища для стадії. Класичний зв'язок із Lambda aliases: в інтеграції function:api:${stageVariables.alias}, stage dev має alias=dev, stage prod має alias=live.

Пастка: для кожної функції чи alias, заданої через stage variable, дозвіл треба дати вручну: aws lambda add-permission з принципалом apigateway.amazonaws.com. Stage variables не для секретів.

Canary на stage (REST): частина трафіку йде на нову версію, усе логується окремо, потім Promote.

Крок 4. Трансформації, валідація, mock

  • Request validator перевіряє тіло за Model (JSON Schema) і обов'язкові параметри до виклику Lambda. Невалідне дає 400, а Lambda не коштувала ні копійки.
  • Mapping templates (VTL) змінюють запит і відповідь. Лише non-proxy.
  • Gateway responses налаштовують помилки, які повертає сам Gateway.
  • Mock-інтеграція: фронтенд може працювати, поки бекенду ще нема. Відповідь береться з шаблону, Lambda не викликається.

Крок 5. Захист і обмеження

Спосіб Коли
IAM (SigV4) сервіси AWS, внутрішнє
Cognito authorizer користувачі в user pool
Lambda authorizer свій токен, сторонні IdP
JWT authorizer HTTP API з OIDC
Resource policy обмежити IP, акаунти, VPC (REST)
API key + usage plan ідентифікація клієнтів і квоти, а не авторизація
mTLS, WAF взаємний TLS; захист від атак (WAF лише REST)

Lambda authorizer: на вхід токен, на вихід IAM-політика й principalId. Типи: TOKEN (один заголовок) і REQUEST (заголовки, query, stage variables; AWS радить саме його). Результат кешується: за замовчуванням 300 с, TTL 0 вимикає кеш; максимум 3 600 с підтверджено для HTTP API.

Пастка кешу авторизатора: політика кешується на токен, тож вона має покривати всі ресурси API, інакше користувач отримає випадковий 403 на іншому методі.

Ліміти: 10 000 RPS і burst 5 000 на акаунт і регіон для всіх API разом. (У частині регіонів типово 2 500 і 1 250.) Для Lambda ліміт concurrency 1 000, тож API може захлинутись нижче. Ліміт можна задати на stage, метод і клієнта (usage plan). Перевищення дає 429.

Інтеграція має timeout за замовчуванням до 29 с (для Regional і Private REST API його можна підняти за рахунок ліміту запитів; у HTTP API максимум 30 с), а тіло запиту й відповіді до 10 МБ, і цей ліміт підняти не можна. Тому файли не ганяють через API Gateway.

Крок 6. Завантаження файлів: presigned PUT

Ліміти 10 МБ і 6 МБ у Lambda означають, що файл на 200 МБ не пройде. Рішення: API лише видає посилання, а файл іде прямо в S3.

Факти про presigned URL:

  • посилання має права того, хто його створив; прав нема дає 403;
  • час життя: консоль 1 хв - 12 год; CLI і SDK до 7 днів;
  • створене тимчасовими обліковими даними помирає разом з ними, навіть якщо вказано більше: роль EC2 приблизно 6 год, роль сесії 1 год за замовчуванням;
  • перевіряється на старті запиту; завантаження, що вже йде, не обірветься;
  • SignatureDoesNotMatch: годинник, проксі, інший метод чи заголовки.

Великі файли: multipart. Від 100 МБ варто, понад 5 ГБ обов'язково. Частини від 5 МіБ до 5 ГіБ, до 10 000 частин, об'єкт до 48,8 ТіБ. Кожну частину можна підписати окремо (UploadPart). Незавершені multipart займають місце: lifecycle-правило AbortIncompleteMultipartUpload (лекція 3).

CORS бакета потрібен, якщо браузер завантажує напряму (PUT, дозволені заголовки). Інакше браузер блокує запит, хоч посилання правильне.

Крок 7. Тестові події й метрики

  • Тестову подію генерує sam local generate-event apigateway aws-proxy, локально API піднімає sam local start-api.
  • Custom domain потребує ACM-сертифіката (лекція 13).
  • Access logs і execution logs у CloudWatch (execution лише REST).
  • Метрики: Count, 4XXError, 5XXError, Latency (весь шлях), IntegrationLatency (лише бекенд). Різниця двох це час у самому Gateway.
  • ALB проти API Gateway: ALB це балансувальник без авторизації й usage plans, а API Gateway керує API.

Нема серверів. Є WebSocket, версії API (v1, v2), середовища (dev, test, prod), безпека, API keys і throttling.

Власний домен

  • HTTPS через ACM.
  • Edge-optimized: сертифікат у us-east-1. Regional: у тому самому регіоні, що й API (звірено).
  • У DNS потрібен CNAME або A-alias (Route 53).

Stages і deployment

  1. Змінили API: нічого не діє, доки не зробите deployment.
  2. Deployment іде на stage (їх скільки завгодно: dev, test, prod). У кожної свої параметри.
  3. Історія deployment зберігається, тож stage можна відкотити.

Stage variables

Це змінні середовища для API Gateway. Їх можна ставити в Lambda ARN, HTTP endpoint і parameter mapping templates. Формат ${stageVariables.variableName}.

Зв'язка зі Lambda alias: stage dev має alias = dev, stage prod має alias = live. В ARN інтеграції стоїть змінна, і API Gateway сам викликає потрібну функцію.

Canary

  • Вмикається на будь-якій stage (зазвичай prod).
  • Ви обираєте відсоток трафіку.
  • Метрики й логи окремі.
  • Можна перевизначити stage variables для canary.

Типи інтеграції

таблицю можна гортати вбік →
Тип Mapping template Суть
MOCK нема API Gateway відповідає сам, бекенд не викликає
HTTP / AWS є, налаштовуєте integration request і integration response перетворення на вході й виході
AWS_PROXY (Lambda proxy) нема запит клієнта цілком у Lambda, функція сама формує відповідь
HTTP_PROXY нема запит як є на бекенд, відповідь бекенду як є; можна додати заголовки (наприклад API key)

Mapping templates

Змінюють запит чи відповідь в інтеграціях AWS і HTTP: перейменувати query-параметри, змінити тіло, додати заголовки; Content-Type application/json або application/xml.

Приклад SOAP (рецепт у 4 кроки).

  1. Дістати дані із запиту (шлях, тіло чи заголовок).
  2. За шаблоном зібрати SOAP-повідомлення (XML).
  3. Викликати SOAP-сервіс і отримати XML.
  4. Перетворити XML у потрібний формат (наприклад JSON) і відповісти користувачеві.

Причина: SOAP на XML, REST на JSON.

OpenAPI і валідація

OpenAPI це опис REST API як код; з нього можна згенерувати SDK. API Gateway може перевірити запит до інтеграції й одразу відхилити, якщо він хибний.

Кеш відповідей

Що Значення
TTL за замовчуванням 300 с (мінімум 0, максимум 3600 с)
Де задається на stage; для окремого методу можна перевизначити
Розмір 0,5-237 ГБ
Ціна платно щогодини, дорого: для production, у dev часто зайве
Що кешується після вмикання лише GET

Інвалідація: клієнт шле Cache-Control: max-age=0, але лише з правом execute-api:InvalidateCache. Без політики будь-хто міг би скидати кеш і підняти затримку.

Метрики кешу: CacheHitCount (влучання) і CacheMissCount (промахи).

Usage plans і API keys

Потрібні, коли API продається як послуга.

  • Usage plan: хто користується якими stages і методами, скільки й наскільки швидко. Throttling і квоти діють на кожного клієнта.
  • API key: рядок, який роздають клієнтам, щоб ідентифікувати їх. Throttling застосовується до ключів.

Ключ ідентифікує, але не авторизує.

Логи, X-Ray, метрики

  • CloudWatch Logs вмикаються на рівні stage (для REST API рівень execution-логів ERROR або INFO, у конспекті ще DEBUG, не звірено). Є execution logs (дії API Gateway) і access logs (хто звертався).
  • X-Ray разом із Lambda дає повну картину.
  • Метрики: Count, 4XXError, 5XXError, Latency (весь шлях, включно з API Gateway), IntegrationLatency (лише бекенд).

Throttling

Ліміт акаунта 10 000 запитів на секунду на всі API. Перевищення дає 429 (можна повторити). Один перевантажений API без власного ліміту може «задушити» інші.

CORS

Потрібен, коли API викликають з іншого домену. Рецепт (3 кроки):

  1. Браузер із сайту www.example.com шле на api.example.com запит OPTIONS (preflight).
  2. API відповідає заголовками Access-Control-Allow-Origin, Access-Control-Allow-Methods, Access-Control-Allow-Headers.
  3. Якщо origin дозволено, браузер робить основний запит (наприклад GET).

WebSocket API

Двостороннє спілкування, зокрема повідомлення від сервера до клієнта (чат, сповіщення). Адреса wss://<id>.execute-api.<region>.amazonaws.com/<stage>.

Як сервер пише клієнтові: Lambda бере connectionId (зберігає, наприклад, у DynamoDB) і шле HTTP-запит на Connection URL .../@connections/<connectionId>, підписаний IAM Sig v4.

Операція Дія
POST надіслати повідомлення клієнтові
GET дізнатись статус підключення
DELETE відключити клієнта

Маршрутизація:

  1. Приходить JSON, наприклад {"service": "chat", "action": "join", ...}.
  2. Route selection expression ($request.body.action) бере поле action: join.
  3. Значення шукають серед route keys ($connect, $disconnect, $default, власні join, quit, delete) і викликають бекенд цього маршруту.

Якщо маршруту нема, іде $default. З'єднання закривається після 10 хв бездіяльності чи 2 год життя.

Що запам'ятати на іспит

  1. Просунуті функції лише в REST API, HTTP API дешевший.
  2. Lambda proxy: statusCode і рядок body, інакше 502.
  3. Зміна REST API діє лише після deployment на stage.
  4. Stage variables і aliases дають середовища, дозвіл дається вручну.
  5. API key ідентифікує, а не авторизує. 429 це ліміт.
  6. Файли йдуть через presigned URL, а не через API.
  7. Presigned живе не довше за облікові дані, що його створили.
  8. Edge-optimized: через CloudFront, але API в одному регіоні; сертифікат для edge у us-east-1 (не звірено).
  9. AWS_PROXY і HTTP_PROXY без mapping template; HTTP і AWS з ним; MOCK без бекенду.
  10. Canary: окремі метрики й логи, можна перевизначити stage variables.
  11. Кеш: TTL 300 с (0-3600), на stage, дорогий, лише GET; інвалідація Cache-Control: max-age=0 з правом InvalidateCache.
  12. CORS: preflight OPTIONS з Allow-Origin, Allow-Methods, Allow-Headers. Безпека: IAM, Cognito (авторизація в бекенді), Lambda authorizer (сторонні токени, кеш).
  13. HTTP API: без usage plans і API keys, з OIDC/OAuth2 і CORS. WebSocket: $connect, $disconnect, $default, route selection expression, @connections POST/GET/DELETE.

Відповіді
  1. REST API.
  2. Функція повернула неправильний формат (нема statusCode чи body не рядок).
  3. Deployment на stage.
  4. TOKEN бере один заголовок, REQUEST заголовки, query й stage variables.
  5. Політика кешується на токен і має покривати всі ресурси API.
  6. Ні, він лише ідентифікує клієнта й дає квоти.
  7. Mock-інтеграція.
  8. Посилання помирає разом з тимчасовими обліковими даними ролі.
