Лекція 7: SAM, шаблон і деплой

Середній рівень: усі правила й числа з повної лекції, але простими словами й без розповіді про наш проєкт, встановлення на Windows та проблеми. Повна: ../7-sam-template-deploy.md. Числа в повній лекції дані з пам'яті, їх варто звірити з документацією AWS. Це тема Deployment (на C03 це 22% іспиту).

Головна ідея

SAM це надбудова над CloudFormation з короткими типами для serverless і власним CLI. Один блок Function з Events розгортається в кілька ресурсів: функція, роль, правило, дозвіл. Деплой іде через CloudFormation: change set, потім стек.

Навіщо це так задумано

SAM скорочує довгі шаблони CloudFormation: одним блоком описуєте функцію, права й тригер замість десятка ресурсів. Поступовий деплой (canary) потрібен, щоб помилка зачепила 10% користувачів, а не всіх.

Крок 2. Як працює SAM

  • Шаблон з рядком Transform: AWS::Serverless-2016-10-31. CloudFormation розгортає короткі типи AWS::Serverless::* у звичайні ресурси (AWS::Lambda::Function, AWS::IAM::Role, AWS::Events::Rule, AWS::Lambda::Permission).
  • CLI: sam validate, sam build, sam local invoke, sam deploy, sam sync, sam logs.
  • Деплой: створюється change set, його виконання створює чи оновлює стек. Відкат стеку повертає все до попереднього стану.

Типи SAM для іспиту: AWS::Serverless::Function, Api, HttpApi, SimpleTable (DynamoDB), LayerVersion, Application, StateMachine, Connector.

Docker потрібен SAM лише для sam local invoke і sam build --use-container. Для sam validate і sam deploy не потрібен.

  • Transform вмикає SAM.
  • Parameters значення, що передаються під час деплою (--parameter-overrides).

Змінні середовища

Блок Environment.Variables. Значення лапкують, щоб YAML не перетворив їх на числа. Сума обмежена 4 КБ, секрети сюди не кладуть.

Права функції

Policies у функції. SAM автоматично створює IAM-роль із довірою до lambda.amazonaws.com і політикою AWSLambdaBasicExecutionRole. Додавайте лише потрібне (читання з одного префікса, запис в інший): розділення префіксів ще й захищає від нескінченного циклу. !Sub підставляє значення параметра, ${AWS::Partition} дає aws (чи aws-cn, aws-us-gov).

Внутрішні функції CloudFormation, які питають: !Ref, !Sub, !GetAtt, !Join, !If, Fn::ImportValue.

Тригер: правило EventBridge

Events з типом EventBridgeRule і Pattern (source, detail-type, detail, prefix). SAM створює правило і resource-based policy на функції (AWS::Lambda::Permission) для events.amazonaws.com. У Terraform без явного aws_lambda_permission правило не змогло б викликати функцію. Подія викликає функцію асинхронно.

Чому EventBridge, а не пряма S3 notification: конфігурація сповіщень бакета одна на всіх, друга підписка перезаписала б першу. З EventBridge бакет вмикає прапорець один раз, а кожна функція додає власне правило.

Повтори і DLQ

EventInvokeConfig:
  MaximumRetryAttempts: 2
  MaximumEventAgeInSeconds: 3600
DeadLetterQueue:
  Type: SQS
  TargetArn: !GetAtt ThumbnailsDlq.Arn
  • MaximumRetryAttempts допустимо 0-2, за замовчуванням 2: усього 3 спроби з паузами приблизно 1 і 2 хв.
  • MaximumEventAgeInSeconds від 60 с до 6 год.
  • DeadLetterQueue SAM сам додає до ролі sqs:SendMessage. Без DLQ чи destination невдала подія зникає. On-failure destination новіший і дає причину збою.

Логи

Без власного ресурсу AWS::Logs::LogGroup Lambda створює групу логів сама з retention «ніколи не видаляти». Описуйте групу в шаблоні (RetentionInDays) і прив'язуйте через LoggingConfig.LogGroup. При видаленні стеку логи теж прибираються.

Версії, alias і canary

  • AutoPublishAlias: live: при кожній зміні коду SAM публікує нову версію (незмінний знімок) і переставляє alias на неї. Події викликають alias.
  • DeploymentPreference робить зсув трафіку поступовим через CodeDeploy. Типи: Canary10Percent5Minutes (10% на 5 хв, далі 100%), Linear10PercentEvery1Minute, AllAtOnce.
  • Alarms: якщо CloudWatch alarm спрацював під час розгортання, CodeDeploy автоматично відкочує alias.
  • Hooks: PreTraffic і PostTraffic, функції перевірки до й після зсуву.

Alarm на помилки

Ім'я функції в alarm задають рядком, а не !Ref: функція посилається на alarm (в DeploymentPreference), alarm на функцію, і !Ref створив би циклічну залежність. TreatMissingData: notBreaching.

Outputs

Значення, які стек показує після деплою. Їх можна експортувати (Export) і використовувати в інших стеках через Fn::ImportValue.

Крок 4. CloudFront в SAM: де трапляється на іспиті

1. Edge-optimized API Gateway. REST API (AWS::Serverless::Api) за замовчуванням має тип кінцевої точки EDGE: запити йдуть на найближчу точку CloudFront, керовану сервісом (її нема в вашій консолі CloudFront). Значення EndpointConfiguration.Type: EDGE, REGIONAL, PRIVATE. Для розкиданих клієнтів документація радить REGIONAL разом із власним CloudFront. Ознака EDGE: заголовки Via ... CloudFront і X-Amz-Cf-Id. HTTP API окремого edge-режиму не має, лише Regional.

2. Власний розподіл. AWS::CloudFront::Distribution пишуть поруч зі SAM-ресурсами. Origin це Regional API або S3 (приватний бакет з OAC). Сертифікат ACM для CloudFront мусить бути в us-east-1.

3. Lambda@Edge (функція на краю):

Lambda@Edge

Версія лише пронумерована версія, не $LATEST і не alias
Не підтримуються змінні середовища, VPC, DLQ, layers, X-Ray, provisioned concurrency, контейнерні образи, arm64
Ephemeral storage не більше 512 МБ

Таймаут 30 с
Розмір архіву 50 МБ стиснутого

У SAM з AutoPublishAlias доступний атрибут !Ref MyFunction.Version (ARN версії), його підставляють в асоціацію CloudFront. Роль функції має довіряти і lambda.amazonaws.com, і edgelambda.amazonaws.com. Через us-east-1 функцію зазвичай виносять в окремий стек.

Крок 5. Перевірка без деплою

  • sam validate --lint перевіряє синтаксис і запускає cfn-lint (ловить неіснуючі властивості й неправильні типи).
  • Червоний NativeCommandError після sam validate у PowerShell це повідомлення про телеметрію в stderr, а не помилка. Вимикається SAM_CLI_TELEMETRY=0.
  • Ліміти Lambda для zip: 50 МБ стиснутого, 250 МБ розпакованого.

Аналог terraform plan: change set. sam deploy --no-execute-changeset створює change set і виводить таблицю змін (Add, Modify, Remove), але не виконує її. Слід в акаунті лишається: zip у S3 і порожній стек у статусі REVIEW_IN_PROGRESS. sam deploy за замовчуванням сам створює change set і питає підтвердження (вимикається --no-confirm-changeset).

Крок 6. Як деплоїти

sam deploy --stack-name ... --region ... --resolve-s3 --capabilities CAPABILITY_IAM

  • --stack-name назва стеку.
  • --resolve-s3 SAM сам створює службовий бакет для артефактів (стек aws-sam-cli-managed-default). У CI краще --s3-bucket, тоді ролі не потрібні права на створення бакетів і політик.
  • --capabilities CAPABILITY_IAM явна згода на створення IAM-ролей. Для іменованих ролей потрібен CAPABILITY_NAMED_IAM.
  • --guided питає параметри й зберігає їх у samconfig.toml.
  • Регіон вказуйте явно (з профілю він може бути іншим), інакше стек потрапить не туди, і правило EventBridge не побачить подій бакета.
  • Порядок: спершу платформа (прапорець EventBridge на бакеті), потім стек.

Крок 7. CI/CD: GitHub Actions і OIDC

таблицю можна гортати вбік →
Файл Коли Доступ до AWS Що робить
ci.yml PR і push у main нема npm ci, typecheck, тести, package, sam validate --lint
deploy.yml лише вручну (workflow_dispatch), лише з main OIDC-роль тести, package, sam deploy

Розділення навмисне: код із PR не торкається акаунта. sam validate --lint працює офлайн. Параметр dry_run додає --no-execute-changeset.

Як workflow потрапляє в AWS без ключів:

  1. Job має permissions: id-token: write, GitHub видає йому підписаний JWT (OIDC-токен) з aud і sub.
  2. aws-actions/configure-aws-credentials викликає STS AssumeRoleWithWebIdentity з токеном і ARN ролі.
  3. STS перевіряє підпис через OIDC-провайдера token.actions.githubusercontent.com, зареєстрованого в IAM, і умови trust policy.
  4. Job отримує тимчасові ключі.

Trust policy пускає лише aud = sts.amazonaws.com і sub = repo:<організація>/<репозиторій>:ref:refs/heads/main. Без умови на sub будь-який репозиторій GitHub міг би отримати цю роль (класична помилка).

Права ролі CI (найменші привілеї; CloudFormation діє від імені користувача, тому потрібні права і на стек, і на кожен створюваний ресурс):

Блок Чому потрібен
CloudFormation на стек створити й виконати change set
cloudformation:CreateChangeSet на transform/Serverless-2016-10-31 виконання макросу SAM
S3 на бакет артефактів sam deploy завантажує туди пакет
Lambda функція, версії, alias, async-конфіг
IAM на ролі стеку SAM створює execution-роль і роль CodeDeploy
CodeDeploy DeploymentPreference створює application і deployment group
SQS, CloudWatch Logs, alarm, EventBridge DLQ, лог-група, alarm, правило

iam:PassRole: щоб передати роль сервісу (Lambda, CodeDeploy), потрібен iam:PassRole на цю роль. Звужуйте до конкретних ролей: Resource: "*" дозволяє передати навіть адмінську роль, це шлях до ескалації привілеїв. Більшість дій CodeDeploy не підтримує зручне обмеження за ресурсом, тому там "Resource": "*".

Що створити в AWS перед першим запуском: IAM OIDC-провайдер token.actions.githubusercontent.com (audience sts.amazonaws.com), роль CI з trust і permission policy, бакет артефактів, змінні репозиторію (ARN ролі, бакет).

Що відбувається на сервері під час деплою:

  1. sam deploy пакує CodeUri, завантажує zip у S3, створює change set.
  2. CloudFormation застосовує зміни.
  3. AutoPublishAlias публікує нову версію й переставляє alias.
  4. DeploymentPreference зсуває трафік (10% на 5 хв, стежить за alarm, потім решта). Alarm спрацював: автовідкат alias.
  5. Якщо оновлення стеку провалилось, CloudFormation відкочує стек до попереднього стану.

Крок 8. Тригер і alias у консолі

  • На сторінці функції тригерів нема: вона показує $LATEST. SAM через AutoPublishAlias вішає правило EventBridge і дозвіл lambda:InvokeFunction на alias, а не на функцію. Це навмисно: тригер на $LATEST обходив би canary.
  • aws lambda get-policy без --qualifier дає ResourceNotFoundException, з --qualifier live покаже принципал events.amazonaws.com і ресурс alias.
  • Режим виклику задає той, хто викликає: EventBridge, S3, SNS, --invocation-type Event це async; API Gateway, SDK, RequestResponse це sync; SQS і Kinesis це event source mapping. Розділ Asynchronous invocation і EventInvokeConfig діють лише для async.
  • Destinations порожній, якщо помилки ловить DLQ.

Крок 9. Execution role проти resource-based policy

таблицю можна гортати вбік →
Execution role Resource-based policy
Питання що функція може робити хто може викликати функцію
Де в консолі Configuration → Permissions → Execution role Configuration → Permissions → Resource-based policy statements (на alias)
Створює SAM із Policies: та DeadLetterQueue Events: (тип EventBridgeRule)

Типова роль має три політики: AWSLambdaBasicExecutionRole (керована AWS, логи), вбудована з ваших Policies:, вбудована DeadLetterQueuePolicy (sqs:SendMessage на DLQ), яку SAM додав сам.

🖼 Відкрити повну схему з конспекту (гортати й масштабувати)

Що запам'ятати на іспит

  1. Transform: AWS::Serverless-2016-10-31 розгортає SAM у CloudFormation. Деплой іде через change set і стек.
  2. AutoPublishAlias створює версію й alias. DeploymentPreference зсуває трафік через CodeDeploy: Canary, Linear, AllAtOnce. Alarm дає автовідкат. Hooks: PreTraffic, PostTraffic.
  3. CAPABILITY_IAM для автоімен, CAPABILITY_NAMED_IAM для іменованих ролей.
  4. Change set дозволяє переглянути зміни перед виконанням (--no-execute-changeset).
  5. CI без ключів: OIDC, AssumeRoleWithWebIdentity, trust policy з обмеженням sub.
  6. iam:PassRole з Resource: "*" зазвичай неправильна відповідь.
  7. REST API типово EDGE (вбудований CloudFront). Lambda@Edge: us-east-1, лише версія, без env і VPC. CloudFront Functions: 10 КБ, JS, дешево.
  8. Тригер EventBridge висить на alias, а не на $LATEST.
  9. Нативні залежності потребують збірки під архітектуру функції.
