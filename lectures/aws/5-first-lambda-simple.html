Лекція 5: перша Lambda, що з неї треба для іспиту

Середній рівень. Повна лекція (87 КБ) здебільшого розповідь про проєкт (структура репозиторію, TypeScript, тести, збірка на Windows, проблеми), тому тут лише те, що перевіряють на іспиті. Повна: ../5-first-lambda-thumbnails.md. Теорію Lambda (моделі виклику, retries, права, версії) дивіться в лекції 6. Ціни й cold start в повній лекції приблизні, позначка (не звірено).

Головна ідея

Типова Lambda на іспиті: подія з S3 (через EventBridge) запускає функцію, яка читає об'єкт, обробляє і пише результат в інший префікс. Функція асинхронна, тому помилка дає повтори й DLQ. Прикладом тут була генерація зменшених копій картинок (мініатюр).

Схема: завантаження у images/ → S3 надсилає Object Created в EventBridge → правило з фільтром за префіксом → Lambda → читає images/*, пише thumbs/* → логи в CloudWatch → після повторів невдача йде в DLQ чи destination.

Навіщо це так задумано

Lambda придумали, щоб не тримати сервер заради малої роботи, яка буває рідко. Ви платите лише за час виконання, а масштабування бере на себе AWS.

Крок 2. Що в handler стандарт Lambda, а що вибір

Що Чиє
Експортована функція, на яку вказує налаштування handler (index.handler = файл index, експорт handler) вимога Lambda; назва довільна
Сигнатура (event, context) => Promise контракт runtime Node.js (старий callback теж підтримується)
Форма event визначає джерело, не ви
Повернене значення для sync іде викликачу (API Gateway зробить з нього HTTP-відповідь), для async ігнорується
Кинута помилка виклик невдалий; async Lambda повторить ще двічі, потім DLQ чи destination
Логіка окремо від handler рекомендація Lambda best practices: handler лише розбирає подію й викликає звичайні функції
Налаштування в змінних середовища, ініціалізація поза handler рекомендація AWS

Тому в async-функції помилку кидають (throw), а не тихо виходять: Lambda тоді повторить виклик.

Крок 3. Змінні середовища й конфігурація

  • Налаштування (префікси, ширини, якість) беруть зі змінних середовища, а не з коду. Змінити можна без зміни коду.
  • Загальний розмір змінних до 4 КБ; Lambda шифрує їх у спокої ключем KMS (за замовчуванням AWS managed). Секрети в них класти не радять: Secrets Manager чи Parameter Store.
  • Конфігурацію читають поза handler (в Init): якщо змінну забули, функція падає одразу при cold start, а не посеред обробки.
  • Захист від рекурсії: тригер лише на images/, запис лише в thumbs/. Якщо Lambda пише в префікс, з якого її тригерить, вона викликає сама себе знову й знову. AWS має recursive loop detection, але вона спрацьовує лише після приблизно 16 ітерацій і покриває не всі сценарії. Два незалежні запобіжники: префікс у правилі EventBridge і перевірка ключа в коді.
  • У S3 GetObject повертає Body як потік; його дочитують у пам'ять (transformToByteArray()). Для великих файлів потік обробляють частинами, бо пам'ять Lambda обмежена. Порожній Body означає кинути помилку (виклик невдалий, Lambda повторить), а не тихий вихід.
  • Ресайз кількох розмірів можна робити паралельно (Promise.all); більше пам'яті (отже CPU) прискорює обробку.
  • Імена результатів, у яких вміст за ключем ніколи не змінюється, віддають із Cache-Control: public, max-age=31536000, immutable; новий вміст виходить під новим ключем.

Крок 4. Powertools for AWS Lambda

Набір утиліт від AWS, фактичний стандарт для Lambda. Модулі ставляться окремо:

Модуль Що робить
Logger структурований JSON-лог з контекстом виклику (cold_start, function_name, function_request_id)
Parser перевіряє форму події під час виконання (zod-схеми); готові схеми, наприклад для подій S3 через EventBridge
Idempotency не виконує ту саму подію двічі, стан у DynamoDB
Metrics метрики CloudWatch у форматі EMF, без викликів API
Tracer трейси X-Ray
  • cold_start Logger визначає сам (true лише в першому виклику середовища); у Logs Insights можна порахувати частку холодних викликів.
  • Налаштовується змінними середовища без коду: POWERTOOLS_SERVICE_NAME, POWERTOOLS_LOG_LEVEL.
  • Тип S3ObjectCreatedNotificationEvent з @types/aws-lambda лише каже компілятору форму події, а під час виконання нічого не перевіряє; Parser справді перевіряє і кидає ParseError (виклик невдалий, retries і DLQ).
  • middy це middleware для Lambda (як у Express), Powertools з ним сумісний.

Крок 5. Тести

  • Тест-раннер (наприклад vitest) плюс aws-sdk-client-mock, що підміняє send у класі клієнта: справжній S3 і AWS-облікові дані не потрібні.
  • sdkStreamMixin з @smithy/util-stream потрібен, щоб імітувати Body потоком.
  • Тестові події беруть зі справжньої форми події (копіюють реальну).

Крок 6. Пакування

Lambda не бере код з git, їй завантажують готовий пакет.

таблицю можна гортати вбік →
Спосіб Ліміт Коли
Zip напряму (update-function-code --zip-file) 50 МБ стиснутого звичайний випадок
Zip через S3 250 МБ розпакованого, разом з усіма layers (до 5) пакет більший за 50 МБ
Container image з ECR 10 ГБ великі залежності: ML-модель, ffmpeg, Chromium
  • Бандл: esbuild склеює наш код і код бібліотек в один файл, прибирає типи TypeScript, викидає невикористане (tree shaking). Без бандла в zip довелося б класти весь node_modules: сотні файлів, повільний cold start.
  • Нативні залежності (наприклад sharp, що містить libvips) esbuild не збирає: їх позначають external і кладуть поруч з бандлом, зібраними під платформу Lambda (Linux, потрібна архітектура arm64 чи x86_64). Бінарники, зібрані на Windows, дадуть invalid ELF header.
  • Для вправи нативну залежність можна винести в layer.

На іспиті:

  • «Пакет 70 МБ, пряме завантаження не проходить»: через S3.
  • «Залежності понад 250 МБ»: container image.
  • «Кілька функцій мають спільну бібліотеку»: layer.
  • «Як зменшити cold start»: менший пакет (бандлінг, менше залежностей).

Крок 7. ECR

ECR це сховище Docker-образів в AWS. Lambda у варіанті container image бере образ тільки з ECR. Для іспиту:

  • логін: aws ecr get-login-password | docker login ..., потім docker push;
  • lifecycle policy видаляє старі образи;
  • image scanning перевіряє образи на вразливості.

Крок 8. Вибір runtime

Приблизний cold start (не звірено):

таблицю можна гортати вбік →
Runtime Cold start Примітка
Rust / Go (бінарник на provided.al2023) приблизно 10-50 мс найшвидший старт
Node.js приблизно 100-300 мс, із sharp 200-400 мс sharp (libvips) найшвидший для ресайзу
Python приблизно 150-300 мс
Java / Kotlin 1-5 с без SnapStart

Для асинхронної обробки cold start не головне: різниця між 30 і 300 мс губиться на фоні самої обробки. Для Go і Rust кодування webp потребує нативних бібліотек. У прикладах до іспиту найчастіше Node і Python.

Крок 9. Provisioned concurrency

Тримає N середовищ уже ініціалізованими, тож перші N одночасних викликів ідуть без cold start. Платно за кожну секунду, поки увімкнено, навіть без викликів; free tier не покриває. Приклад: 1 ГБ × 2 592 000 с у місяці × приблизно 0,0000041667 USD за ГБ·с дає близько 10,80 USD (не звірено).

Для асинхронних подій (результату ніхто не чекає) він не потрібен. Він має сенс для синхронних API (API Gateway → Lambda), особливо на Java.

Що з цього питають:

  • Reserved ≠ provisioned. Reserved безкоштовна: резервує частину ліміту акаунта й обмежує функцію зверху (значення 0 вимикає функцію). Provisioned платна й тримає середовища теплими.
  • Provisioned налаштовується на версію чи alias, не на $LATEST. Через Application Auto Scaling її вмикають за розкладом чи навантаженням.
  • Ліміт concurrency акаунта: за замовчуванням 1000 на регіон; у нових акаунтів нижчий, піднімається через Service Quotas. Перевищення: синхронний виклик отримує 429 TooManyRequestsException, асинхронний AWS повторює сам.
  • SnapStart (Java, Python, .NET): AWS відновлює середовище зі знімка вже ініціалізованого. Для Java безкоштовний. Типова відповідь на «Java Lambda повільно стартує, як дешево виправити».

Крок 10. CloudFront чи інший CDN

таблицю можна гортати вбік →
AWS CloudFront Зовнішній CDN (наприклад Cloudflare)
Origin = S3 приватний бакет через OAC публічне читання потрібних префіксів
Доступ до S3 bucket policy Principal: cloudfront.amazonaws.com з AWS:SourceArn bucket policy Principal: * лише на потрібні префікси
Сертифікат ACM у us-east-1 керує CDN
Кеш TTL з Cache-Control або політика кешу; інвалідація платна понад ліміт TTL з Cache-Control; purge вручну чи через API
Підписані URL і cookie є (приватний контент) окремі механізми
Edge-код Lambda@Edge, CloudFront Functions Workers

Типова відповідь іспиту: «приватний S3 за CDN, доступ лише від CDN» означає CloudFront плюс OAC.

Крок 11. Пам'ять, таймаут, вартість

  • Пам'ять 1536-2048 МБ для ресайзу обрано заради CPU, а не пам'яті (повне vCPU приблизно на 1769 МБ). Використання пам'яті видно лише в рядку REPORT (Max Memory Used).
  • Timeout дає запас на повільне читання з S3. Платять за фактичний час виклику, а не за timeout, тож великий timeout нічого не коштує, доки функція не зависає.
  • Вартість виклику це пам'ять в ГБ × тривалість у секундах. Постійний free tier: 400 000 ГБ·с на місяць (приклад: близько 1,3-1,5 ГБ·с на виклик, тобто 250-300 тис. викликів на місяць).
  • Init Duration (cold start) входить у Billed Duration.
  • Більше пам'яті дає коротший виклик, і добуток пам'ять × час часто виходить не більшим, ніж на малій пам'яті. Підібрати допоможе AWS Lambda Power Tuning.
  • arm64 (Graviton) приблизно на 20% дешевше за x86.
  • S3-клієнт створюйте поза handler.
  • Імпортуйте лише потрібний модуль SDK (@aws-sdk/client-s3), а не весь SDK.

Крок 12. Безпека й витрати (чек-лист)

  • Тригер лише на images/, запис лише в thumbs/.
  • Execution role з least privilege: s3:GetObject на images/*, s3:PutObject на thumbs/*, плюс запис логів. Більше нічого.
  • Без VPC, якщо Lambda лише читає й пише S3. Lambda у VPC втрачає вихід в інтернет; потрібен NAT Gateway (приблизно 32 USD на місяць) або VPC endpoint. Класичне питання: «Lambda в VPC не бачить інтернет чи AWS API».
  • Retention для CloudWatch Logs (наприклад 7 днів).
  • On-failure destination або DLQ для асинхронних викликів: Lambda повторює невдалий виклик двічі, потім подія йде туди, а не губиться.
  • Виклики безкоштовні в межах free tier: 1 млн викликів і 400 000 ГБ·с на місяць.

Крок 13. Два бакети: приватний і публічний

Для прикладу з двома різними потоками файлів:

  • бакет сайту: публічне читання лише потрібних префіксів, прапорець EventBridge увімкнено, Lambda запускається;
  • бакет клієнтських файлів: приватний, доступ лише через сервіс за токеном, події немає, Lambda не запускається (і прав у неї на нього нема).

Мініатюри публічні, а приватні файли (плани, фото) лишаються приватними.

Що запам'ятати на іспит

  1. Handler index.handler, сигнатура (event, context). Async: помилку кидають, щоб Lambda повторила.
  2. Змінні середовища до 4 КБ; секрети в Secrets Manager чи Parameter Store.
  3. Ініціалізація (клієнти, конфіг) поза handler.
  4. Zip 50 МБ напряму, 250 МБ розпакованого через S3, container image 10 ГБ з ECR.
  5. Нативні залежності збирати під платформу Lambda (invalid ELF header).
  6. Рекурсія S3 → Lambda → S3 лікується різними префіксами.
  7. Reserved безкоштовна й обмежує, provisioned платна й прогріває; provisioned лише на версію чи alias.
  8. SnapStart для Java (дешево), provisioned concurrency для синхронних API.
  9. Lambda у VPC без NAT/endpoint не має інтернету.
  10. Приватний S3 за CDN: CloudFront плюс OAC.
  11. Пам'ять для CPU; Power Tuning; arm64 дешевше на 20%.

Відповіді
  1. Кинута помилка робить виклик невдалим, і Lambda повторить його (потім DLQ). Тихий вихід втратить подію.
  2. Функція впаде одразу при cold start (Init) з зрозумілою помилкою, а не посеред обробки.
  3. Reserved безкоштовна, резервує частину ліміту й обмежує функцію зверху (0 вимикає). Provisioned платна, тримає середовища теплими, лише на версії чи alias.
  4. Через S3. Залежності понад 250 МБ: container image з ECR (до 10 ГБ).
  5. Бінарник зібраний під іншу ОС чи архітектуру. Збирають під Linux і архітектуру функції.
  6. Тригер і запис в один префікс. Лікується різними префіксами (images/ і thumbs/) і фільтром у правилі та в коді.
  7. Тип лише каже компілятору форму. Parser перевіряє подію під час виконання й кидає ParseError.
  8. SnapStart (для Java безкоштовний).
  9. NAT Gateway у приватній підмережі або VPC endpoint (gateway для S3).
  10. CloudFront з OAC.
  11. CPU росте з пам'яттю, а ресайз залежить від CPU.
  12. Init Duration (cold start) входить у Billed Duration.
