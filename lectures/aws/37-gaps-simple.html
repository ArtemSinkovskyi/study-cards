Лекція 37: що лишилось поза іншими лекціями

Середній рівень: усі правила з повної лекції, але простими словами. Повна: ../37-gaps-and-skill-map.md (там ще карта всіх 72 навичок, її тут нема). Факти, які в повній лекції «з пам'яті», тут із позначкою (не звірено).

Головна ідея

Це все, що не вмістилося в профільні лекції: серіалізація, Elastic Beanstalk, Auto Scaling, конкурентність, бази даних, сховища, мінімум мережі, інструменти і що поза іспитом. Це дрібні теми, але кожна дає окреме питання.

Навіщо це так задумано

Це дрібниці, які на іспиті трапляються поруч: формати даних, способи деплою, мережа. Різні сервіси передають дані по-різному, тому їх варто знати.

Крок 1. Серіалізація (навичка 1.1.7)

Сервіси AWS обмінюються текстом і байтами, тому дані треба перетворювати при вході й виході.

таблицю можна гортати вбік →
Де Що відбувається Пастка
Lambda подія приходить об'єктом, відповідь серіалізується в JSON Date, BigInt, цикли не переживуть JSON
API Gateway proxy event.body це рядок JSON.parse на вході, JSON.stringify на виході, інакше 502
SQS Body завжди рядок свій JSON кладете самі
SNS → SQS конверт SNS всередині Body подвійний JSON.parse або raw delivery
Kinesis data у події Lambda в base64 Buffer.from(data, "base64").toString()
Firehose повернути data теж треба в base64
DynamoDB низького рівня значення з типом: {"S":"text"}, {"N":"5"} числа передаються рядком
S3 Body це потік transformToByteArray() чи transformToString()

DynamoDB у коді. Щоб не писати типи вручну, беруть Document Client (DynamoDBDocumentClient) або marshall / unmarshall (не звірено).

Бінарні дані в JSON передають через base64 (+33% розміру), тому файли не ганяють через API.

Крок 2. Elastic Beanstalk

PaaS: завантажив код, отримав балансувальник, Auto Scaling і моніторинг. Шість способів оновлення, таблиця «як обирати» і .ebextensions: лекція 28, простою мовою тут.

Крок 3. EC2 і Auto Scaling (навичка 4.3.1)

Auto Scaling group і політики масштабування: лекція 4. Типи інстансів, роль EC2 через IMDSv2, диски: лекція 3.

Крок 4. Конкурентність (навичка 4.3.1)

Поняття Суть
Provisioned concurrency заздалегідь прогріті середовища Lambda
Connection pooling перевикористання з'єднань; RDS Proxy
Thread pool обмежена кількість робочих потоків; забагато дає тиск на базу
Keep-alive в SDK HTTP-з'єднання перевикористовуються, менша затримка

Головна ідея: кількість паралельних викликів має відповідати можливостям того, що позаду. 1000 Lambda × 1 з'єднання = 1000 з'єднань з RDS.

Крок 5. Бази даних

RDS чи Aurora, Multi-AZ проти read replica, RDS Proxy: лекція 10. Лише тут: перемикання через RDS Proxy до 66% швидше.

OpenSearch, Athena, zero-ETL із DynamoDB: лекція 14. «Повнотекстовий пошук по DynamoDB» означає OpenSearch.

Крок 6. Сховище: EBS, EFS, S3

EBS, Instance Store, EFS і порівняння з S3: лекція 3.

Крок 7. Мережа: мінімум для розробника

Проєктування мереж Exam Guide виключає, але використання лишається (1.2.1, 2.3.2).

  • Lambda до RDS у приватній підмережі, gateway і interface endpoint, NAT: лекція 5.
  • ALB (L7) і NLB (L4): лекція 4.
  • DNS і перемикання за здоров'ям: лекція 6.
  • CloudFront: лекція 7.

WAF: на CloudFront, ALB, API Gateway, AppSync. Правила в web ACL. Rate-based rule обмежує запити з одного IP за 5 хв.

Shield офіційно поза межами іспиту.

Lambda у VPC не має виходу в інтернет без NAT Gateway.

Крок 8. Інструменти

  • CodeArtifact: приватні npm, Maven, PyPI та інші формати; upstream до публічних; токен входу живе до 12 годин.
  • Amplify: хостинг фронтенду; гілка дає середовище (навичка 3.2.4): лекція 26.
  • CloudShell: термінал у браузері з готовими обліковими даними.
  • AWS CLI: --query фільтрує вивід на клієнті (JMESPath), а серверну фільтрацію дає параметр самого сервісу (часто --filters); пагінація автоматична, а --no-paginate віддає лише першу сторінку; --dry-run для EC2 (не звірено).
  • SDK: повтори, backoff, регіон і облікові дані: лекція 2.

Крок 9. Що офіційно поза іспитом

Зі сторінки Out-of-Scope: Amazon Rekognition, Polly, SageMaker AI, Strands Agents, Quick Sight, Connect, Elastic Transcoder, Shield, Storage Gateway, Snow Family, Transfer Family. Якщо така назва є у варіанті відповіді, це майже напевно не те.

Нове в C03 порівняно з C02: завдання 2.3 про AI-безпеку, AI-навички в 1.1, 3.2, 3.3, 4.1, 4.3, presigned URL (2.1), образи контейнерів (3.1), деплой контейнерів (3.3). Вага Troubleshooting виросла з 18% до 22%.

🖼 Схема: Elastic Beanstalk

Що це
Сервіс для легкого деплою: сам керує EC2, балансувальниками й масштабуванням. Веб-додатки й бекенди (Java, Python, Node.js, .NET).
Шлях
Create: Application
↓
Upload: Version (свій код, приклад AWS чи збережена версія)
↓
Launch: Environment (Web server чи Worker, платформа, preset)
↓
Manage: оновлювати версію
CLI
eb create
eb events
eb health
eb logs
eb open
eb status
Розширення середовища
`.ebextensions/`
  • у корені коду
  • YAML/JSON, файли `.config`
  • додати RDS, ElastiCache, DynamoDB
  • option_settings для змін
Версії
  • максимум 1000 версій
  • не чистите: деплой стане неможливим
  • lifecycle policy за місцем чи за часом
  • використані версії не видаляються
Cloning робить копію середовища з тією самою конфігурацією (LB, RDS, env vars). Корисно для тестового середовища. Для особливої платформи беріть Docker.
✅ коли доречно
  • швидкий MVP
  • мінімум DevOps
  • класичні моноліти
❌ коли ні
  • потрібен повний контроль над інфраструктурою

🖼 Схема: Beanstalk: способи оновлення

Способи оновлення: групи
На тих самих інстансах (in-place)
All-at-once
Rolling
Rolling з додатковим batch
На нових інстансах
Immutable
Traffic splitting
Окреме середовище (ручний прийом, не політика)
Blue-green: swap URL
Способи оновлення: крок за кроком
⚡ All-at-once
v1 STOPPEDv1 STOPPEDv2 RUNNINGv2 RUNNING
Усе за раз: є простій (downtime).
🔄 Rolling
v1 RUNNINGv1 RUNNINGv2 PENDING
Батчами (розмір налаштовується, може бути 1): менший ризик, повільніше. Потужність на час оновлення зменшується.
🧱 Rolling з batch
batch = 2v2 PENDINGv2 PENDING
Кілька за раз: швидше, але ризик вищий.
🧊 Immutable
v1 RUNNINGv2 нові інстансиv2 RUNNING
Нові інстанси у тимчасовому ASG, потім заміна. Схоже на blue-green, але без switch.
🔵🟢 Blue-green
BLUE v1GREEN v2switch
Не вбудована політика, а ручний прийом: друге середовище, потім swap URL.
🚦 Traffic splitting
v1 ← 90%v2 ← 10%
Піднімає повний набір нових інстансів, шле на них заданий відсоток на заданий час оцінювання. Якщо здорові, весь трафік іде на v2, інакше відкат. Потрібен ALB.
Traffic splitting це ЩО ми робимо (ділимо трафік), Canary це НАВІЩО (безпечна перевірка), Weighted це ЯК (через ваги).

🖼 Схема: EC2: сімейства інстансів

Сімейства інстансів
ЛітераДля чого
T / MT: tiny, M: medium, збалансоване, стандартна частота CPU
Ccompute: обчислення
R / X / zR: більше RAM, X: максимум RAM, z: висока частота CPU. Для RAM-інтенсивних задач, баз даних, аналітики
I / D / HI: максимальний IOPS, D: dense, величезні обсяги диска, H: високий throughput для потоків даних

Мнемоніка: I це Input/Output per sec, D це dense (густий, щільний), H це High disk throughput.

Що запам'ятати на іспит

  1. API Gateway proxy: event.body це рядок, JSON.parse на вході й JSON.stringify на виході.
  2. Kinesis data у Lambda в base64.
  3. Beanstalk: All at once швидко, але простій; Immutable найбезпечніше; Blue/green міняє DNS.
  4. Multi-AZ це доступність, read replica це масштабування читань.
  5. Lambda вичерпує з'єднання RDS: RDS Proxy.
  6. Спільні файли для багатьох EC2: EFS. Захист від SQL injection: WAF.
  7. Rekognition, Polly, SageMaker AI, Shield поза іспитом.
