Тема 6 з 11: Claude Code 101 (українською)

Шлях Claude Certified Architect. Тема 6: Claude Code як агент: цикл, дозволи, встановлення, процес «Explore → Plan → Code → Commit», контекст, рев'ю коду, CLAUDE.md, субагенти, скіли, MCP, хуки. Незнайомі слова шукай у картках English words. Джерело: курс Anthropic «Claude Code 101». Розділ 10 (скіли) і розділ 13 (перевірка) взято з офіційної документації Claude Code (звірено 2026-11-16). Команди, режими й налаштування змінюються між версіями, тож звіряй у своїй установці.

1. Що таке Claude Code

  • Claude Code це агентний інструмент для кодингу: він розуміє твою кодову базу, редагує файли, запускає команди й підключається до твоїх інструментів розробника.
  • Працює в терміналі, VS Code, застосунку Claude Desktop, у вебі та в IDE від JetBrains.
  • Чим він відрізняється від Claude.ai: Claude Code має прямий доступ до твоїх файлів, терміналу й кодової бази. Не треба копіювати код туди-сюди: він іде й робить роботу сам.
  • Головна відмінність: Claude Code працює як AI-агент.

Що таке агент? Програма, яка взаємодіє зі своїм середовищем і виконує дії, щоб досягти мети. Суть проста: мовна модель, що працює в циклі, і має доступ до інструментів, зовнішніх сервісів чи навіть інших агентів.

Що він робить на практиці:

  • читає й розуміє кодову базу (пояснює функцію, шукає джерело багу)
  • редагує файли по всьому проєкту (переписує функцію й оновлює всі місця, де її викликають)
  • запускає команди в терміналі (збірка, тести, встановлення пакетів) і за результатом вирішує, що робити далі
  • шукає в інтернеті документацію й довідники з API

Три речі, які варто тримати в голові:

  1. Вікно контексту це його робоча пам'ять: велика, але не безмежна. Claude шукає розумні шляхи знайти відповідь, не завантажуючи в контекст усю кодову базу.
  2. Дозволами керуєш ти: можна, щоб він питав перед кожною дією, а можна, щоб працював сам під фоновою перевіркою безпеки.
  3. Він може помилитися: не так зрозуміти задачу, додати баг, ускладнити рішення. Тож лишайся в процесі.

2. Як працює Claude Code

Агентний цикл

  1. Ти вводиш запит.
  2. Claude збирає контекст: працює з моделлю, а та повертає текст або виклик інструмента, який Claude Code може виконати.
  3. Він діє (редагує файл, запускає команду).
  4. Він перевіряє результат: чи справді це те, що просив запит.
  5. Якщо готово, зупиняється й чекає. Якщо ні, повертається на початок циклу й пробує знову, поки результат не буде повним і перевіреним.

Увесь цей час ти можеш додати контекст, перервати або скерувати його.

Контекст, інструменти, дозволи

  • Контекст: у вікні лежать розмова, вміст файлів і вивід команд. Коли воно майже повне, Claude Code стискає розмову автоматично (робить резюме, викидає зайве).
  • Інструменти це основа: звичайні асистенти беруть текст і повертають текст, а інструменти дають Claude Code самому вирішувати, коли виконати код (прочитати файл, пошукати в інтернеті тощо) і використати результат.
  • Режими дозволів:
Режим Що відбувається
Manual (ручний) Питає перед правкою файлу чи запуском команди
Auto-accept (у документації Accept edits) Правки файлів і звичні файлові команди (mkdir, mv, rm) проходять без питань, решта команд усе одно питає
Plan (планування) Читає файли й запускає команди, щоб розвідати, але не редагує код; спершу складає план
Auto Працює без звичних запитів; у фоні класифікатор перевіряє дії й намагається блокувати незворотні, руйнівні чи спрямовані за межі твого середовища. Якщо щось заблоковано, Claude зазвичай шукає безпечніший шлях або питає дозволу

У якому режимі стартує нова сесія, залежить від версії та налаштувань. Усе налаштовується у файлі settings. З пропуском дозволів будь обережний: помилку стає важче вчасно помітити.

Підсумок: агентний цикл, керований контекст, інструменти й налаштовувані дозволи: саме це відрізняє його від вікна чату.

3. Встановлення

  • Термінал: на macOS, Linux чи WSL ставиш інсталятором через curl (Homebrew теж підходить, але без автооновлення за замовчуванням). На Windows: PowerShell Invoke-RestMethod, CMD curl або winget (теж без автооновлення). Потім у теці проєкту запускаєш claude. Якщо команди немає, перезапусти термінал.
  • Перший запуск: обираєш тему, заходиш з акаунтом Claude (Pro, Max, Ultra, Team чи Enterprise) або з API-ключем. Якщо в організації є Enterprise, обирай цей варіант.
  • Область доступу: у якій теці запустив claude, ту теку з усіма підтеками він і бачить.
  • VS Code: ставиш розширення «Claude Code» від Anthropic (з синьою позначкою), за потреби перезапускаєш, відкриваєш через палітру команд (Ctrl/Cmd+Shift+P, «Claude Code Open in New Tab») або через логотип. Майже те саме, що термінал.
  • JetBrains: ставиш плагін із Marketplace, перезапускаєш; логотип відкриває панель із терміналом поруч із редактором.
  • Desktop: вкладка Code: працюєш у вибраній теці, міняєш дозволи, можеш навіть використати хмарне середовище.
  • Веб: claude.ai/code; лише репозиторії GitHub.

Що обрати? Термінал: нові можливості з'являються там першими. IDE: майже те саме, ближче до редактора. Desktop: зручно, коли Claude працює у фоні, а ти займаєшся іншим. Веб: віддалена робота з репозиторієм на GitHub.

4. Перший запит

  • Режими перемикаються через Shift + Tab. Правильної відповіді нема: бери те, з чим тобі комфортно.
  • Plan mode читає файли й досліджує твою ідею, не редагуючи код, ставить уточнювальні питання, а тоді дає докладний план, який може виконати. Найкраще для складних багатокрокових фіч і для безпечного рев'ю коду.
  • Приклад: «У додатку треба темну тему. Додай перемикач у шапці й підбери контрастний колір, який пасує до наявної світлої теми». Переглянь план, прийми його, нехай Claude працює; наприкінці бачиш, що він зробив і чому.
  • Описуй якомога докладніше.

5. Процес Explore → Plan → Code → Commit

Якщо запам'ятати з курсу лише одне, то це. Без нього люди одразу просять написати код, а потім довго виправляють курс.

Крок Що відбувається
Explore (розвідка) Дає Claude потрібний контекст. Користуйся plan mode (або субагентом Explore поза plan mode, щоб отримати огляд кодової бази)
Plan (план) План дій, за яким Claude потім міряє успіх. Найкраще місце, щоб підправити напрямок: доки коду ще нема
Code (код) Діалог туди-сюди. Затверджуєш план; режим дозволів визначає, як часто він питатиме
Commit (коміт) Сам перевір, запусти субагента-рев'юера, а тоді нехай Claude напише повідомлення коміту у твоєму стилі

Приклад для Explore/Plan: «Треба додати конвертацію в WebP до нашого конвеєра завантаження зображень. З'ясуй, де це краще робити, чи потрібні нові залежності й як за це взятися».

Поради для кроку Code:

  • Задай критерій успіху: Claude має знати, що таке «правильно». Запиши це в план.
  • Додай інструменти: для вебінтерфейсу розширення Claude in Chrome дає Claude керувати вкладкою браузера й самому тестувати UI.
  • Дай набір тестів, за яким можна звірятися. Переконайся, що тестам можна вірити (без хибнопозитивних).
  • Якщо Claude раз у раз спотикається об одне й те саме, попроси записати рішення в CLAUDE.md.

Навіщо рев'юер-субагент: у нього свіжий погляд, і він не несе упередження головної сесії.

6. Керування контекстом

  • Місце займає все: кожен прочитаний файл, кожна команда, кожне повідомлення.
  • Коли вікно заповнюється: автоматичне стискання робить резюме важливого й викидає непотрібні результати інструментів. Воно може загубити деталі.
таблицю можна гортати вбік →
Команда Що робить Коли брати
/compact Стискає все, що було досі, залишаючи пам'ять про роботу Ти в одній фічі, впираєшся в ліміт, а продовжувати треба
/clear Стирає все, нова сесія без пам'яті Береш нову фічу; стара розмова її б «забарвила»
/context Показує розмір, найбільші категорії й візуальну розбивку Хочеш побачити, що з'їдає вікно

Те, що треба пам'ятати між сесіями, клади в CLAUDE.md.

Як заощадити контекст:

  • Будь конкретним. Розпливчастий запит здається дешевшим, але змушує Claude більше досліджувати й міркувати, і це коштує більше контексту.
  • Стеж за MCP-серверами. За замовчуванням сервер завантажує лише назви інструментів та інструкції, повні подробиці підтягуються за потреби. Але місце займає кожен сервер, тож вимикай ті, що не стосуються проєкту.
  • Використовуй субагентів: окреме вікно контексту, назад повертається лише резюме («де в нас ендпоінти авторизації?»).

7. Рев'ю коду

Сесія, що писала код, не найкращий суддя для нього. Спершу подивись зміну сам, а потім дай Claude переглянути її ще раз у чистому контексті.

  • /diff відкриває інтерактивний перегляд незакомічених змін (і того, що змінив кожен хід Claude). Стрілки перемикають файли, Enter відкриває. /diff і /code-review потребують git-репозиторію. На іншій системі контролю версій дивись зміну у своєму інструменті й проси Claude звичайними словами переглянути файли, яких він торкався; /rewind усе одно працює.
  • Що заслуговує другого погляду щоразу:
    1. Зміни, яких ти не просив (чиєсь значення в конфігу, переписаний допоміжний метод).
    2. Ослаблені тести (пропущені, видалені чи підганяні, щоб пройшли).
    3. Нові пакети й захардкоджені значення (залежність заради однієї функції, URL чи ключ просто в коді).
  • Відкотити хибну зміну: /rewind (або двічі Esc на порожньому запиті), вибираєш запит, обираєш Restore code and conversation. Файли, змінені командами оболонки (скажімо, встановленням пакета), не відкочуються.
  • /code-review це другий рев'юер із чистим контекстом: він звітує, нічого не править, поки не попросиш, працює у фоні (від секунд до кількох хвилин) і витрачає твій ліміт. Можна й просто попросити словами. Рівні effort: /code-review low (менше знахідок, найупевненіші), high (ширша сітка, є й менш певні). Рівень запам'ятовується.

Вправа 1 (порівняти підсумок із diff): підсумок Claude про зміну форми реєстрації правдивий («валідацію додано, тести проходять»), але змінилося 8 файлів. Три заслуговують уваги: файл тестів (послаблено перевірки), src/config.ts (захардкоджений URL) і нова залежність у package.json/lock-файлі. Урок: правдивий підсумок усе одно може промовчати про зміни, які варто перевірити. (Точного набору прапорців у джерелі нема, це виведено з прикладу.)

Сортування знахідок: Fix now, Ask why, Leave it.

  • Fix now: справжня проблема, яка важлива. Ask why: ти не можеш перевірити, або вона виглядає дивно; рев'юер, що читає «з нуля», теж може помилитися. Leave it: справжня, але дрібна; збери в пачку на потім.
  • Щоб спитати «чому», процитуй знахідку й попроси Claude перевірити ще раз: «Ти пишеш, що isValidEmail не обрізає пробіли, а в рядку 4 є trim(). Перевір ще раз».
  • Просячи виправлення, проси докази: «Виправ першу знахідку, поверни початкову перевірку, запусти тести й покажи вивід».
  • Якщо виправлення виросло у велику зміну, зроби рев'ю ще раз.

Вправа 2 (чотири знахідки), відповіді виведено з показаного коду:

таблицю можна гортати вбік →
№ Знахідка Купка
1 Тест пропущено, перевірку послаблено Fix now
2 isValidEmail не обрізає пробіли Ask why (код уже викликає trim(): хибна тривога)
3 API_URL захардкоджено на localhost:3000 Fix now (продакшн ходив би на адресу розробки)
4 Hex-колір замість --color-danger Leave it (лише стиль)

Коли придивлятися пильніше: однорядкову зміну досить глянути побіжно. Людське й Claude-рев'ю разом потрібні, коли зміна більша, ніж ти можеш втримати в голові, торкається чутливого чи руйнівного, і перед передачею колезі.

Це не Claude Code Review: то окремий командний продукт (власник організації вмикає його для репозиторію на GitHub, і він лишає коментарі в pull request). Для цього уроку він не потрібен.

8. Файл CLAUDE.md

  • Проблема: без нього кожна сесія стартує з нуля: Claude заново досліджує проєкт, з'ясовує залежності й готові фічі та вигадує припущення.
  • Що це: Markdown-файл у корені проєкту, який читається автоматично на початку кожної сесії й додається до твого запиту. Це як вступний інструктаж для кодової бази.
  • Приклад вмісту: проєкт (Next.js 15, App Router, Tailwind, Drizzle), команди (pnpm dev, pnpm test, pnpm lint), стиль коду (2 пробіли, іменовані експорти, API-маршрути в app/api/).
  • Для команди: коміть його. Рівень проєкту: CLAUDE.md у корені, спільний для всіх. Рівень користувача: CLAUDE.md у твоїй теці конфігурації, особистий і діє в усіх проєктах.

Поради:

  • Зберігай виправлення в пам'ять: якщо раз у раз поправляєш те саме, попроси Claude записати правило.
  • Посилайся на документи через @: @README.md підтягує цей файл.
  • Почни без нього, подивись, де постійно доводиться виправляти модель, тримай файл компактним, а тоді запусти /init, щоб згенерувати його.

Те, що завжди правда, лежить у CLAUDE.md. Процедури лежать у скілі (розділ 10).

9. Субагенти

  • Claude вміє передавати частини роботи субагентам, які виконують складові завдання паралельно, кожен у власному ізольованому вікні контексту.
  • Як це працює: Claude породжує субагента («дослідь цю кодову базу»), той робить усю розвідку у своєму контексті, а тоді повертає лише резюме. Ти отримуєш відповідь, а шлях до неї не засмічує головний контекст.
  • Як створити: Markdown-файл із YAML-шапкою. Найпростіше доручити це Claude: «Створи субагента code-reviewer у .claude/agents/, що перевіряє код на баги й читабельність. Зроби його лише для читання».
  • Де: .claude/agents/ діє в цьому проєкті; ~/.claude/agents/ у всіх проєктах. Якщо теки не було на старті сесії, перезапусти Claude Code.
  • Налаштування: постійна пам'ять між розмовами; попереднє завантаження скілів через ключ skills (у субагента вантажиться весь скіл, на відміну від головної розмови).

10. Скіли (з офіційної документації Claude Code)

У матеріалі курсу була лише примітка «тут можна додати про скіли з офіційної документації»; цей розділ зібрано зі сторінки Skills документації Claude Code.

  • Скіл це тека з файлом SKILL.md: інструкції, які Claude завантажує, коли вони доречні, або які ти викликаєш напряму через /назва-скіла. Старі файли в .claude/commands/ досі працюють і вже злиті зі скілами.
  • Скіли тримають процедури, CLAUDE.md тримає факти. Якщо розділ у CLAUDE.md виріс у процедуру, винеси його в скіл (тіло вантажиться лише коли воно потрібне).

Де живуть скіли:

Рівень Шлях
Enterprise .claude/skills/<name>/SKILL.md у теці managed settings
Особистий ~/.claude/skills/<name>/SKILL.md (усі твої проєкти)
Проєкту .claude/skills/<name>/SKILL.md (коміть, щоб ділитися)
Плагіна <plugin>/skills/<name>/SKILL.md, викликається як /plugin-name:skill-name

Однакова назва в кількох місцях: enterprise сильніший за особистий, особистий сильніший за проєктний; скіли плагінів мають власний префікс, тож не конфліктують. Claude Code стежить за теками зі скілами, тому правки діють просто в сесії.

Будова: YAML-шапка між рядками ---, далі інструкції в Markdown. Усі поля необов'язкові, рекомендоване одне: description.

---
name: summarize-changes
description: Summarizes uncommitted changes and flags risky ones. Use when the user asks what changed or wants a commit message.
allowed-tools: Bash(git diff *) Bash(git status *)
---
Summarize the changes, then list any risks.
Поле Навіщо
name Назва в меню / (за замовчуванням ім'я теки)
description Що робить і коли застосовувати: за цим Claude вирішує, чи завантажувати
disable-model-invocation: true Викликати може лише ти (для дій із побічними ефектами, як /deploy)
user-invocable: false Прихований із меню /; завантажує лише Claude (фонові знання)
allowed-tools Інструменти, заздалегідь дозволені на час скіла; решту не обмежує
context: fork (+ agent) Запустити скіл у субагенті, який не бачить твоєї розмови
model, effort Перевизначення на цей хід
paths Автозавантаження, лише коли в роботі відповідні файли
hooks Хуки, що діють, поки скіл використовується

Як відбувається завантаження (поступове розкриття): описи всіх скілів лежать у контексті, тож Claude знає, що в нього є; повне тіло завантажується лише тоді, коли скіл потрібен. description разом із when_to_use у списку обрізається на 1 536 символах: найважливіший випадок став на початок. Завантажений вміст лишається в розмові, тому пиши постійні інструкції, а не разові кроки. Після стискання останній виклик кожного скіла приєднується назад (до 5 000 токенів на скіл і 25 000 разом).

Допоміжні файли: тримай SKILL.md у межах приблизно 500 рядків, а подробиці виносить у reference.md, examples.md чи scripts/ (скрипти виконуються, а не завантажуються). Посилайся на них зі SKILL.md, щоб Claude знав, коли їх читати.

Аргументи й динамічний контекст: $ARGUMENTS, $0/$1, ${CLAUDE_SKILL_DIR}. Рядок на кшталт !`git diff HEAD` запускає команду до надсилання скіла й вставляє її вивід.

Скіли проти інших інструментів:

Інструмент Для чого
CLAUDE.md Постійні факти про проєкт
Скіл Повторювана процедура, що вантажиться за потреби
Субагент Ізольований виконавець зі своїм контекстом (скіл може йти в ньому через context: fork)
Хук Те, що має відбуватися щоразу (детерміновано)
MCP Підключення зовнішніх інструментів і даних (поєднуй зі скілом, який вчить ними користуватися)

Контроль доступу: заборонити всі скіли можна правилом Skill у deny; дозволити чи заборонити один: Skill(name). Серед вбудованих скілів є /code-review, /debug, /loop, /claude-api, /skill-doctor (показує, скільки контексту коштують твої скіли).

11. MCP

  • Model Context Protocol це відкритий стандарт, який підключає Claude Code до зовнішніх інструментів і даних (бази, застосунки для роботи, публічні репозиторії). Claude сам вирішує, коли їх застосувати.
  • Приклади: MCP-сервер Linear, щоб тягнути деталі задач; Context7 для актуальної документації бібліотек.
  • Додати сервер: claude mcp add. Два основні типи: HTTP (віддалений, його хостить сервіс) і stdio (локальний процес на твоїй машині).
  • Керування: /mcp у сесії показує, що підключено, статус, і дає вимкнути сервер.
  • Області дії (scopes):
Scope Що означає
Local Лише поточний проєкт, лише ти (за замовчуванням)
User Усі твої проєкти
Project .mcp.json у репозиторії; уся команда отримує ті самі сервери
  • Ціна для контексту: кожен підключений сервер додає назви інструментів та інструкції, навіть коли простоює. Відкрий /mcp і вимкни зайві. Tool search увімкнено за замовчуванням: повні описи інструментів не потрапляють у контекст, доки не знадобляться.
  • Якщо є CLI, віддавай перевагу йому (gh, aws): він не додає списку інструментів, тож ощадніший для контексту.
  • Поєднуй MCP-сервер зі скілом, який вчить Claude добре користуватися його інструментами.

12. Хуки

  • Хуки запускають команди в певні моменти життєвого циклу Claude Code. На відміну від усього іншого тут вони детерміновані: виконуються завжди.
  • Навіщо: «запускай Prettier після кожної правки» в CLAUDE.md спрацює здебільшого; хук робить так, що це відбувається щоразу.
  • Приклади: автоформатування після правок; журнал усіх команд для аудиту; блокування небезпечних операцій; сповіщення, коли Claude закінчив.
  • Налаштовуються в settings.json: обираєш подію, за бажанням matcher (до яких інструментів), і команду.
Подія Коли спрацьовує
PreToolUse Перед викликом інструмента (може заблокувати)
PostToolUse Після завершення виклику інструмента
UserPromptSubmit Коли ти надсилаєш запит, до обробки Claude
Stop Коли Claude завершив відповідь
Notification Коли Claude надсилає сповіщення
  • Приклад автоформатування: PostToolUse із matcher Edit|Write і командою, що дивиться на розширення файлу й запускає Prettier, gofmt тощо.
  • Блокування через PreToolUse: хук отримує назву інструмента й вхідні дані як JSON на stdin. Код виходу 0: продовжувати. Код виходу 2: блок; stderr повертається Claude, щоб він міг підлаштуватися. Будь-який інший код: неблокувальна помилка, показується тобі, нічого не зупиняє.
  • Поділитися з командою: хуки в .claude/settings.json діють на рівні проєкту й коміться. Використовуй CLAUDE_PROJECT_DIR, щоб посилатися на скрипти: так вони працюють з будь-якої робочої теки.
  • /hooks відкриває список лише для читання, щоб перевірити, що новий хук з'явився.

Якщо щось має відбуватися щоразу без винятків, не клади це в промпт. Клади в хук.

13. Звірено з офіційною документацією (2026-11-16)

Джерела: документація Claude Code: «Skills», «Permission modes», «Hooks», «MCP».

Твердження в курсі Статус
Режими Manual, Auto-accept, Plan, Auto; Shift+Tab перемикає Підтверджено, але з іншими назвами: у документації Manual (default), Accept edits (acceptEdits), Plan, Auto. Документація додає Don't ask (dontAsk) для закритого CI (у циклі Shift+Tab його нема) і Bypass permissions лише для ізольованих контейнерів і віртуальних машин

Події хуків PreToolUse, PostToolUse, UserPromptSubmit, Stop, Notification Підтверджено; у документації їх набагато більше (SessionStart, SubagentStop, PreCompact та інші). Коди виходу 0 / 2 / інший підтверджено; документація наголошує: код 1 не блокує

/hooks лише для читання Підтверджено
MCP: HTTP і stdio; scopes local, user, project; .mcp.json Підтверджено. Local це scope за замовчуванням. SSE застарів; WebSocket лише через .mcp.json чи add-json. Документація додає пріоритет local, потім project, потім user для серверів з однаковою назвою. Інтерактивна сесія просить схвалити проєктні сервери

Відповіді до вправ із рев'ю (які файли позначити, яка купка) У джерелі не наведено; виведено з показаного коду

Підсумок для іспиту: знай цикл (зібрати контекст, діяти, перевірити), чотири режими, процес Explore → Plan → Code → Commit, /compact проти /clear, навіщо рев'юер із чистим контекстом, CLAUDE.md проти скіла, субагента, хука й MCP, та правило коду виходу 2. Назви команд, підтримку моделей і номери версій сприймай як факти, які треба звіряти.

15. Питання з тесту курсу

1. Claude Code працює як AI-агент. Що таке AI-агент? ШІ, який діє, щоб досягти мети. Хибні відповіді: чат-бот, що відповідає в реальному часі; редактор коду з автодоповненням; хмарний сервіс для хостингу проєктів.

2. Що відбувається, коли Claude Code досягає ліміту вікна контексту? Він автоматично стискає розмову, щоб звільнити місце. Хибні відповіді: перемикається на меншу модель; видаляє найстаріші файли; зупиняється й просить перезапустити сесію.

3. Який рекомендований процес роботи з Claude Code? Explore → Plan → Code → Commit. Хибні відповіді: Code → Test → Deploy → Monitor; Write → Review → Merge → Ship; Prompt → Accept → Push → Repeat.

4. Як Claude Code використовує файл CLAUDE.md? Читає його автоматично на початку кожної сесії. Хибні відповіді: лише після /init; один раз, коли створюєш проєкт; лише коли ти попросиш.
