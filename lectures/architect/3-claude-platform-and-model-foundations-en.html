1. The four decisions

Before you write a prompt, four decisions set the quality ceiling of a session:

  1. Entry point: Chat, Project, Artifact or Research.
  2. Capability layer: Projects, Skills, Code Execution, Memory.
  3. Model: Haiku, Sonnet or Opus.
  4. Context management: restart, summarize or persist.

They decide whether sessions build on prior work or need constant re-setup.

2. Five behavioral properties of Claude

таблицю можна гортати вбік →
# Property What to do
1 Responses vary: the same question twice gives two answers. Output is produced by probability, not retrieved from a database. Plan for variation and build review into the workflow
2 Confident tone is not a signal of accuracy: a fabricated statistic reads as assured as a verified one. Build verification habits
3 Context is a budget: every conversation has a working-memory limit. Near the limit, claude.ai automatically summarizes earlier messages (paid plans with Code Execution enabled), and detail is compressed. Restart, summarize or persist (section 7)
4 Knowledge has a training boundary: a cutoff date. Connect a current source, turn on web search or use Research
5 Configured procedures still produce varied outputs: even a Skill reduces variance but does not remove it. Keep review in the workflow

3. Core entry points

Task Entry point
One-off question or quick task, no plan to reuse Chat
Recurring work with stable context Project
Output is a deliverable the recipient will open and read Artifact
Deep multi-source investigation or synthesis Research
  • Chat: the default, unstructured conversation. It is saved to history and can be continued, and Memory plus past-chat search can carry some context forward. It lacks a Project's deliberate persistence, standing instructions and curated knowledge base. Warning sign: you paste the same background paragraph into every new Chat.
  • Project: a persistent workspace with three parts:
    • Standing instructions: how Claude should behave in every conversation of the space.
    • Knowledge base: documents uploaded once.
    • Conversation history: its own list, separate from global history. Conversations in a Project share the instructions and knowledge base, but not context with each other.
  • Artifact: a separate, editable block next to the chat; for documents, tables, reports, code. Use inline replies for answers you act on in the conversation.
  • Research: multi-step searches over many sources, synthesized (paid plans). Plain Chat can also search the web via a per-chat toggle on all plans; on Team and Enterprise an Owner must first enable web search for the workspace. Quick lookups: web search in Chat; deep work: Research.

When is a Project worth building? Ask three questions: does the task recur, is the background context stable, is the output format consistent? Two or more "yes" = build the Project. Setup time is recovered within two or three sessions.

Example: a coordinator wrote weekly status reports in a new Chat every Monday (40 minutes, about 12 of them context loading). With a Project (team and stakeholders in the knowledge base, format and escalation rules in instructions) the session takes 25 minutes. Same quality; the "setup tax" is gone.

4. Capability layer

Entry points decide where you work; the capability layer decides what Claude can do there. The layers are independent; use any combination.

Layer Solves
Projects carry context background knowledge and standing instructions for a workstream
Skills define procedures how a task is executed, consistently
Code Execution verifies computations the result must be correct, not merely plausible
Memory persists continuity facts carry across sessions without re-entry

Skills

  • Reusable procedures. Built-in Skills cover Excel, Word, PowerPoint and PDF work; custom Skills can be added in settings.
  • Skills live at the account level, not inside one Project; Claude invokes them automatically when relevant, in or out of a Project.
  • Skills reduce variance but do not eliminate it: the prose still differs each run.
  • Trust evaluation: a Skill can reach whatever you give Claude access to. Review a third-party Skill's source and requested permissions first. Anthropic-provided and organization-approved Skills are the lower-risk start.

Memory

  • Stores work-relevant facts: role context, format preferences, frequent collaborators, standing constraints.
  • Curate it: review at least monthly for active users, delete or update stale entries, keep only what really recurs. A stale memory can mislead; accuracy matters more than volume.
  • Project-scoped Memory keeps contexts separate per Project (client A does not leak into client B). Use separate Projects for separate workstreams.
  • Incognito mode keeps a session out of Memory and chat history (standalone chats, outside Projects). It does not override your organization's data retention.
  • Memory import from other AI platforms was experimental as of June 2026 (documented for Free, Pro, Max, Team; not Enterprise). Fallback: add key facts to Memory manually in settings, not into a Project's knowledge base.

Worked scenario: an analyst's monthly regulatory report went from 65 to 30 minutes per session after moving context and format instructions into a Project, prior reports into the knowledge base, the output format into a Skill and the numeric calculations into Code Execution. Verification still ran; no errors in months 3 to 8.

Questions to find the layer: what is the same every time (standing instructions + Skill)? what reference material recurs (knowledge base)? what must be computed correctly (Code Execution)? what to carry across sessions (Memory)?

Contract review mapping:

Component Layer
"Flag any clause that departs from the playbook and explain it in one sentence" Standing instructions
The company contract playbook; this cycle's contracts Knowledge base
A procedure that extracts flagged clauses into the standard report template Skill
Financial exposure from a penalty clause with a variable rate Code Execution

Standing instructions define how Claude behaves; the knowledge base defines what Claude knows. Both live in the Project.

5. Choosing models: Haiku, Sonnet, Opus

The layer decides what Claude does; the model decides how well, and at what cost in speed.

Task profile Model
Routine, structured extraction or classification at volume Haiku: fastest and most efficient; classification, extraction, formatting, simple summaries
Most professional drafting, synthesis, analysis Sonnet: best combination of speed and intelligence (docs); everyday and simpler work
Complex judgment, high-stakes output, ambiguous or multi-layered inputs Opus: higher capability, latency moderate (docs); client deliverables, strategy, multi-source synthesis
  • If quality falls short on a complex task, move up to Opus; if the task is structured and speed and volume matter, consider Haiku.
  • On metered or usage-budgeted plans (including API) a more capable tier also costs more per call. On the claude.ai subscription, treat speed and usage headroom as the proxy for cost.
  • The model picker, default model and auto-switching vary by plan and change over time.
  • Note from the course, checked in section 11: by June 2026 the family also has a fourth tier above Opus (Fable). The course says the certification pins the three-tier Haiku/Sonnet/Opus frame and Fable is not exam-relevant; I could not verify that against an official exam guide. Where to start: the course here says Sonnet, but the official docs say if unsure, start with Opus; this path follows the docs (standard rule in section 11). See Topic 4 for the four-model view.

6. Context limits and conversation hygiene

  • The context window fills as messages and files accumulate; claude.ai then summarizes earlier messages (full history stays available for reference). Instructions from the first 10 minutes may not be followed 90 minutes later because detail is compressed, not because Claude ignores you.
  • Signs a conversation needs intervention: it stops following earlier instructions; it answers only the latest exchange; accuracy drops in ways that fit missing early context.
таблицю можна гортати вбік →
Response What When
Restart New conversation; the Project's instructions and knowledge base carry over, the thread does not The session drifted beyond recovery, or a new task starts
Summarize Ask Claude for a summary of decisions, work in progress and open questions; paste it into the new conversation You want thread continuity without the degraded window
Persist Save to Memory or update the Project knowledge base Information needed in all future sessions
  • Usage limits run on several windows: a short rolling session window plus weekly limits on paid plans across models (on some plans a separate weekly pool for Fable); the session window resets every five hours. Plan ahead: split big tasks, save interim progress to the knowledge base, restart from a summary instead of extending one session forever.

8. Module quiz

The source prints the questions without the key; the answers below are derived from the module's logic.

  1. Weekly inventory reconciliation (unchanged threshold document, new file each week, formatted exception report) → B: a Project with the threshold document in the knowledge base, standing instructions for the format and Code Execution for the comparison.
  2. Compound interest with five variables, most trustworthy result → C: Code Execution returns a verified result.
  3. 500 vendor agreements, low/medium/high by a clear rubric, one session → C: Haiku for structured classification at volume.
  4. Two-hour session, responses stopped reflecting the framework defined at the start → C: start a new conversation and paste a summary of decisions and progress (a bigger model does not fix compressed context).
  5. Two clients, keep Client A out of Client B → C: separate Projects with Project-scoped Memory (Incognito removes all persistence, it does not separate clients).

9. Five takeaways

  1. Select the entry point before writing the prompt.
  2. Four layers, four problems: Projects carry context, Skills define procedures, Code Execution verifies computation, Memory persists continuity.
  3. Model tiers are a speed-capability trade-off.
  4. Context is a budget: restart, summarize or persist.
  5. Variation is inherent, review is structural: even configured Skills vary run to run.
