Topic 6 of 11: Claude Code 101 (English)

Claude Certified Architect path. Topic 6: Claude Code as an agent: the loop, permissions, install, the Explore → Plan → Code → Commit workflow, context, code review, CLAUDE.md, subagents, Skills, MCP, hooks. Unknown words are in the cards: English words. Source: Anthropic course "Claude Code 101". Section 10 (Skills) and section 13 (checks) come from the official Claude Code docs (checked 2026-11-16). Commands, modes and settings change between versions; verify in your install.

1. What is Claude Code

  • Claude Code is an agentic coding tool: it understands your codebase, edits your files, runs commands and connects to your developer tools.
  • It runs in the terminal, VS Code, the Claude Desktop app, on the web and in JetBrains IDEs.
  • Difference from Claude.ai: Claude Code has direct access to your files, terminal and codebase. You do not copy code back and forth; it goes in and does the work.
  • The key difference: Claude Code works as an AI agent.

What is an agent? Software that can interact with its environment and perform actions to complete a goal. At its core: a language model running in a loop, with access to tools, external services or even other agents.

What it does in practice:

  • reads and understands the codebase (explain a feature, trace a bug)
  • edits files across the project (refactor a function and update every reference)
  • runs terminal commands (build, tests, install packages) and uses the output to decide the next step
  • searches the web for documentation and API references

Three things to keep in mind:

  1. The context window is its working memory: large, but not everything at once. Claude finds strategic ways to locate answers without loading the whole codebase.
  2. You control permissions: ask before every action, or let it run with a background safety check.
  3. It can make mistakes: misread your intent, add a bug, over-engineer. Stay in the loop.

2. How Claude Code works

The agentic loop

  1. You enter a prompt.
  2. Claude gathers context by working with the model, which returns text or a tool call Claude Code can execute.
  3. It takes action (edits a file, runs a command).
  4. It verifies the result against what your prompt asked for.
  5. If it is done, it stops and waits. If not, it loops back until the result is complete and verifiable.

Throughout the loop you can add context, interrupt or steer.

Context, tools, permissions

  • Context: the window holds conversation, file contents and command output. At the limit, Claude Code compacts the conversation automatically (summarizes, drops what it can).
  • Tools are the backbone: most assistants take text in and return text out; tools let Claude Code decide when to execute code (read a file, search the web, and more) and use the output.
  • Permission modes:
Mode What happens
Manual Asks before editing a file or running a shell command
Auto-accept (docs: Accept edits) File edits and common filesystem commands (mkdir, mv, rm) run without asking; other commands still ask
Plan Reads files and runs shell commands to explore, does not edit source, builds a plan first
Auto Works without routine prompts; a classifier in the background screens actions, aiming to block irreversible, destructive or out-of-environment ones. If blocked, Claude usually finds a safer way or asks

Which mode a new session starts in depends on your version and settings. Everything is configurable in the settings file. Be careful skipping permissions: a mistake becomes harder to catch.

Recap: an agentic loop, a managed context window, tools and configurable permissions: that is what makes it different from a chat window.

3. Installing Claude Code

  • Terminal: on macOS, Linux or WSL use the curl installer (Homebrew also works, but does not auto-update by default). On Windows: PowerShell Invoke-RestMethod, CMD curl, or winget (also no auto-update). Then run claude in your project directory. If the command is missing, restart the terminal.
  • First run: pick a theme and sign in with a Claude account (Pro, Max, Ultra, Team or Enterprise) or an API key. Under an Enterprise org choose that option.
  • Access scope: whatever directory you run claude in, it can access that directory and all subfolders.
  • VS Code: install the "Claude Code" extension by Anthropic (blue check), maybe restart, open from the command palette (Ctrl/Cmd+Shift+P, "Claude Code Open in New Tab") or the logo. Almost the same as the terminal.
  • JetBrains: install the plugin from the Marketplace, restart; the logo opens a terminal pane next to your editor.
  • Desktop: the Code tab: work in a chosen folder, change permissions, even use a cloud environment.
  • Web: claude.ai/code; GitHub repositories only.

Which to use? Terminal: newest features ship there first. IDE: nearly identical, closer to the editor. Desktop: good for letting Claude run in the background. Web: remote work on a GitHub repository.

4. Your first prompt

  • Switch modes with Shift + Tab. There is no right answer; pick what you are comfortable with.
  • Plan mode reads files and researches your idea without editing source, asks clarifying questions, then returns a detailed plan it can execute. Best for complex multi-step features and for a safe code review.
  • Example: "My app needs dark mode across the whole app. Add a toggle in the header and find a contrast colour that works with the existing light theme." Review the plan, accept it, and let Claude work; at the end you can see what it did and why.
  • Be as descriptive as you can in the prompt.

5. The Explore → Plan → Code → Commit workflow

If you take one thing from the course, take this. Without it people jump straight to code and correct course later.

Step What happens
Explore Gives Claude the context it needs. Use plan mode (or the Explore subagent outside plan mode for a codebase summary)
Plan A plan of action Claude later measures success against. The best place to course-correct: before any code exists
Code The back and forth. Approve the plan; permission mode decides how much it asks
Commit Test it yourself, run a subagent code reviewer, then have Claude write the commit message in your style

Explore/Plan example: "Add WebP conversion to our image upload pipeline. Figure out where it should happen, whether we need new dependencies, and how to approach it."

Tips for the Code step:

  • Define success criteria: Claude needs to know what "correct" looks like. Put it in the plan.
  • Add tools: for a web UI, the Claude in Chrome extension lets Claude drive a browser tab and test the UI.
  • Include a test suite it can validate against. Make sure tests are a reliable source of truth (no false positives).
  • If Claude keeps hitting the same issue, ask it to save the solution to CLAUDE.md.

Why a subagent reviewer: it gets fresh eyes and does not carry the bias of the main session.

6. Context management

  • Everything takes space: every file read, command run, message sent.
  • When it fills: automatic compaction summarizes key details and removes unneeded tool results. It can lose details.
таблицю можна гортати вбік →
Command Does Use when
/compact Compacts everything up to now, keeps a memory of the work You are on one feature and nearing the limit, but must continue
/clear Wipes everything, a fresh session with no memory You start a new feature; old conversation would bias it
/context Shows size, biggest categories and a visual breakdown You want to see what is eating the window

Things to remember across sessions go in CLAUDE.md.

Saving context:

  • Be specific. A vague prompt looks cheaper but forces Claude to explore and reason more, which costs more context.
  • Manage MCP servers. By default a server loads only tool names and instructions; full details load when needed. Each server still takes space, so turn off ones unrelated to the project.
  • Use subagents: separate context window, only a summary comes back ("where are the auth endpoints?").

7. Code review

The session that wrote the code is not the best judge of it. Look at the change yourself, then have Claude review it again from a clean context.

  • /diff opens an interactive viewer of uncommitted changes (and what each Claude turn changed). Arrows move between files, Enter opens one. /diff and /code-review need a git repository. On another VCS, read the change in your own tool and ask Claude in plain words to review the files it touched; /rewind still works.
  • What deserves a second look every time:
    1. Changes you did not ask for (an edited config value, a rewritten helper).
    2. Weaker tests (skipped, deleted, loosened until they pass).
    3. New packages and hard-coded values (a dependency for one function, a URL or key in code).
  • Undo a wrong change: /rewind (or press Esc twice on an empty prompt), pick the prompt, choose Restore code and conversation. Files changed by shell commands (such as a package install) are not rolled back.
  • /code-review is the clean-context second reviewer: it reports, edits nothing unless asked, runs in the background (seconds to minutes) and counts against your usage. You can also ask in plain words. Effort levels: /code-review low (fewer, most confident findings), high (wider net, less sure findings). The level is remembered.

Exercise 1 (compare summary with diff): Claude's summary of a signup-form change is true ("validation added, tests pass") but 8 files changed. Three deserve scrutiny: the test file (assertions weakened), src/config.ts (hard-coded URL), and the new dependency in package.json/lock file. Lesson: a true summary can still omit changes worth scrutinizing. (The exact flagged set is not in the source; this is derived from the example.)

Sorting findings: Fix now, Ask why, Leave it.

  • Fix now: a real problem that matters. Ask why: you cannot verify it or it looks off; a reviewer reading cold can be wrong. Leave it: real but small; batch for later.
  • To ask why, quote the finding and ask Claude to check again: "You reported that isValidEmail doesn't trim, but line 4 calls trim(). Check again."
  • When asking for a fix, ask for evidence: "Fix the first finding, restore the original assertion, run the tests and show me the output."
  • If a fix grows into a large change, review again.

Exercise 2 (the four findings), answers derived from the code shown:

таблицю можна гортати вбік →
# Finding Pile
1 Test skipped and assertion weakened Fix now
2 isValidEmail doesn't trim Ask why (the code already calls trim(): false alarm)
3 API_URL hard-coded to localhost:3000 Fix now (production would hit a dev address)
4 Hex colour instead of --color-danger Leave it (style only)

When to review closely: a one-line change needs a glance. Use human + Claude review when the change is bigger than you can hold in your head, touches something sensitive or destructive, or before handing it to a teammate.

Not the same as Claude Code Review: that is a separate team product (an org Owner enables it for a GitHub repo and it posts on pull requests). Nothing in this lesson needs it.

8. The CLAUDE.md file

  • Problem: without it, every session starts fresh: Claude re-explores, rediscovers dependencies and features, and makes assumptions.
  • What it is: a Markdown file in the project root, read automatically at the start of every session, added to your prompt. An onboarding script for the codebase.
  • Example content: project (Next.js 15, App Router, Tailwind, Drizzle), commands (pnpm dev, pnpm test, pnpm lint), code style (2 spaces, named exports, API routes in app/api/).
  • For teams: commit it. Project-level CLAUDE.md in the root is shared. User-level CLAUDE.md in your config folder is personal and applies to all projects.

Tips:

  • Save corrections to memory: if you keep correcting the same thing, ask Claude to save the rule.
  • Reference docs with @: @README.md pulls that file in.
  • Start without one, see where you keep correcting the model, keep it compact, then run /init to generate one.

Facts that are always true belong in CLAUDE.md. Procedures belong in a Skill (section 10).

9. Subagents

  • Claude can delegate to subagents that run component tasks in parallel, each in its own isolated context window.
  • How it works: Claude spawns a subagent ("explore this codebase"), it does all the exploration in its own context, then returns only a summary. You get the answer without the journey cluttering the main context.
  • Create one: a Markdown file with YAML frontmatter. Easiest: let Claude generate it. "Create a code-reviewer subagent in .claude/agents/ that reviews code for bugs and readability. Make it read-only."
  • Where: .claude/agents/ = this project; ~/.claude/agents/ = all projects. If the folder did not exist when the session began, restart Claude Code.
  • Customization: persistent memory across conversations; preload skills with the skills key (the entire skill is loaded into the subagent, unlike in the main conversation).

10. Skills (from the official Claude Code docs)

The course material only pointed here ("add skills from the official docs"); this section is built from the Claude Code Skills page.

  • A skill is a folder with a SKILL.md: instructions Claude loads when relevant, or that you invoke directly with /skill-name. Old .claude/commands/ files still work and have been merged into skills.
  • Skills hold procedures, CLAUDE.md holds facts. If a CLAUDE.md section has grown into a procedure, move it to a skill (the body only loads when used).

Where skills live:

Scope Path
Enterprise .claude/skills/<name>/SKILL.md in the managed settings directory
Personal ~/.claude/skills/<name>/SKILL.md (all your projects)
Project .claude/skills/<name>/SKILL.md (commit to share)
Plugin <plugin>/skills/<name>/SKILL.md, used as /plugin-name:skill-name

Same name in several places: enterprise beats personal, personal beats project; plugin skills are namespaced, so they do not conflict. Claude Code watches the skill folders, so edits apply within the session.

Anatomy: YAML frontmatter between --- lines, then Markdown instructions. All fields are optional; description is the recommended one.

---
name: summarize-changes
description: Summarizes uncommitted changes and flags risky ones. Use when the user asks what changed or wants a commit message.
allowed-tools: Bash(git diff *) Bash(git status *)
---
Summarize the changes, then list any risks.
Field Purpose
name Name in the / menu (defaults to the folder name)
description What it does and when to use it: this is how Claude decides to load it
disable-model-invocation: true Only you can invoke it (use for side effects like /deploy)
user-invocable: false Hidden from the / menu; only Claude loads it (background knowledge)
allowed-tools Tools pre-approved while the skill runs; does not restrict other tools
context: fork (+ agent) Run the skill in a subagent that does not see your conversation
model, effort Override for that turn
paths Auto-load only when matching files are in play
hooks Hooks registered while the skill is used

How loading works (progressive disclosure): the descriptions of all skills sit in context so Claude knows what exists; the full body loads only when the skill is used. description + when_to_use is cut at 1,536 characters in the list: put the key use case first. Once loaded, the content stays in the conversation, so write standing instructions, not one-off steps. After compaction the latest invocation of each skill is re-attached (up to 5,000 tokens each, 25,000 combined).

Supporting files: keep SKILL.md under about 500 lines and put detail in reference.md, examples.md or scripts/ (scripts are executed, not loaded). Reference them from SKILL.md so Claude knows when to read them.

Arguments and dynamic context: $ARGUMENTS, $0/$1, ${CLAUDE_SKILL_DIR}. A line like !`git diff HEAD` runs a command before the skill is sent and inserts its output.

Skills vs the other tools:

Tool Best for
CLAUDE.md Always-on facts about the project
Skill A reusable procedure loaded on demand
Subagent An isolated worker with its own context (a skill can run in one with context: fork)
Hook Something that must happen every time (deterministic)
MCP Connecting external tools and data (pair it with a skill that teaches how to use it well)

Control access: deny all skills with Skill in deny rules; allow or deny one with Skill(name). Bundled skills include /code-review, /debug, /loop, /claude-api, /skill-doctor (reports the context cost of your skills).

11. MCP

  • Model Context Protocol is an open standard to connect Claude Code to external tools and data (databases, productivity apps, public repos). Claude decides on its own when to use them.
  • Examples: a Linear MCP server to pull issue details; Context7 for up-to-date library docs.
  • Add a server: claude mcp add. Two main types: HTTP (remote, hosted by the provider) and stdio (a local process on your machine).
  • Manage: /mcp inside a session shows what is connected, status, and lets you disable servers.
  • Scopes:
Scope Meaning
Local Current project only, just you (the default)
User All your projects
Project .mcp.json committed to the repo; the whole team gets the same servers
  • Context cost: each connected server adds tool names and instructions even when idle. Run /mcp and disable unused ones. Tool search is on by default: full tool definitions stay out of context until needed.
  • Prefer a CLI when one exists (gh, aws): it adds no per-tool listing, so it is more context-efficient.
  • Pair an MCP server with a Skill that teaches Claude to use its tools well.

12. Hooks

  • Hooks run commands at points in Claude Code's lifecycle. Unlike everything else here they are deterministic: they always run.
  • Why: "run Prettier after every edit" in CLAUDE.md works most of the time; a hook makes it happen every time.
  • Use cases: auto-format after edits; log every command for compliance; block dangerous operations; notify you when Claude finishes.
  • Configured in settings.json: pick an event, optionally a matcher (which tools), and a command.
Event Fires
PreToolUse Before a tool call (can block)
PostToolUse After a tool call completes
UserPromptSubmit When you submit a prompt, before Claude processes it
Stop When Claude finishes responding
Notification When Claude sends a notification
  • Auto-format example: PostToolUse with matcher Edit|Write, a command that checks the file extension and runs Prettier, gofmt, etc.
  • Blocking with PreToolUse: the hook gets the tool name and input as JSON on stdin. Exit code 0 = proceed. Exit code 2 = block; stderr is fed back to Claude so it can adjust. Any other code = non-blocking error, shown to you, nothing stops.
  • Share with the team: hooks in .claude/settings.json are project-level and can be committed. Use CLAUDE_PROJECT_DIR to reference scripts so they work from any working directory.
  • /hooks opens a read-only list so you can check a new hook appears.

If something must happen every time without fail, do not put it in a prompt. Put it in a hook.

15. Quiz questions from the course

1. Claude Code works as an AI agent. What is an AI agent? AI that takes action to complete goals. Wrong answers: a chatbot that answers in real time; an editor with autocomplete; a cloud service hosting your projects.

2. What happens when Claude Code reaches its context window limit? It automatically compacts your conversation to free up space. Wrong answers: it switches to a smaller model; it removes your oldest files; it stops and asks you to restart.

3. What is the recommended workflow for using Claude Code effectively? Explore → Plan → Code → Commit. Wrong answers: Code → Test → Deploy → Monitor; Write → Review → Merge → Ship; Prompt → Accept → Push → Repeat.

4. How does Claude Code use the CLAUDE.md file? It reads it automatically at the start of every session. Wrong answers: only after /init; once when the project is created; only when you ask.
