1. Чотири рішення

Ще до першого промпта чотири рішення визначають, наскільки добрим може вийти результат сесії:

  1. Точка входу (entry point): Chat, Project, Artifact чи Research.
  2. Шар можливостей (capability layer): Projects, Skills, Code Execution, Memory.
  3. Модель: Haiku, Sonnet чи Opus.
  4. Робота з контекстом: почати заново (restart), підсумувати (summarize) чи зберегти надовго (persist).

Від них залежить, чи нова сесія спирається на попередню роботу, чи щоразу доводиться все налаштовувати з нуля.

3. Основні точки входу

Завдання Точка входу
Разове питання чи швидке завдання, повторювати не плануєш Chat
Робота, що повторюється, зі сталим контекстом Project
Результат це документ, який отримувач відкриє й прочитає Artifact
Глибоке дослідження чи зведення даних із багатьох джерел Research
  • Chat це розмова за замовчуванням, без структури. Вона зберігається в історії, її можна продовжити, а Memory і пошук по минулих чатах переносять частину контексту. Але в ній нема того, що дає Project: цілеспрямованої сталості, постійних інструкцій і підібраної бази знань. Тривожна ознака: ти щоразу вставляєш у новий Chat той самий абзац із передісторією.
  • Project це постійний робочий простір із трьох частин:
    • Постійні інструкції (standing instructions): як Claude має поводитись у кожній розмові цього простору.
    • База знань (knowledge base): документи, завантажені один раз.
    • Історія розмов: власний список, окремо від загальної історії. Розмови всередині Project діляться інструкціями й базою знань, але контекстом одна з одною не діляться.
  • Artifact це окремий блок, який можна редагувати, поруч із чатом: для документів, таблиць, звітів, коду. Відповіді, з якими ти одразу щось робиш у розмові, лишай звичайним текстом чату.
  • Research шукає в кілька кроків по багатьох джерелах і зводить результат докупи (платні плани). Звичайний Chat теж уміє шукати в мережі: це перемикач у чаті, доступний на всіх планах; на Team і Enterprise власник спершу вмикає вебпошук для всієї організації. Швидко щось уточнити: вебпошук у Chat. Глибоке дослідження: Research.

Коли Project вартий зусиль? Постав три питання: чи завдання повторюється, чи передісторія стала, чи формат результату однаковий? Якщо «так» двічі чи тричі, створюй Project. Час на налаштування окупиться за дві-три сесії.

Приклад. Координаторка щопонеділка писала тижневий статус-звіт у новому Chat: 40 хвилин, із них близько 12 на те, щоб заново розповісти контекст. З Project (команда й стейкхолдери в базі знань, формат і правила ескалації в інструкціях) сесія триває 25 хвилин. Якість та сама, а «податок на налаштування» зник.

4. Шар можливостей

Точка входу визначає, де ти працюєш. Шар можливостей визначає, що Claude вміє на цьому місці. Шари незалежні, їх можна комбінувати як завгодно.

Шар Яку проблему розв'язує
Projects несуть контекст передісторія й постійні інструкції для цілого напряму роботи
Skills задають процедури як виконувати завдання, щоразу однаково
Code Execution перевіряє обчислення результат має бути правильним, а не лише правдоподібним
Memory зберігає тяглість факти переходять між сесіями без повторного введення

Skills

  • Це багаторазові процедури. Вбудовані Skills працюють з Excel, Word, PowerPoint і PDF; свої можна додати в налаштуваннях.
  • Skills належать акаунту, а не окремому Project (так каже курс; офіційного підтвердження я не знайшов); Claude викликає їх сам, коли доречно.
  • Skills зменшують розкид результатів, але не усувають його: формулювання щоразу трохи інші.
  • Перевіряй, кому довіряєш. Skill бачить усе, до чого ти дав Claude доступ у сесії. Перш ніж вмикати чужий Skill, переглянь його джерело й дозволи, яких він просить. Skills від Anthropic і ті, що схвалила твоя організація, безпечніший початок.

Memory

  • Зберігає робочі факти: роль, уподобання щодо формату, постійні співрозмовники, сталі обмеження.
  • Доглядай за нею. Переглядай не рідше разу на місяць, видаляй чи оновлюй застаріле, лишай тільки те, що справді повторюється. Застаріла пам'ять вводить в оману; точність важливіша за обсяг.
  • Пам'ять на рівні Project тримає контексти окремо для кожного Project: клієнт A не потрапляє в сесії клієнта B. Різні напрями роботи веди в різних Project.
  • Режим інкогніто (Incognito) тримає чат поза Memory й історією (стосується окремих чатів, не Project). Він не скасовує правил збереження даних у твоїй організації.
  • Імпорт пам'яті з інших AI-платформ станом на червень 2026 був експериментальним (за курсом: Free, Pro, Max, Team, без Enterprise). Якщо автоматичного імпорту нема, додай ключові факти в Memory вручну в налаштуваннях, а не в базу знань Project.

Приклад. Щомісячний регуляторний звіт аналітикині скоротився з 65 до 30 хвилин за сесію. Контекст і формат пішли в Project, минулі звіти в базу знань, формат результату в Skill, а числові розрахунки в Code Execution. Перевірка лишилась, і з 3-го по 8-й місяць помилок не знайшли.

Як вирішити, який шар потрібен: що щоразу однакове (постійні інструкції + Skill)? які довідкові матеріали повторюються (база знань)? що має бути пораховане правильно (Code Execution)? що переносити між сесіями (Memory)?

Перевірка договорів:

Компонент Шар
«Познач кожен пункт, що відхиляється від playbook, і поясни одним реченням» Постійні інструкції
Playbook компанії; договори цього циклу База знань
Процедура, що витягає позначені пункти в стандартний шаблон звіту Skill
Фінансові втрати за штрафним пунктом зі змінною ставкою Code Execution

Постійні інструкції визначають, як Claude поводиться. База знань визначає, що Claude знає. Обидві лежать у Project.

5. Вибір моделі: Haiku, Sonnet, Opus

Шар визначає, що Claude робить. Модель визначає, наскільки добре і з якою швидкістю.

Який тип завдання Яка модель
Рутинне структуроване витягування чи класифікація у великих обсягах Haiku: найшвидша й найекономніша; класифікація, витяг даних, форматування, прості резюме
Більшість професійного письма, підсумків і аналізу Sonnet: найкраще поєднання швидкості й інтелекту (за документацією); повсякденна й простіша робота
Складне судження, високі ставки, неоднозначні чи багатошарові вхідні дані Opus: потужніша, затримка помірна (за документацією); результати для клієнтів, стратегія, підсумки за багатьма джерелами
  • Якщо якість складного завдання недотягує, піднімись до Opus. Якщо завдання структуроване, а важливі швидкість і обсяг, розглянь Haiku.
  • На тарифах із лічильником чи бюджетом (зокрема API) потужніша модель ще й коштує більше за виклик. У підписці claude.ai швидкість і запас до ліміту слугують замінником вартості.
  • Перелік моделей у меню, модель за замовчуванням і автоматичне перемикання залежать від плану й змінюються з часом.
  • Примітка курсу, перевірена в розділі 10: у червні 2026 є й четвертий рівень над Opus (Fable). Курс каже, що сертифікація тримається триярусної схеми Haiku/Sonnet/Opus, а Fable для іспиту не важливий; підтвердити це офіційним посібником я не зміг. З чого починати: курс тут каже Sonnet, але офіційна документація каже «якщо вагаєшся, починай з Opus». Цей шлях іде за документацією (єдине правило в розділі 10). Погляд на чотири моделі дивись у Темі 4.

6. Ліміти контексту й гігієна розмови

  • Контекстне вікно заповнюється повідомленнями й файлами; тоді claude.ai стискає ранні повідомлення (повна історія лишається для довідки). Інструкції з перших 10 хвилин можуть не виконуватись через 90 не тому, що Claude тебе ігнорує, а тому, що деталі при стисканні губляться.
  • Ознаки, що розмову треба рятувати: вона перестала виконувати раніші інструкції; відповідає лише на останнє повідомлення; точність падає так, ніби бракує початку розмови.

Плануй наперед: ділити великі завдання на частини, зберігати проміжний результат у базі знань і перезапускати з підсумку, а не розтягувати одну сесію до безкінечності.

8. Тест модуля

Джерело дає питання без ключа; відповіді нижче я вивів із логіки модуля.

  1. Щотижнева звірка запасів (документ із порогами не змінюється, щотижня новий файл, звіт про винятки у фіксованому форматі) → B: Project із документом порогів у базі знань, постійними інструкціями про формат і Code Execution для порівняння.
  2. Складні відсотки з п'ятьма змінними; який підхід найнадійніший → C: Code Execution повертає перевірений результат.
  3. 500 договорів постачальників, low/medium/high за чітким критерієм, одна сесія → C: Haiku для структурованої класифікації у великому обсязі.
  4. Дві години в одній сесії, відповіді перестали враховувати рамку, задану на початку → C: нова розмова з підсумком рішень і прогресу (більша модель не виправить стиснутий контекст).
  5. Два клієнти, контекст A не має потрапити до B → C: окремі Project із пам'яттю на рівні Project (Incognito прибирає будь-яку сталість, а не розділяє клієнтів).

9. П'ять висновків

  1. Обирай точку входу до промпта.
  2. Чотири шари, чотири проблеми: Projects несуть контекст, Skills задають процедури, Code Execution перевіряє обчислення, Memory зберігає тяглість.
  3. Рівні моделей це компроміс між швидкістю й потужністю.
  4. Контекст це бюджет: restart, summarize або persist.
  5. Різнобій у відповідях неминучий, перевірка обов'язкова: навіть налаштовані Skills щоразу дають трохи різне.

Питання для самоперевірки: (1) Які чотири рішення на початку сесії? (2) Які три умови, з яких двох досить для Project? (3) Чим постійні інструкції відрізняються від бази знань? (4) Чому довга сесія перестає виконувати ранні інструкції? (5) Коли restart, коли summarize, коли persist? (6) Яка модель для 800 рутинних класифікацій, а яка для аналізу для ради?

Sonnet як звична стартова модель Відрізняється від офіційної поради: документація каже «if unsure, start with Opus 5.5». Дивись Тему 4
«Сертифікація тримається триярусної схеми; Fable для іспиту не важливий» Не вдалося підтвердити (офіційного посібника іспиту не знайшов; сторонні сайти називають лише п'ять доменів і їхні ваги). Це власне твердження курсу
Відповіді тесту й вправи Ключа в джерелі нема; відповіді виведено, і вони не суперечать перевіреним фактам (наприклад, Q5 збігається з окремою пам'яттю Project)

Єдине правило для цього шляху: починай з Opus; для повсякденної чи простішої роботи йди до Sonnet, для великих обсягів із чутливістю до затримки (класифікація, витяг, маршрутизація) до Haiku; піднімайся до Fable, коли Opus на вищому effort усе ще не дотягує.
