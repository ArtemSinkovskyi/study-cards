Шлях Claude Certified Architect. Тема 3: чотири рішення на початку кожної сесії Claude. Незнайомі слова є в картках: English words. Read in English · Попередня: Тема 2 · Наступна: Тема 4 Джерело: курс Anthropic Associate, модуль 1 «Claude Platform & Model Foundations». Поведінка продукту станом на червень 2026; сам курс радить звіряти з актуальною документацією Anthropic.

1. Чотири рішення

До першого промпта чотири рішення задають стелю якості сесії:

  1. Entry point (точка входу): Chat, Project, Artifact або Research.
  2. Capability layer (шар можливостей): Projects, Skills, Code Execution, Memory.
  3. Модель: Haiku, Sonnet чи Opus.
  4. Керування контекстом: restart, summarize чи persist.

Вони визначають, чи сесії надбудовуються на попередніх, чи щоразу все налаштовується заново.

2. П'ять поведінкових властивостей Claude

# Властивість Що робити
1 Відповіді різняться: те саме питання двічі дає дві відповіді. Вивід породжується ймовірністю, а не береться з бази. Закладіть варіативність і додайте перевірку в процес
2 Впевнений тон не ознака точності: вигадана статистика звучить так само певно, як перевірена. Виробіть звички перевірки
3 Контекст це бюджет: у кожної розмови є ліміт робочої пам'яті. Біля ліміту claude.ai автоматично підсумовує ранні повідомлення (платні плани з увімкненим Code Execution), і деталі стискаються. Restart, summarize чи persist (розділ 7)
4 Знання мають межу навчання: дата cutoff. Підключіть актуальне джерело, увімкніть вебпошук чи Research
5 Налаштовані процедури теж дають різний вивід: навіть Skill зменшує розкид, але не прибирає. Лишайте перевірку в процесі

3. Основні точки входу

Завдання Точка входу
Разове питання чи швидке завдання, без повторного використання Chat
Повторювана робота зі сталим контекстом Project
Результат це документ, який отримувач відкриє й прочитає Artifact
Глибоке дослідження чи синтез із багатьох джерел Research
  • Chat: типова, неструктурована розмова. Зберігається в історії й може продовжуватись, а Memory і пошук по минулих чатах переносять частину контексту. Йому бракує свідомої сталості Project, постійних інструкцій і впорядкованої бази знань. Тривожний знак: щоразу вставляєте в новий Chat той самий абзац передісторії.
  • Project: постійний робочий простір із трьох частин:
    • Standing instructions (постійні інструкції): як Claude діє в кожній розмові цього простору.
    • Knowledge base (база знань): документи, завантажені раз.
    • Історія розмов: власний список, окремо від глобальної. Розмови в Project ділять інструкції та базу знань, але не ділять контекст між собою.
  • Artifact: окремий редагований блок поруч із чатом; для документів, таблиць, звітів, коду. Відповіді, за якими дієте тут-таки в розмові, лишайте в тексті чату.
  • Research: багатокрокові пошуки по багатьох джерелах із синтезом (платні плани). Звичайний Chat теж шукає в інтернеті через перемикач на чат на всіх планах; на Team і Enterprise Owner спершу вмикає вебпошук для робочого простору. Швидкі довідки: вебпошук у Chat; глибока робота: Research.

Коли Project вартий створення? Три питання: чи завдання повторюється, чи передісторія стала, чи формат виводу сталий? Двох і більше «так» досить. Час налаштування повертається за дві-три сесії.

Приклад: координаторка щопонеділка писала тижневий статус-звіт у новому Chat (40 хвилин, близько 12 на завантаження контексту). З Project (команда й стейкхолдери в базі знань, формат і правила ескалації в інструкціях) сесія триває 25 хвилин. Якість та сама; «податок на налаштування» зник.

4. Capability layer

Точки входу визначають, де ви працюєте; шар можливостей визначає, що Claude вміє там. Шари незалежні; комбінуйте як треба.

Шар Розв'язує
Projects несуть контекст передісторія й постійні інструкції для напряму роботи
Skills задають процедури як виконувати завдання, однаково щоразу
Code Execution перевіряє обчислення результат має бути правильним, а не лише правдоподібним
Memory зберігає тяглість факти переходять між сесіями без повторного введення

Skills

  • Багаторазові процедури. Вбудовані Skills працюють з Excel, Word, PowerPoint і PDF; власні можна додати в налаштуваннях.
  • Skills живуть на рівні акаунта, а не всередині одного Project; Claude викликає їх автоматично, коли доречно, у Project чи поза ним.
  • Skills зменшують розкид, але не прибирають його: текст щоразу трохи інший.
  • Оцінка довіри: Skill має доступ до всього, що ви дали Claude в сесії. Перед увімкненням стороннього Skill перегляньте джерело й запитані дозволи. Skills від Anthropic і схвалені організацією це безпечніший початок.

Memory

  • Зберігає робочі факти: роль, уподобання щодо формату, постійні співрозмовники, сталі обмеження.
  • Доглядайте за нею: переглядайте не рідше разу на місяць для активних користувачів, видаляйте чи оновлюйте застаріле, лишайте лише те, що справді повторюється. Застаріла пам'ять може ввести в оману; точність важливіша за обсяг.
  • Project-scoped Memory тримає контексти окремо для кожного Project (клієнт A не потрапляє в сесії клієнта B). Різні напрями робіть у різних Project.
  • Incognito mode тримає сесію поза Memory та історією чатів (окремі чати, поза Project). Він не скасовує політику збереження даних вашої організації.
  • Імпорт пам'яті з інших AI-платформ станом на червень 2026 був експериментальним (задокументований для Free, Pro, Max, Team; не для Enterprise). Запасний шлях: додати ключові факти в Memory вручну в налаштуваннях, а не в базу знань Project.

Приклад: щомісячний регуляторний звіт аналітикині скоротився з 65 до 30 хвилин на сесію після того, як контекст і формат пішли в Project, минулі звіти в базу знань, формат виводу в Skill, а числові розрахунки в Code Execution. Перевірка лишилась; помилок у місяці 3-8 не було.

Питання, щоб знайти шар: що однакове щоразу (постійні інструкції + Skill)? який довідковий матеріал повторюється (база знань)? що має бути обчислене правильно (Code Execution)? що переносити між сесіями (Memory)?

Перегляд договорів:

Компонент Шар
«Познач будь-який пункт, що відхиляється від playbook, і поясни одним реченням» Постійні інструкції
Playbook компанії; договори цього циклу База знань
Процедура, що витягує позначені пункти у стандартний шаблон звіту Skill
Фінансова експозиція зі штрафного пункту зі змінною ставкою Code Execution

Постійні інструкції визначають, як поводиться Claude; база знань визначає, що Claude знає. Обидві живуть у Project.

5. Вибір моделі: Haiku, Sonnet, Opus

Шар визначає, що робить Claude; модель визначає, наскільки добре і якою ціною швидкості.

Профіль завдання Модель
Рутинне структуроване витягування чи класифікація у великому обсязі Haiku: найшвидша й найефективніша; класифікація, витяг, форматування, прості резюме
Більшість професійного складання, синтезу, аналізу Sonnet: збалансована; відправна точка для більшості роботи зі знаннями
Складне судження, високі ставки, неоднозначні чи багатошарові входи Opus: вища здатність, повільніша; клієнтські результати, стратегія, синтез із багатьох джерел
  • Якщо якість у складному завданні недотягує, підніміться до Opus; якщо завдання структуроване, а важливі швидкість і обсяг, розгляньте Haiku.
  • На планах із лічильником чи бюджетом використання (включно з API) вища модель ще й коштує більше за виклик. На підписці claude.ai вважайте швидкість і запас використання замінником вартості.
  • Перелік у вибірнику моделей, типова модель і автоперемикання залежать від плану й змінюються.
  • Примітка курсу: у червні 2026 родина має й четвертий рівень над Opus (Claude Fable 5), а затримку Opus описують як помірну. Сертифікація фіксує триярусну схему Haiku/Sonnet/Opus, тож вчіть її; Fable позначено як неважливий для іспиту. Погляд із чотирма моделями див. у Темі 4.

6. Ліміти контексту й гігієна розмови

  • Вікно контексту заповнюється повідомленнями й файлами; тоді claude.ai підсумовує ранні повідомлення (повна історія лишається для довідки). Інструкції з перших 10 хвилин можуть не виконуватись через 90, бо деталі стиснулись, а не тому, що Claude вас ігнорує.
  • Ознаки, що розмові потрібне втручання: перестала виконувати раніші інструкції; відповідає лише на останній обмін; точність падає так, ніби бракує раннього контексту.

Плануйте наперед: діліть великі завдання, зберігайте проміжний прогрес у базі знань, перезапускайтесь із підсумку, а не розтягуйте одну сесію без кінця.

8. Тест модуля

Джерело показує питання без ключа; відповіді нижче виведено з логіки модуля.

  1. Щотижнева звірка запасів (незмінний документ порогів, новий файл щотижня, форматований звіт винятків) → B: Project із документом порогів у базі знань, постійними інструкціями про формат і Code Execution для порівняння.
  2. Складні відсотки з п'ятьма змінними, найнадійніший результат → C: Code Execution повертає перевірений результат.
  3. 500 договорів постачальників, low/medium/high за чітким рубрикатором, одна сесія → C: Haiku для структурованої класифікації у великому обсязі.
  4. Дві години в одній сесії, відповіді перестали відображати рамку, задану на початку → C: нова розмова з підсумком рішень і прогресу (більша модель не виправить стиснутий контекст).
  5. Два клієнти, не пускати контекст A у B → C: окремі Project із Project-scoped Memory (Incognito прибирає будь-яку сталість, а не розділяє клієнтів).

9. П'ять висновків

  1. Обирайте точку входу до промпта.
  2. Чотири шари, чотири проблеми: Projects несуть контекст, Skills задають процедури, Code Execution перевіряє обчислення, Memory зберігає тяглість.
  3. Рівні моделей це компроміс швидкість-здатність.
  4. Контекст це бюджет: restart, summarize чи persist.
  5. Варіативність невідворотна, перевірка структурна: навіть налаштовані Skills різняться від запуску до запуску.

  4. Чому довга сесія перестає виконувати ранні інструкції?
