Topic 5 of 11: Claude Platform 101 (English)

Claude Certified Architect path. Topic 5: building with Claude through the API: first call, models, the agent loop, tools, thinking, built-in tools, Skills, MCP, context, Managed Agents, Claude Code. Unknown words are in the cards: English words. Source: Anthropic course "Claude Platform 101" (14 lessons; the final quiz was not in the material). Code in the course uses older model IDs in places; section 14 compares it with the current docs (checked 2026-11-15).

1. What is the Claude Platform

The Claude Platform is Anthropic's infrastructure for building with Claude from code: you send structured requests and get structured responses, with control over the model, tokens, tools and system instructions. It consists of a REST API, SDKs, command-line tools and the Console (API keys, usage, managed agents, prompt testing).

Three layers:

Layer What it holds
Primitives Messages API, tool use, files, web search, code execution, MCP servers, Skills: the pieces you call
Infrastructure What you need past a prototype: managed agents, retries, queues, observability, prompt caching, memory
Controls Running in production: dashboards, evals, workspaces, usage and spend limits, request logs

Build with primitives, scale on infrastructure, run with control.

Example: a help desk button "Draft reply with Claude": define a client, fetch the ticket, call messages.create, show the draft. You are not building a chatbot; you are adding Claude to a product that already exists.

2. Your first API call

  1. Get an API key in the Console and make sure the account has credit (Billing page).
  2. Keep the key in an environment file such as .env.local, out of version control. Hardcoded keys end up leaked on GitHub.
  3. Install the SDK (npm install @anthropic-ai/sdk, or the Python package).

Every call goes through messages.create with three required things:

  • model: which Claude model handles it;
  • max_tokens: a cap on the response length;
  • messages: a list of objects with role user or assistant.

Optional but common: system, the system prompt that sets the role and tone (for example "You are a terse senior code reviewer").

response = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=2048,
    system="You are a terse senior code reviewer.",
    messages=[{"role": "user", "content": "Review this code: ..."}],
)
for block in response.content:
    if block.type == "text":
        print(block.text)

The response content is an array of blocks, not a string. Claude can return text, tool calls and thinking, so always loop and check block.type. The same call is the engine of a "summarize" endpoint in a real app: read a transcript, send it with a system prompt, store the result.

3. Choosing the right model

  • Four tiers, chosen with the model parameter: Fable (top capability, highest cost), Opus (hard problems), Sonnet (the balanced "sweet spot" for most production work), Haiku (fastest and cheapest: classification, extraction, routing). See Topic 4.
  • Build a small evaluation first: 20 or 30 representative examples from your real workload, scored against what "good" means for you.
  • The course's method: run the examples through Haiku first; if quality holds, you are done; otherwise step up to Sonnet; only use Opus when the task needs it. The right model is the cheapest one whose output you would actually ship.
  • Compare tiers by changing only the model field and reading response.usage: it returns input and output tokens, which is what your bill is based on.
  • Route different work to different models in one endpoint: for example classify every incoming file with Haiku, draft client updates with Sonnet, and reserve Opus for RFP responses.

4. The agent loop

An agent is Claude in a loop with no human in the middle: observe, decide, act, repeat.

  1. Send a message to Claude with tools available.
  2. Claude answers with a final answer or a request to use a tool.
  3. Your code runs the tool.
  4. Send the result back.
  5. Repeat until stop_reason is end_turn.
while True:
    response = client.messages.create(model=MODEL, max_tokens=1024, tools=tools, messages=messages)
    if response.stop_reason == "end_turn":
        break
    results = []
    for block in response.content:
        if block.type == "tool_use":
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": run_tool(block.name, block.input)})
    messages.append({"role": "assistant", "content": response.content})
    messages.append({"role": "user", "content": results})

Two turns in the weather demo: turn 1 ends with tool_use (Claude asks for get_weather); turn 2 ends with end_turn (the answer). You own the loop and the tools; Claude owns the reasoning. In production the shape is the same; only the tools and plumbing change (real tools, streaming to the UI, saving results). When you do not want to own the loop, managed agents run it for you.

5. What is tool use

  • A tool is a function you define and expose. Claude decides when to call it, but your code executes it.
  • A tool is a JSON schema with a name, a description and an input_schema, passed as a tools array.
  • The description is what Claude reads to decide whether to call the tool. Vague descriptions are the number one reason agents misfire or ignore available tools. Be specific.
  • stop_reason: "tool_use" is your signal; return the result as a tool_result block inside a user message, tied by tool_use_id.
  • Multiple tools: declare them all; Claude reads the descriptions and picks which to call, sometimes several in one turn. To add a tool, add it to the array and add a case to your dispatch function.
  • Tool runner (SDK helper, beta, in TypeScript, Python, Ruby, C#, Go, Java and PHP): you define each tool once (in TypeScript with betaZodTool() and a Zod schema, which also validates input) and the runner handles the whole tool use / tool result loop. Awaiting the runner returns the final message.
  • Real tools are thin wrappers around functions you already have (for example lookup_building_code).

6. What is thinking

  • Extended thinking lets Claude reason step by step before answering; it generates internal reasoning tokens (a chain of thought). Without it, a multi-step question can get a confidently wrong quick answer.
  • Adaptive thinking: Claude decides when to think and how much; there is no token budget to pick. The reasoning text stays hidden unless the request sets "display": "summarized".
  • Control depth with the effort parameter, which goes inside output_config, not next to thinking. Levels: low, medium, high, xhigh, max.
  • Use it for: math and multi-step logic, debugging, regulatory analysis, trade-offs and comparisons. Skip it for simple classification, extraction and boilerplate: it only adds latency and cost.
  • In production it lets an agent connect findings across sections (for example a wind-load spec in section 3 that conflicts with a material spec elsewhere).

7. Built-in tools

Some capabilities ship pre-built, so you write no code and host no sandbox.

таблицю можна гортати вбік →
Kind Who runs it Examples
Server tools Anthropic, on its infrastructure Web search (with citations), code execution (Python in a sandbox), web fetch
Client tools Your code, but the schema is built into Claude Memory (read and write across sessions), Bash (a persistent shell)
  • For server tools there is no agent loop: you declare the tool, Anthropic runs it, and the result comes back in the same response as new block types (server_tool_use, a code execution tool result) next to normal text.
  • Client tools have the same shape as custom ones, but you do not write the schema. For memory, four SDKs ship a helper that handles memory calls against storage you provide; for bash, your application runs the shell.
  • Web search can power a fact-check endpoint, but something verified on the internet is not necessarily true. Always double-check.

8. Skills

  • Skills are folders of instructions, scripts and resources that Claude loads dynamically. The core is a SKILL.md file. Upload once, then attach to any request.
  • Tools vs Skills: tools connect Claude to data and actions (what Claude can do); Skills teach a procedure (how you want it done), sometimes by running bundled scripts.
  • Progressive loading: at startup only the name and description load; the full Skill enters context when the agent decides it is relevant. This keeps context lean even with many Skills.
  • Upload with client.skills.create(...) (or in the Console), then attach through container.skills: a list of entries with type, skill_id and version. You can layer several.
  • On the API, Skills run inside the code execution tool's container, so code execution must be enabled in the request. Skills are generally available, so the old beta header is no longer required.
  • Use a Skill when the how matters as much as the what: for example every PM gets the same report structure, tone and order.

9. MCP

  • Why MCP exists: with custom tools you write and maintain every integration. With MCP, the service provider publishes an MCP server and maintains it. When their API changes, you change nothing.
  • Tools are for your systems (you own the code and maintenance); Skills are for your processes; MCP is for third-party services.
  • In the request: mcp_servers declares the connection (type, URL, name, optional auth token) and an mcp_toolset entry in tools grants access. Claude introspects the server and finds the tools itself; you write no schemas. The MCP connector is beta, so a beta header is required.
  • Limit what Claude may use: set default_config: {"enabled": False} and enable only chosen tools in configs (for example search and list, but not post or delete). Useful for read-only access and for saving context.

10. Context management

Context is everything Claude sees on a turn: system prompt, message history, tool definitions and results, attached files and Skills, thinking blocks. You pay for it on the way in; when the window is full, the request fails. The goal is not to fit everything, but to fit the right things.

таблицю можна гортати вбік →
Pattern What it does Type
Just-in-time context Load only what is needed now; let the agent pull more through tools (a code lookup tool instead of the whole code book in the prompt) Design pattern
Server-side compaction The API summarizes old turns into one block automatically when input crosses the trigger threshold; you opt in with a context_management edit API feature (beta)
Prompt caching Mark stable parts (system prompt, tool definitions, long documents) and reuse them at a fraction of the cost API feature
Memory tool Claude reads and writes a memory directory via tool calls; you implement the storage (files, database, encrypted store) API feature, survives across sessions

Each pattern fixes a different failure: cost, window size, statelessness. Production agents usually layer all four. Managed agents ship with caching and compaction on by default.

11. What are Managed Agents

Claude Managed Agents is a suite of APIs to build and deploy agents at scale, hosted on Anthropic's infrastructure: Claude works inside an isolated container with file system access, bash and web search. It is your agent loop, hosted for you.

Examples from the course: a Kanban ticket "optimize website performance" starts a session in an environment with Lighthouse and Puppeteer and your repo mounted; a rubric defines "done" (score above 90, no render-blocking resources, lazy-loaded images) and a separate grader in its own context window checks the result until it passes; several sessions run in parallel. A weekly research agent that uses web search, Python, an Excel Skill and MCP servers (Slack, Asana) and keeps a memory store so next week's report can say what changed. An incident-response setup where a coordinator agent delegates to specialists, each in its own context window on a shared file system, and a permission policy pauses sensitive actions for human approval.

Building blocks: Agents, Sessions, Environments, Tools (including your custom ones), MCP, Memory, Outcomes (rubrics and graders), Multi-agent coordination.

12. Building your first managed agent

Use a managed agent when the loop would run too long, do too much, or need to survive a hiccup (minutes to hours, many tools, state, files, resume after a network drop). Use a manual loop when you want full control.

Four primitives, in order:

  1. Agent: persona (model, system prompt, toolset), reusable across runs.
  2. Environment: where it runs (cloud or self-hosted, networking configuration).
  3. Session: one run of an agent in an environment; the unit of work.
  4. Events: the messages flowing in and out (actions, tool calls, results, replies).

Steps in the demo: create the agent (the bundled agent toolset covers file, bash and web tools); create a cloud environment with limited networking (the sandbox and web tools reach only hosts in allowed_hosts; use unrestricted only when you cannot list the sites in advance); create the session; open the event stream first (it only delivers events after it opens), then send the user.message event; read events: agent.message, agent.tool_use, session.status_idle.

Check stop_reason.type on idle: end_turn means the turn finished (or was interrupted); requires_action means a tool call needs an answer from you. The event history is stored on the server, so after a dropped connection you can open a new stream, list past events and skip any live event already returned. You are not running a while loop; you send events and read events.

13. Building with Claude Code

  • Claude Code is an agent that edits files and runs commands in your terminal. It has a built-in Claude API skill (invoke with /claude-api, or it loads automatically when it detects the TypeScript SDK).
  • A good prompt names the file, the pattern and the end state. It then fills in the code, runs it and fixes errors in place.
  • The recurring shape of API code: define a tool, hand it to a runner, return the result. Stub it, delegate it, review the diff.

16. Practice questions from the course quiz

The quiz has 8 questions; these 3 were available.

1. When Claude decides to use a tool, who actually executes it? Your code runs it and sends the result back. Claude only returns a tool-use request. Your application executes the tool and sends a tool_result back, then Claude continues. Flow: user request, Claude decides to call a tool, your code runs it, your code returns the result, Claude writes the final answer. Wrong answers: Claude runs it inside the model; Anthropic runs it automatically (true only for server tools such as web search and code execution); the SDK blocks until a human approves.

2. Why does context management matter for long-running agents? The window is finite and you pay for what is in it, so the goal is fitting the right things in. Keep what is relevant, summarize or drop what is outdated, avoid filling the window with unnecessary data. Wrong answers: Claude refuses requests above half the window; old messages are deleted after ten turns; bigger contexts always improve quality. More context is not better context.

3. Which jobs are the best fit for a managed agent? Long-running, sandboxed or background work. Multi-step, extended runs with tools, where your application does not have to orchestrate every step. Wrong answers: single quick questions (use a plain messages.create call); high-volume cheap classification (use Haiku through the Messages API); work where you must inspect every tool call yourself (use your own loop).
