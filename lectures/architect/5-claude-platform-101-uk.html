1. Що таке Claude Platform

Claude Platform це інфраструктура Anthropic для створення продуктів із Claude через код: ти надсилаєш структуровані запити й отримуєш структуровані відповіді та керуєш моделлю, токенами, інструментами й системними інструкціями. До неї входять REST API, SDK, командні утиліти і Console (ключі API, використання, managed agents, перевірка промптів).

Три шари:

Шар Що в ньому
Primitives (будівельні блоки) Messages API, tool use, файли, вебпошук, виконання коду, MCP-сервери, Skills: те, що ти викликаєш у коді
Infrastructure (інфраструктура) Те, що потрібне після прототипу: managed agents, повтори запитів, черги, спостережуваність, prompt caching, пам'ять
Controls (керування) Робота в продакшні: дашборди, evals, робочі простори, ліміти використання й витрат, журнали запитів

Будуй із примітивів, масштабуй на інфраструктурі, керуй через контроль.

Приклад: кнопка «Скласти відповідь через Claude» в системі підтримки: створити клієнт, дістати тікет, викликати messages.create, показати чернетку. Ти не пишеш чат-бот із нуля, а додаєш Claude в продукт, який уже існує.

2. Перший виклик API

  1. Отримай ключ API в Console і переконайся, що на акаунті є кошти (сторінка Billing).
  2. Тримай ключ у файлі оточення, наприклад .env.local, поза системою контролю версій. Ключі, вписані в код, зрештою потрапляють на GitHub.
  3. Встанови SDK (npm install @anthropic-ai/sdk або пакет для Python).

Кожен виклик іде через messages.create і потребує трьох речей:

  • model: яка модель обробляє запит;
  • max_tokens: стеля довжини відповіді;
  • messages: список об'єктів із роллю user або assistant.

Часто додають system: системний промпт, що задає роль і тон (наприклад, «Ти стислий старший рев'ювер коду»).

response = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=2048,
    system="You are a terse senior code reviewer.",
    messages=[{"role": "user", "content": "Review this code: ..."}],
)
for block in response.content:
    if block.type == "text":
        print(block.text)

content у відповіді це масив блоків, а не рядок. Claude може повернути текст, виклики інструментів і thinking, тому завжди проходь циклом і дивись на block.type. Той самий виклик лежить в основі ендпоінта «підсумувати» в справжньому застосунку: взяти стенограму, надіслати з системним промптом, зберегти результат.

3. Як обрати модель

  • Чотири рівні, вибір через параметр model: Fable (найпотужніша, найдорожча), Opus (складні задачі), Sonnet («золота середина» для більшості продакшн-завдань), Haiku (найшвидша й найдешевша: класифікація, витяг даних, маршрутизація). Докладніше в Темі 4.
  • Спершу зроби невелику оцінку (eval): 20-30 типових прикладів із твоєї справжньої роботи й критерії, що для тебе означає «добре».
  • Метод курсу: прожени приклади через Haiku; якщо якість тримається, то все; якщо ні, піднімись до Sonnet; Opus бери лише тоді, коли без нього не обійтись. Правильна модель це найдешевша з тих, чий результат ти справді випустиш.
  • Щоб порівняти рівні, міняй лише поле model і дивись на response.usage: там вхідні й вихідні токени, а за них і рахується рахунок.
  • Розподіляй роботу між моделями в одному ендпоінті: наприклад, класифікуй кожен вхідний файл через Haiku, чернетки оновлень для клієнтів роби на Sonnet, а Opus лишай для відповідей на RFP.

4. Цикл агента

Агент це Claude у циклі без людини посередині: спостерігає, вирішує, діє, повторює.

  1. Надішли Claude повідомлення й доступні інструменти.
  2. Claude відповідає або остаточною відповіддю, або запитом викликати інструмент.
  3. Твій код виконує інструмент.
  4. Надішли результат назад.
  5. Повторюй, поки stop_reason не стане end_turn.
while True:
    response = client.messages.create(model=MODEL, max_tokens=1024, tools=tools, messages=messages)
    if response.stop_reason == "end_turn":
        break
    results = []
    for block in response.content:
        if block.type == "tool_use":
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": run_tool(block.name, block.input)})
    messages.append({"role": "assistant", "content": response.content})
    messages.append({"role": "user", "content": results})

У прикладі з погодою два ходи: у першому зупинка з tool_use (Claude просить get_weather), у другому end_turn (відповідь). Цикл та інструменти твої, міркування Claude. У продакшні форма та сама, міняються лише інструменти й обв'язка (справжні інструменти, потокова передача в інтерфейс, збереження результатів). Не хочеш вести цикл сам, віддай його managed agents.

5. Що таке tool use

  • Інструмент це функція, яку ти визначаєш і відкриваєш Claude. Коли її викликати, вирішує Claude, а виконує твій код.
  • Інструмент це JSON-схема з назвою, описом і input_schema, яку передають масивом tools.
  • Саме опис Claude читає, щоб вирішити, чи викликати інструмент. Нечіткі описи це головна причина, чому агенти схиблюють або не беруть доступні інструменти. Пиши конкретно.
  • Сигнал до дії: stop_reason: "tool_use"; результат повертай блоком tool_result усередині повідомлення з роллю user, прив'язаним через tool_use_id.
  • Кілька інструментів: оголоси всі; Claude прочитає описи й сам вибере, що викликати, іноді кілька за один хід. Щоб додати інструмент, додай його в масив і додай гілку у функцію-диспетчер.
  • Tool runner (допоміжний засіб SDK, beta, у TypeScript, Python, Ruby, C#, Go, Java і PHP): інструмент описуєш один раз (у TypeScript через betaZodTool() і схему Zod, яка ще й перевіряє вхід), а runner веде весь цикл tool use / tool result. Дочекавшись runner, отримуєш фінальну відповідь.
  • Справжні інструменти це тонкі обгортки над функціями, які в тебе вже є (наприклад, lookup_building_code).

6. Що таке thinking

  • Extended thinking дає Claude міркувати крок за кроком перед відповіддю: він породжує внутрішні токени міркування (ланцюжок думок). Без цього на багатокрокове питання можна отримати швидку, але впевнено хибну відповідь.
  • Adaptive thinking: Claude сам вирішує, коли й скільки думати; обирати бюджет токенів не треба. Текст міркувань прихований, якщо в запиті немає "display": "summarized".
  • Глибину задають параметром effort, який стоїть усередині output_config, а не поруч із thinking. Рівні: low, medium, high, xhigh, max.
  • Коли вмикати: математика й багатокрокова логіка, відлагодження, регуляторний аналіз, компроміси й порівняння варіантів. Коли ні: проста класифікація, витяг даних, шаблонний текст: там це дає лише затримку й витрати.
  • У продакшні це дозволяє агенту зв'язувати знахідки між розділами (наприклад, специфікація вітрового навантаження в розділі 3 суперечить специфікації матеріалів деінде).

7. Вбудовані інструменти

Деякі можливості вже готові, тож не треба писати код чи тримати пісочницю.

Тип Хто виконує Приклади

8. Skills

  • Skills це папки з інструкціями, скриптами й ресурсами, які Claude завантажує на льоту. Основа це файл SKILL.md. Завантажуєш один раз, потім підключаєш до будь-якого запиту.
  • Tools проти Skills: інструменти з'єднують Claude з даними й діями (що Claude може); Skills вчать процедури (як ти хочеш, щоб це було зроблено), іноді запускаючи вбудовані скрипти.
  • Поступове завантаження: на старті вантажаться лише назва й опис; повний Skill потрапляє в контекст, коли агент вирішить, що він доречний. Так контекст лишається легким навіть із багатьма Skills.
  • Завантаж через client.skills.create(...) (або в Console), підключай через container.skills: список записів із type, skill_id і version. Можна накласти кілька.
  • В API Skills працюють у контейнері інструмента виконання коду, тож у запиті має бути ввімкнено виконання коду. Skills загальнодоступні, тож старий beta-заголовок більше не потрібен.
  • Бери Skill, коли «як» не менш важливо, ніж «що»: наприклад, щоб кожен PM отримував однакову структуру, тон і порядок звіту.

9. MCP

  • Навіщо MCP: зі своїми інструментами ти сам пишеш і підтримуєш кожну інтеграцію. З MCP постачальник сервісу публікує MCP-сервер і підтримує його. Змінився їхній API, ти нічого не міняєш.
  • Tools для твоїх систем (код і підтримка твої); Skills для твоїх процесів; MCP для сторонніх сервісів.
  • У запиті: mcp_servers оголошує з'єднання (тип, URL, ім'я, необов'язковий токен), а запис mcp_toolset у tools дає доступ. Claude сам вивчає сервер і знаходить інструменти; схем писати не треба. MCP connector у beta, тож потрібен beta-заголовок.
  • Обмеж, що Claude може використовувати: задай default_config: {"enabled": False} і вмикай у configs лише потрібні інструменти (наприклад, пошук і список, але не публікація й видалення). Корисно для доступу лише на читання й для економії контексту.

10. Керування контекстом

Контекст це все, що Claude бачить за хід: системний промпт, історія повідомлень, визначення й результати інструментів, прикріплені файли й Skills, блоки thinking. Ти платиш за нього на вході; коли вікно заповнене, запит завершується помилкою. Мета не втиснути все, а вмістити потрібне.

11. Що таке Managed Agents

Claude Managed Agents це набір API для створення й розгортання агентів у масштабі, розміщених на інфраструктурі Anthropic: Claude працює в ізольованому контейнері з доступом до файлової системи, bash і вебпошуку. Це твій цикл агента, який хтось інший веде за тебе.

Приклади з курсу: тікет на Kanban-дошці «оптимізувати швидкість сайту» запускає сесію в оточенні з Lighthouse і Puppeteer та підключеним репозиторієм; rubric (критерії) визначає «готово» (оцінка понад 90, жодних ресурсів, що блокують рендер, ліниво завантажені зображення), а окремий grader у власному вікні контексту перевіряє результат, поки той не пройде; кілька сесій можуть працювати паралельно. Тижневий дослідницький агент, який шукає в мережі, рахує на Python, формує Excel через Skill, постить у Slack і створює задачу в Asana через MCP, а ще веде сховище пам'яті, щоб наступного тижня звіт міг сказати, що змінилось. Реагування на інциденти, де координатор делегує трьом спеціалістам, кожен у своєму контексті на спільній файловій системі, а політика дозволів зупиняє чутливі дії до схвалення людиною.

Складники: Agents, Sessions, Environments, Tools (зокрема власні), MCP, Memory, Outcomes (rubrics і graders), Multi-agent coordination (кілька агентів).

12. Перший managed agent

Бери managed agent, коли цикл надто довгий, робить надто багато або має пережити збій (хвилини чи години, багато інструментів, стан, файли, відновлення після обриву мережі). Бери ручний цикл, коли потрібен повний контроль.

Чотири примітиви, по порядку:

  1. Agent: «персона» (модель, системний промпт, набір інструментів), використовується повторно.
  2. Environment: де він працює (хмара чи власна інфраструктура, налаштування мережі).
  3. Session: один запуск агента в середовищі; одиниця роботи.
  4. Events: повідомлення, що ходять туди й назад (дії, виклики інструментів, результати, відповіді).

Кроки в демо: створити агента (вбудований набір інструментів агента охоплює файли, bash і веб); створити хмарне середовище з обмеженою мережею (limited) (пісочниця й вебінструменти бачать лише хости з allowed_hosts; unrestricted бери лише тоді, коли сайти наперед не перелічити); створити сесію; спершу відкрити потік подій (він доставляє лише події, що настали після відкриття), потім надіслати подію user.message; читати події: agent.message, agent.tool_use, session.status_idle.

Коли агент завмер у стані idle, перевір stop_reason.type: end_turn означає, що хід закінчено (або перервано); requires_action означає, що виклик інструмента чекає на твою відповідь. Історія подій зберігається на сервері, тож після обриву з'єднання відкрий новий потік, отримай список минулих подій і пропускай живі події, які в списку вже були. Ти не ведеш цикл while: ти надсилаєш події й читаєш події.

13. Робота з Claude Code

  • Claude Code це агент, який редагує файли й запускає команди в твоєму терміналі. Має вбудований Claude API skill (виклик /claude-api, або вантажиться сам, коли він бачить TypeScript SDK).
  • Добрий промпт називає файл, патерн і кінцевий результат. Далі Claude Code дописує код, запускає його й виправляє помилки на місці.
  • Типова форма коду для API: описати інструмент, віддати runner, повернути результат. Зроби заготовку, віддай Claude Code й переглянь diff.

«Проганяй eval від Haiku вгору» Робочий метод, коли ставка на ціну. Власна порада документації, коли вагаєшся: починай з Opus, а Fable бери, якщо Opus на вищому effort не дотягує. Роби так: є eval, проганяй його; нема, починай з Opus
Рівні effort low, medium, high (за замовчуванням), xhigh, max Рівні підтверджено (Help Center). Типове значення залежить від моделі: у таблиці документації типовий effort API це medium для Opus 5.5 і Haiku 5.5, high для Sonnet 5.5 і Fable 5.2
Managed Agents «увімкнено за замовчуванням для кожного акаунта API» Підтверджено, але документація додає: це beta (заголовок managed-agents-2026-04-01, SDK ставить його сам) і воно не підпадає під Zero Data Retention і HIPAA (окрім self-hosted Managed Agents)
MCP connector у beta, заголовок mcp-client-2025-11-20 Підтверджено beta; у документації названо mcp-client-2026-09-15 і mcp-client-2025-11-20; старий mcp-client-2025-04-04 застарів. Connector для віддалених серверів; не підпадає під Zero Data Retention
Server-side compaction із заголовком compact-2026-01-12 і записом compact_20260112 Змінилось: документація тепер описує два види в beta: compaction on demand (заголовок compact-2026-09-04, параметр верхнього рівня compaction, момент вирішуєш ти) і compaction at a token threshold (API стискає, коли вхід досягає заданого порога; саме це показує курс). Перед кодуванням звір актуальний заголовок і параметр
Skills загальнодоступні; працюють у контейнері виконання коду Це твердження курсу; цього разу в документації не перевіряв
Tool runner у beta у семи SDK Це твердження курсу; не перевіряв
Точні версії інструментів (web_search_20260209, code_execution_20260120, agent_toolset_20260401) Не перевіряв; рядки версій змінюються, копіюй їх з поточної документації

Висновок для іспиту: знай поняття (шари, цикл, stop_reason, tool use, серверні й клієнтські інструменти, Skills проти tools проти MCP, чотири патерни контексту, agent / environment / session / events), а ID моделей, beta-заголовки й рядки версій сприймай як довідкові факти, що змінюються.
