🖼 IAM: політики, boundary, SCP

Політика: JSON зі списком правил
ЕлементСуть
Versionзавжди 2012-10-17: версія мови, не дата
Statementсписок правил
EffectAllow або Deny
Actionservice:Operation, можна *
NotActionусе, окрім цього (обережно)
ResourceARN або шаблон
Principalкому; лише в resource-based
Conditionпрефікс, IP, MFA, тег, час
Читати так: хто (Principal) може чи не може (Effect) що (Action) з чим (Resource) за якої умови (Condition). Без Version змінні на кшталт ${aws:username} не підставляються.
Класика іспиту: бакет і об'єкти
Дія над бакетом
  • s3:ListBucket
  • Resource: arn:aws:s3:::bucket
Дії над об'єктами
  • s3:GetObject, s3:PutObject
  • Resource: arn:aws:s3:::bucket/*
ListBucket на bucket/* дає AccessDenied, бо такого ресурсу для цієї дії нема.
Типи політик
Дають права
  • AWS managed
  • Customer managed
  • Inline: живе з ідентичністю
  • Resource-based: на ресурсі
  • Trust policy: на ролі
Лише обмежують
  • Permission boundary: стеля для користувача чи ролі
  • SCP: стеля для акаунта чи OU
  • Session policy: звужує сеанс AssumeRole
Boundary проти SCP
BoundarySCP
Декористувач чи рольAWS Organizations: корінь, OU, акаунт

Ефективні праваперетин з identity policyперетин на кожному рівні шляху
Не діє на-management-акаунт, service-linked ролі
SCP діє на member-акаунти, включно з root такого акаунта. За замовчуванням прикріплена FullAWSAccess. Deny-list (додати Deny на небажане) простіший за allow-list. Потрібні all features в Organizations.
